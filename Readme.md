## 1. 项目概览

### 背景与痛点

在高中、大学的班级/院系羽毛球比赛中，长期依赖**手写记分表 + Excel 排赛程**的传统模式，存在三个核心痛点：

| 痛点 | 传统做法 | 后果 |
|------|---------|------|
| 计分效率低 | 纸质记分表，边打边划正字 | 容易记错、丢失、事后无法复盘 |
| 赛程排布易出错 | Excel 手动拉表，人工核对晋级 | 轮空处理容易遗漏，晋级路径不清晰 |
| 赛后统计难 | 各场比分散落各处 | 无法快速查看完整赛果和历史数据 |

### 解决方案

**Badminton Scoring** 是一款微信小程序，一期聚焦羽毛球项目，提供两大核心能力：

- **实时记分牌** — 横屏防误触 UI + 快照栈撤销 + 本地离线容错
- **智能赛程管理** — 淘汰赛自动排表 + 轮空坍缩 + 赛果回传自动晋级

> 打完一场比赛，记分牌点击"同步结算"→ 胜者自动晋级下一轮 → 对阵图实时刷新。形成完美的**物理闭环**。

## 3. V1.0 核心功能特性

### 模块一：智能计分板 (Scoreboard)

记分板是本项目的**前端核心组件**，可脱离后端独立运行，支持"离线计分 → 云端同步"的混合模式。

#### 🎯 横屏分屏防误触 UI

```
┌────────────────────────────────────────┐
│ [左退赛]  [撤销][换边][结束][上帝模式]  [右退赛] │
│                                        │
│         张三                李四        │
│   ┌──────────────┐  ┌──────────────┐   │
│   │              │  │              │   │
│   │      21      │  │      19      │   │
│   │   ● 发球     │  │              │   │
│   └──────────────┘  └──────────────┘   │
│                                        │
└────────────────────────────────────────┘
```

- 页面强制横屏 (`pageOrientation: landscape`)，左右分屏对称布局
- 点击分数区域直接 +1 分，发球权自动跟随
- 深色主题 (`#1A2A3A`) + 橙色强调色 (`#FF8C00`)，户外阳光下清晰可见

#### ⏮️ 快照栈撤销 (History Stack)

```
每次操作前: pushHistory()  →  将完整状态快照压栈
点击撤销:   historyStack.pop()  →  applySnapshot(prev)  →  恢复上一步
```

不同于事件溯源或增量记录，**快照栈**模式实现简单、容错性强。每次快照包含：

- 双方队名、分数、发球权
- 换边状态 (`sidesSwapped`)
- 比赛计时、退赛/完赛状态

#### 💾 Storage 离线容错

```js
// 页面加载：优先从本地缓存恢复
onLoad → restoreStateFromStorage() → 若有缓存，完整恢复上次比赛状态
// 每次操作后：自动持久化
addScore / switchSides / retire / endMatch → saveStateToStorage()
```

- 基于 `wx.setStorageSync` 实现
- 按 `matchId` 区分缓存键，同一比赛多次进入互不干扰
- 缓存恢复后的空值兜底逻辑（`'' || '左队'` → 显示默认标签）

#### 👑 上帝模式 (God Mode)

解决实际比赛中的非标准场景（裁判误操作、特殊规则），开启后在分数面板上方显示 ±1 按钮，允许跳出规则自由调整分数。作为标准加分流程的兜底方案。

#### 🏁 退赛 / 完赛结算

- **退赛**：弹出确认框 → 记录退赛方与胜者 → 显示比赛用时
- **结束比赛**：比较分数判定胜者 → 展示结算卡片（胜者、比分、用时）
- **同步结算**：将赛果回传后端 → 触发自动晋级 → 返回对阵图

#### 🔄 换边安全机制

换边是实际比赛中的高频操作。记分牌完整追踪换边状态：

- `sidesSwapped` 标记位在每次换边时 toggle
- 同步结算时，**胜者侧**和**分数**均根据 `sidesSwapped` 反向映射回原始左右
- 确保后端记录的比分与选手严格对应，不会出现"张三的 21 分跑到李四名下"

### 模块二：赛事大厅与赛程树 (Tournament & Bracket)

#### 📋 一键创建赛事

```
输入赛事名称 → 输入地点(选填) → 粘贴选手名单 → 点击"一键生成赛事"
                                                    ↓
                              后端自动完成: 建赛事 → 存选手 → 生成签表 → 写入对阵记录
                                                    (单个 @Transactional 保证原子性)
```

- 选手名单支持空格、换行、逗号分隔，前端自动解析去重
- 最少 2 人，无上限（实际受淘汰赛轮次限制）

#### 🧠 BracketEngine — 淘汰赛排表算法

这是项目**技术含量最高**的模块。核心流程：

```
输入: n 个选手 (已随机 shuffle)

Step 1 · 容量对齐
  n → 向上取整到 2 的幂 p  (例: 6人 → p=8)

Step 2 · 种子排序
  递归构建平衡二叉树种子序列
  关键不变式: 每对相邻种子之和 = p + 1
  例: p=8 → [1,8,4,5,2,7,3,6]

Step 3 · 轮空坍缩
  种子编号 > n 的位置 → 轮空位
  第一轮自动判胜 → propagateWinnerToParent() → 晋级到下一轮

Step 4 · 晋级链表
  每场记录 next_match_id + next_match_slot (left/right)
  决赛: next_match_id = null
  上传赛果 → 沿链找到下一场 → 填入胜者 → 双方就位自动激活 (status=1)
```

**设计哲学：** 相比一次性生成完整树 + 赛后递归重算，这种"链表指针"式设计让每场比赛独立更新、职责单一。多场比赛并行进行时互不干扰，天然支持并发场景。

#### 🌳 "生命之树"对阵图

```
第 1 轮          第 2 轮        第 3 轮
┌─────────┐
│ 张三    │
│  vs     │──┐
│ 李四 ✓  │  │    ┌─────────┐
└─────────┘  ├───→│ 李四    │
             │    │  vs     │──┐
┌─────────┐  │    │ ???     │  │
│ 王五 ✓  │  │    └─────────┘  │    ┌─────────┐
│  vs     │──┘                 ├───→│  ???    │
│ (轮空)  │                     │    │  vs     │
└─────────┘                     │    │ ???     │
                   ┌─────────┐  │    └─────────┘
                   │ 赵六    │  │
                   │  vs     │──┘
                   │ 孙七 ✓  │
                   └─────────┘
```

- 前端按轮次 (`roundNum`) 分组，横向 `<scroll-view>` 可左右滑动
- 胜者橙色高亮 + 粗体，轮空自动标记"已完赛"
- 点击任意比赛卡片 → 进入记分牌页面，自动传入选手名字
- 从记分牌返回时 `onShow` 自动刷新，展示最新晋级结果

## 4. 开发历程与决策复盘

### Phase 0 — 基调奠定

**技术选型决策：**

| 决策点 | 选择 | 放弃的方案 | 理由 |
|--------|------|-----------|------|
| 前端框架 | uni-app (Vue 3) | 原生微信小程序 / Taro / React | 团队 Vue 背景，一套代码多端编译，学习成本最低 |
| 后端架构 | 模块化单体 | 微服务 (Spring Cloud) | MVP 阶段业务简单，微服务徒增运维复杂度；模块化单体保留未来拆分可能 |
| ORM | MyBatis-Plus | JPA / MyBatis 原生 | 兼顾灵活性与开发效率，Lambda QueryWrapper 可读性强 |
| 数据库 | MySQL 8.0 | PostgreSQL / H2 | 团队最熟悉，周边工具链完善 |

**确立的工程原则：**
- 前后端分离，JSON 通信
- 统一 `ApiResponse<T>` 响应体：`{ code, message, data }`
- 全局异常拦截：业务异常 400，状态异常 500，参数校验失败 400

### Phase 1 — 需求裁剪

采用 **MVP (Minimum Viable Product)** 策略：

- **砍掉**：篮球/乒乓球/排球等多球类规则适配、局分配置（21分/15分/追分）、团体赛模式、循环赛
- **聚焦**：羽毛球单打淘汰赛计分闭环 — 这是最高频、最刚需的场景
- **三层赛制模型**：`Tournament（赛事）→ Player（选手）→ Match（比赛）`，一层套一层，职责清晰

### Phase 2 — 前端计分引擎

**自底向上开发**，优先完成不依赖后端的纯本地计分板：

1. 搭建 uni-app 项目骨架，配置 `pages.json` 三页面路由
2. 实现计分板核心逻辑：加分、撤销、换边、退赛、结束比赛
3. 引入 `historyStack` 快照栈作为撤销机制的数据结构
4. 接入 `wx.setStorageSync` 实现本地持久化
5. 开发上帝模式作为边界情况的兜底方案
6. 封装 `request.js` 网络层，自动适配小程序/H5 环境（`getBaseUrl()` 环境探测）

> **关键决策：** 计分板设计为"黑盒组件"，内部状态自管理，与后端解耦。这保证了即使网络断开，计分功能 100% 可用。

### Phase 3 — 后端算法破局

**淘汰赛排表算法是最大技术难点：**

1. 第一版：简单顺序排列 → 强选手可能首轮相遇
2. 第二版：引入**递归种子排序**，保证相邻种子编号之和相等 → 强选手合理安排在不同分支
3. 第三版：实现**轮空自动坍缩** → `propagateWinnerToParent()` 递归传播
4. 第四版：引入**晋级链表** (`next_match_id` + `next_match_slot`) → 赛果上传后自动推导晋级路径

**质量保障：** 编写了 **9 个单元测试用例**，覆盖：

| 场景 | 断言数 |
|------|--------|
| 2 人 → 1 场比赛 | 5 |
| 3 人 → 正确处理轮空 | 5 |
| 4 人 → 无轮空 | 4 |
| 6 人 → 正确坍缩 + 晋级 | 7 |
| 8 人 → 3 轮完整签表 | 5 |
| 非法参数 → 抛异常 | 2 |
| ID 全局唯一性 | 1 |
| 轮次数对数验证 | 4 |

### Phase 4 — 全栈贯通

**联调过程中解决的关键问题：**

1. **CORS 跨域** — 微信小程序 `uni.request` 直连后端需配置 CORS；H5 开发环境通过 Vite `server.proxy` 代理 `/api` 到 `127.0.0.1:8080`

2. **自动建库建表** — Spring Boot 配置 `createDatabaseIfNotExist=true` → 首次启动自动创建 `scoring_mvp` 数据库；MyBatis-Plus 自动建表

3. **赛果同步闭环** — 记分牌"同步结算" → 后端 `finishMatch` → 更新当前比赛 → 沿 `next_match_id` 找到下一场 → 填入胜者 → 双方就位则比赛自动激活 (status=1) → 决赛则赛事标记结束 (status=2)

4. **记分牌刷新机制** — `onShow` 生命周期中重新调用 `fetchData()`，从记分牌返回对阵图时自动拉取最新数据，晋级结果即时可见

5. **换边安全修复** — 发现同步结算时换边后的分数和胜者侧未做反向映射，引入 `sidesSwapped` 标记位贯穿快照、缓存、同步全链路

## 5. 快速启动指南

### 环境要求

| 工具 | 版本要求 |
|------|---------|
| Node.js | ≥ 18 |
| JDK | 17 |
| MySQL | 8.0 |
| Maven | 3.9+（项目已内置于 `.tools/`） |
| 微信开发者工具 | 最新稳定版 |

### 后端启动

```bash
# 1. 进入后端目录
cd backend

# 2. 修改 application.yml 中的数据库密码
#    src/main/resources/application.yml
#    spring.datasource.password: 你的MySQL密码

# 3. 确保 MySQL 正在运行 (端口 3306)

# 4. 启动 Spring Boot
../.tools/apache-maven-3.9.9/bin/mvn spring-boot:run

# 后端运行在 http://127.0.0.1:8080
```

> 首次启动时，`createDatabaseIfNotExist=true` 会自动创建 `scoring_mvp` 数据库，MyBatis-Plus 会根据实体类自动建表。

### 前端启动

```bash
# 1. 安装依赖 (首次)
npm install

# 2. 启动微信小程序开发模式
npm run dev:mp-weixin

# 3. 打开微信开发者工具
#    导入项目 → 选择 dist/dev/mp-weixin/ 目录
#    填入你的 AppID (或选择"测试号")
```

### 环境说明

- **微信小程序环境**：`request.js` 自动探测环境，小程序直连后端 IP（需修改 `src/utils/request.js` 中的 `BASE_URL` 为你的局域网 IP）
- **H5 开发环境**：Vite 代理自动转发 `/api` 请求到 `127.0.0.1:8080`

## 6. API 接口一览

| 方法 | 路径 | 说明 |
|------|------|------|
| `GET` | `/api/v1/tournaments` | 获取赛事列表（按创建时间倒序） |
| `POST` | `/api/v1/tournaments` | 创建赛事 → 自动生成淘汰赛签表 |
| `GET` | `/api/v1/tournaments/{id}/bracket` | 获取签表详情（含选手、所有轮次对阵） |
| `PUT` | `/api/v1/matches/{id}/finish` | 上传比赛结果 → 自动晋级胜者 |

**统一响应格式：**

```json
{
  "code": 0,
  "message": "success",
  "data": { ... }
}
```

- `code = 0` 表示成功，前端取 `data` 字段
- `code ≠ 0` 表示失败，前端取 `message` 字段弹 Toast
