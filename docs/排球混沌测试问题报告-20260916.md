## 3. 基线复核：seed 10015 副攻克隆漏洞（已修复，待回归确认）

### 3.1 现场还原

第 1 局，比分 15:13，第 47 步 `SCORE` 首次触发断言，出错瞬间右队场上：

```
右队场上: ["B_5", "B_5", "B_3", "B_2", "B_1", "B_10"]
                        ↑ 0 号槽与 1 号槽出现两个 B_5
```

### 3.2 缺陷机理（与动作流水吻合）

1. B_8 为右队自由人；B_5 为其绑定的前排副攻。B_8 替换 B_5 上场后，B_5 以"被自由人替换"状态处于场下。
2. **第 44 步** `SUBSTITUTION`：常规换人通道仅校验 `!isOnCourt(B_5)`，未识别其正处于自由人激活链路，将 B_5 作为普通替补放入 0 号槽位。
3. **第 47 步** `SCORE`：得分轮转导致自由人转至前排触发"原进原出"，系统又自动把 B_5 放回其原槽位——两个 B_5 同时在场，此后 97 次 `DUPLICATE_ON_COURT_PLAYER` 与 58 次 `LIBERO_IN_FRONT_ROW` 断言连锁爆发。

### 3.3 修复确认状态

- `3861595`（09-15）：按 FIVB 规则重构双层站位模型，替补资格校验纳入"正被自由人替换"状态 → 针对性修复。
- `4b12bb5`（09-16）：修复跨局站位继承局末轮转、调轮次副攻漂移 → 同族问题加固。
- **本批次 600 场（含 12600+ 次换人、大量连续撤销场景）若 0 重复球员断言，即为回归通过**；结论见 §5。

## 4. 测试基建缺陷与修复（本次新发现）

夜批筹备中发现原仿真体系在当前环境下**连 10 场都无法单进程跑完**，与文档"千场 3 分钟"的宣称严重不符。诊断过程与结论如下（探针实测数据），修复均为测试文件，不触及生产代码。

### 4.1 【已修复】批量仿真 worker 堆内存 OOM

- **现象**：`FUZZ_MATCHES=10` 时 worker fork 报 `Ineffective mark-compacts near heap limit`，进程崩溃，报告不落盘；3 场可过，10 场必炸。
- **定位**（逐场堆采样探针）：
  - 每场保留约 **0.6~0.7GB**，与动作数严格线性（约 3MB/动作），与撤销次数无关；
  - `effectScope` 包裹 `useScoreboard()` 回收响应式副作用后**无改善** → 排除 Vue 响应式图；
  - 堆曲线呈锯齿状（自然 major GC 后从 2.1GB 跌回 490MB）→ 主体是**浮动垃圾 + V8 惰性回收**，而非纯泄漏；
  - 垃圾主源：`uni.setStorageSync` 等均为 `vi.fn()` mock，**永久保留每次调用的实参**——每动作保存一次全量状态（含 40 条历史快照，约 3MB/次），200 动作即累积约 600MB。
- **修复**（`scoreboard-fuzzer.js`）：
  1. 每场结束 `vi.clearAllMocks()`（只清调用记录，不破坏 mock 行为）；
  2. 每场结束强制 `globalThis.gc()`（需 `--expose-gc`，编排器已注入）；
  3. 每场用独立 `effectScope` 包裹 `useScoreboard()`，赛后 `scope.stop()`（卫生修复）。
- **效果**：10 场连续仿真堆从 52MB → 162MB（残余约 11MB/场的缓慢真实保留，根因待查，100 场/块、4GB 堆上限下安全裕量充足）。

### 4.2 【已修复】批量用例超时写死 120 秒

- **现象**：`scoreboard-fuzzer.test.js` 中 `it(..., 120000)` 写死超时；本机实测单场 27~30 秒，8 场以上即使仿真成功也会被误判超时失败。
- **修复**：超时按 `FUZZ_MATCHES` 线性缩放（`30000 + 25000 × 场数`）。

### 4.3 【新增】分块编排器 `run-fuzz-batch.mjs`

单进程长跑既受内存斜率限制，也无中断恢复能力。新增编排器提供：

- **分块隔离**：每块独立 vitest 进程 + 4GB 堆上限，块结束整体释放；
- **种子连续性**：块内 seed 公式与 `runFuzzerBatch` 完全一致，全局可复现；
- **断点续跑**：块产物按 baseSeed 归档，重复执行同一命令自动跳过已完成块；
- **块级超时**：单块超时强制 `taskkill` 后继续下一块，不会卡死整晚；
- **增量合并**：每块结束立即刷新 `fuzz-summary.json` / `fuzz-anomalies.json`，中断不丢数据；
- **看门狗联动**：配合每 30 分钟巡检的自动化任务实现无人值守。

### 4.4 【开放问题】留给下次验收

1. **每场约 11MB 的残余真实保留**：量级无害（100 场/块 ≈ 1.1GB），但根因未查明，跑万场级需先解决；
2. **单场 27~30 秒 vs 文档宣称"数毫秒"**：`Date` 被 fake timers 劫持导致场内无法直接计时，粗测瓶颈在全量状态序列化（每动作 `saveMatchState` 深拷贝含 40 条历史快照的状态）。若需提速一个量级，可评估"历史快照增量化/按需序列化"；
3. **文档数字修正**：建议将《排球状态机混沌测试与Agent接手指南》中"100 场约 30 秒 / 1000 场约 3 分钟"更新为本机实测数据，并补充 `run-fuzz-batch.mjs` 用法。

### 5.1 根因溯源与修复（chunk-000 六场 CRITICAL 已全部定论）

**结果**：94 场干净，6 场 CRITICAL（0 场 SUSPICIOUS）。6 场异常全部发生于决胜局
8 分换边（`CONFIRM_SIDE_SWITCH`）前后，且动作流水里都存在「换边确认之后发生过 `UNDO`」
或「换边确认后立刻执行 `SUBSTITUTION`」的组合。按症状分两类：

| 症状 | 场次（matchSeed） | 触发序列 |
|---|---|---|
| `DUPLICATE_ON_COURT_PLAYER`（场上重复球员，多为自由人克隆） | 20310781 / 20639890 / 20968999 / 21058756 | 换边确认 → **撤销** →（再换边）→ 轮转时克隆 |
| `LIBERO_IN_FRONT_ROW` + 跨队球员混入 | 20380592 / 20440430 | 换边确认 → 撤销/换人 → 异队球员被当作普通替补换入前排 |

#### 5.1.1 根因一【产品缺陷，已修复】：撤销跨越换边边界不还原花名册归属

- **机理**：`confirmDisplaySideSwitch()` → `swapSides()` 做两件事——① `applyState(交换后的快照)`
  翻转球场/比分/自由人配置坐标；② **原地交换 `leftTeam`/`rightTeam` 花名册引用**（并
  `syncRuntimeSideCollections()` 翻转待选状态）。而历史快照 `buildHistorySnapshot()`
  **不含花名册**。因此 `undo()` 弹出一个换边前的快照恢复球场坐标后，花名册仍停留在换边后
  的归属上 → 名册与球场错位。
- **后果链**：错位后 `getPlayerState` 的自由人判定（`isLiberoMember` → `memberById` 按错位名册
  查询）与替补资格校验全部张冠李戴；下一次得分轮转触发自由人"原进原出"结算时，即按错误的
  绑定关系把场下球员放回场上 → `DUPLICATE_ON_COURT_PLAYER`（match 5/38/71/80）。
- **真实性**：裁判在换边确认后发现换边前比分录错、按撤销回退是**真实操作路径**，此前每次
  都会产生一个错位状态继续比赛。`4b12bb5` 并非引入者——该路径在换边+撤销组合下一直存在。
- **修复**（`useScoreboard.js`）：`undo()` 在 `applyState` 前记录
  `screenLeftParticipantSide`，若快照回退导致屏侧翻转，则同步换回 `leftTeam`/`rightTeam`
  并调用 `syncRuntimeSideCollections()`。

#### 5.1.2 根因二【防御缺失 + 测试器缺陷，已修复】：名册外球员被当作普通替补放行

- **机理**：换边后（未撤销）花名册与球场坐标已合法交换，此时 `getPlayerState(side, id)` 对
  **本侧名册查不到的球员**（异队 ID）会一路落到 `BENCH_FREE` 兜底分支 → `canSelectBenchPlayer`
  放行。测试器此前的换人选择器用**静态场景名册**（side=right 恒取 B 队），换边后送入的正是
  异队 ID，于是 B 队自由人 B_8 被当作普通替补换入前排 0 号槽
  （match 12/18/71，`LIBERO_IN_FRONT_ROW` / 混编球场）。
- **真实性**：真实裁判 UI 的替补名单按屏侧名册渲染，正常操作送不进异队 ID；但该兜底分支
  意味着任何数据错位（持久化状态与名册不同步等）都会静默放行，属于应堵住的防御缺口。
- **修复**：
  - `useScoreboard.js`：`getPlayerState` 对 `memberById` 查不到的球员直接返回 `''`
    （不可选），不再落入 `BENCH_FREE`；
  - `scoreboard-fuzzer.js`：换人选择器改按**当前屏侧**解析花名册（读取新暴露的
    `screenLeftParticipantSide`），与真实 UI 行为对齐；
  - `scoreboard-fuzzer.js`：`auditStateInvariants` 的自由人集合同样按屏侧解析——修复前
    换边后的前排自由人会被漏检（match 5 的 B_8 前排槽位 0 当时未被报
    `LIBERO_IN_FRONT_ROW` 正是此盲点）。
