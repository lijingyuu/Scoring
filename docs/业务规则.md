# 业务规则 — 核心业务状态机与算法

> 固化最烧脑的体育规则：赛制流转、计分、排名/晋级、排球专项。算法约束以此为准。
> 关联：[[数据库.md]] · [[架构.md]]

## 1. 赛制推进流转

### 1.1 整体状态机

```
创建赛事 (status=0)
  → 生成签表/赛程 → status=1 (进行中)
  → 小组赛(如有) → 全部结束 → 生成淘汰赛
  → 淘汰赛逐轮推进
  → 决赛结束 → status=2 (已结束)
```

### 1.2 单场比赛闭环（核心链路）

```
双方选手就位 → 记分页进入"进行中"（match status 保持 0；后端仅在完赛置 2）
  ↓
记分板操作: 加分 → 换边 → 暂停 → 换人(排球)
  ↓
一方达到获胜条件 → finishMatch
  ↓
后端 finishMatch():
  1. 更新当前比赛: status=2, winnerId, gameScores, scoreDisplay
  2. 查 next_match_id（淘汰赛晋级链表）
     ├─ 有下一场 → 填入胜者到 nextMatchSlot(left/right)
     │              写入胜者到下一场选手位(slot)；下一场 status 保持 0 (待赛)，可操作性由执裁锁/前端就位判定决定
     └─ 无下一场 → 按组别完赛判定: 小组赛(type1)不触发结束；纯循环赛须本组别
                    全部赛程完赛；启用季军赛的淘汰赛须决赛+季军赛全部完赛
                    → division.status=2 → 全部组别完赛后 tournament.status=2
```

### 1.3 淘汰赛晋级链表

```
match A: next_match_id = match C, next_match_slot = "left"
match B: next_match_id = match C, next_match_slot = "right"
match C: next_match_id = null (决赛)

A 结束 → winnerId 写入 C.leftPlayerId
B 结束 → winnerId 写入 C.rightPlayerId
C.leftPlayerId ≠ null AND C.rightPlayerId ≠ null → 仅两个选手位就绪，C.status 保持 0 (待赛)；可操作性由执裁锁/前端就位判定决定
```

### 1.4 小组赛出线 → 淘汰赛

```
小组赛全部结束 → 用户点击"生成淘汰赛"
  → 校验: 所有小组赛已完成、无未解决平局
  → collectQualifiers(): 收集每个小组的出线者
  → 蛇形交叉排列: 第1名按组号升序、第2名按组号降序(避免同组)
  → BracketEngine.generateKnockoutBracketBySlots()
  → division.currentStage = 1 (淘汰赛阶段)、division.knockoutGenerated = true、
    division.status = 1 (单组别赛事镜像同步 tournament 同名列)
```

### 1.5 分组抽签（assignGroups）

```
创建分组赛 (tournamentType=1) 时执行，个人赛/羽毛球团体/排球共用:

Step 1 · 拆分名单
  - 刻意设置了种子(seedRank)的选手 → 按种子序升序
  - 未设置种子的选手 → Collections.shuffle() 随机打乱
    (禁止任何确定性兕底，如按名字排序)

Step 2 · 蛇形分发
  拼接[种子在前，随机选手在后]后按行蛇形分配:
  第 1 行: 组1→组2→…→组N (正序)
  第 2 行: 组N→…→组2→组1 (逆序)
  交替往复，groupPosition 记录组内位次

效果:
  - 全员无种子 → 整份名单绝对随机分组
  - 有 k 个种子(k≤组数) → 种子互不同组，其余选手随机
```

### 1.6 手写分组（manual-groups，V28）

```
创建分组赛时可传 drawMode="manual-groups" + groups[[名册下标...]]（仅 tournamentType=1），
线下抽好签后直接录入分组结果，跳过 Step 1/2 的蛇形+shuffle：

校验（服务端全量把守）:
  - 组数 = knockoutSlots / qualifiersPerGroup（不允许自选）
  - 每组 ≥ max(2, qualifiersPerGroup)，允许组间不均（线下常态，不用平均 group_size 硬卡）
  - 下标 ∈ [0, 名册数)、无重复、恰好全覆盖；组内顺序即 groupPosition（决定组内轮转座次）
  - seed 不参与分组，仅保留展示

重抽窗口 = 该组别任何小组赛开赛前（痕迹法：只查 stage_type=0 的记分/事件/阵容/子项痕迹），
PUT .../group-assignments 全量替换（元素=playerId）：重写 group_no/group_position 后
全删全建小组赛赛程（match id 会变，与 draw-slots 的"原地不动"刻意不同）；
内容未变时幂等返回（match id 稳定）。淘汰赛一旦生成即锁定；仅 drawMode=manual-groups 可用。
战报草稿（match_report_meta）不算开赛痕迹，但重分组时随旧赛程一并删除作废（不留孤儿行）；
淘汰赛生成后小组赛一律不可重开（重开会使 standings 与已生成签表脱钩）。
division.group_size 恒为 ceil(人数/组数) 的均值展示口径，重分组不改写（人数与组数不变，值恒定）。

多组别赛事：draw_mode 为组别级字段，创建时每个组别可独立携带 drawMode/knockoutSlotOrder/groups
（divisions[] 与顶层手写字段不可混用，其余顶层赛制字段同样禁带），组别间互不影响；
手写签表（manual）仅纯淘汰组别、手写分组（manual-groups）仅小组+淘汰组别，循环赛组别无手写形态；
网页端创建页自 2026-10-05 起按组别暴露开关（详见 [[手写签表改造方案]] §14.6）。
```

## 2. 小组赛积分与排名

### 2.1 排名模板必须按比赛类型隔离

小组赛排名不是一套规则覆盖所有比赛。当前产品必须把以下 4 类比赛视为互相独立的排名域：

1. 羽毛球个人赛：`sportType=0` + `participantType=0`
2. 羽毛球团体赛-苏杯五项与自定义多项：`sportType=0` + `participantType=1` + `teamMatchTemplate ∈ {1, 3}`（两类团体赛均按场内大分与胜负场次统计，复用 `BADMINTON_TEAM_COMMON_1` 排名域）
3. 羽毛球团体赛-接力追分：`sportType=0` + `participantType=1` + `teamMatchTemplate=2`
4. 排球比赛：`sportType=1`

任何“常用模板一/二/三”都只能属于其中一类，不能跨类型复用。尤其不能把羽毛球个人赛的“胜局/小分”直接拿去解释团体赛，因为团体赛在父比赛和子比赛之间多了一层“场内大分”。

### 2.2 核心概念

#### 2.2.1 羽毛球个人赛三层分数

个人赛只有一场比赛本身，没有父子比赛结构：

- 胜场：赢了几场小组赛。
- 胜局/净胜局：每场比赛内部赢了几局、输了几局，例如 2:0、2:1。
- 局内小分/净胜分：每一局的具体比分累计，例如 21:18、19:21、21:15。

个人赛排名模板只能使用这三层及 H2H 等兜底规则。

#### 2.2.2 羽毛球团体赛-苏杯五项四层分数

苏杯五项团体赛是一场父级团体赛包含 5 场子项比赛：男单、女单、男双、女双、混双。

- 胜场：队伍赢了几场父级团体赛。
- 场内大分：一场父级团体赛内赢了几个子项，例如 3:2、4:1、5:0。代码中父级 `match_record.left_game_wins/right_game_wins` 在这个语境下表示场内大分，不表示普通“局”。
- 场内局：5 个子项比赛内部的局数累计，例如某子项 2:1、另一子项 0:2，汇总为队伍的场内局差。
- 局内小分：所有子项每一局的具体比分累计，例如 21:18、19:21、21:15。

注意：团体赛的“场内大分”不是排球比赛积分，也不是个人赛的“局分”。它是父比赛里的子项胜负数，是团体赛比个人赛多出来的一层。

#### 2.2.3 羽毛球团体赛-接力追分

接力追分赛也是团体赛，但不是苏杯五项结构。它不包含固定 5 个独立子项，而是按接力段连续累计总分。

因此接力追分的小组排名不能直接套用苏杯五项的“场内大分/场内局/局内小分”模板。接力没有场内大分和场内局，只有团体赛胜负、各接力段汇总出的局内小分和胜负关系。

#### 2.2.4 排球比赛

排球比赛固定以队伍为参赛单位，但它不是羽毛球团体赛父子结构。排球排名可使用：

- 胜场
- 比赛积分（FIVB 口径：3-0/3-1 胜 3 分、3-2 胜 2 分、2-3 负 1 分、0-3/1-3 负 0 分）
- 胜负局比 / 净胜局
- 得失分比 / 净胜分
- H2H

排球模板不得复用羽毛球个人赛或羽毛球团体赛模板。

### 2.3 当前模板语义

#### 2.3.1 羽毛球个人赛

默认 BWF 模板：

```
胜场 → 两人同分优先 H2H → 净胜局 → 净胜分 → H2H
```

个人赛常用模板一：

本模板按“胜场数 → 净胜局 → 得失分比”排名。不要用团体赛的场内大分规则解释个人赛。

#### 2.3.2 羽毛球团体赛-苏杯五项

常用模板一：

```
胜场数 → 两队直胜；多队并列时比较场内大分、场内局、局内小分
```

数据来源：

- 胜场来自父级团体赛 `match_record.winner_id`。
- 场内大分来自父级团体赛 `left_game_wins/right_game_wins`，例如 3:2。
- 场内局和局内小分来自 `team_match_item.child_match_id` 指向的子比赛 `match_record.game_scores`。

#### 2.3.3 羽毛球团体赛-接力追分

常用模板一：

```
胜场数 → 两队直胜 → 小分得失比
```

自定义排名只允许选择团体赛胜负、局内小分、胜负关系，不显示场内大分和场内局。

#### 2.3.4 排球

排球模板独立于羽毛球：

```
常用模板一：胜场数 → 胜局数 → 得失分比
FIVB：胜场 → 比赛积分 → 胜负局比 → 得失分比 → H2H
```

### 2.4 平局检测

`markRanksAndTies()` 中，如果多名参赛方按当前模板的有效指标仍完全相同，且卡在出线边缘 → `tieUnresolved = true` → 阻止生成淘汰赛。

2 人完全相同时，仅当模板包含 H2H 类判据才会看双方直胜：有胜者则不标记未解决；模板无 H2H 判据或无直胜胜者时，仍标记为未解决。

完全并列且无法裁决时，按输入顺序（ORDER BY group_no, group_position, create_time, id，即组内座次（group_position）、报名时间（create_time）、id）稳定输出——非名字序，不保证语义公平，仅保证确定。

未决并列可经由创建者/裁判「晋级资格覆盖」人工指定出线（见 §21）。

## 3. 淘汰赛排表算法（BracketEngine）

### 3.1 算法流程

```
输入: n 个选手 (已随机 shuffle)

Step 1 · 容量对齐
  n → 向上取整到 2的幂 p (例: 6人 → p=8)

Step 2 · 递归种子排序
  构建平衡二叉树种子序列
  不变式: 每对相邻种子之和 = p + 1
  例: p=8 → [1, 8, 4, 5, 2, 7, 3, 6]

Step 3 · 安置选手
  - 有种子排名的选手 → 精确放入对应槽位
  - 无种子排名的选手 → 随机填入剩余非 bye 槽位
  - seedOrder 中值 > n 的位置 → 轮空 (bye)

Step 4 · 轮空坍缩
  bye 槽位 → 直接晋级
  propagateWinnerToParent() → 递归传播到父节点

Step 5 · 晋级链表
  每场记录 next_match_id + next_match_slot (left/right)
  决赛: next_match_id = null
```

### 3.2 小组赛出线后的蛇形排法

```
第1名: 组1-1, 组2-1, 组3-1, 组4-1 (按组号升序)
第2名: 组4-2, 组3-2, 组2-2, 组1-2 (按组号降序)
findOpponentIndex() 避免同组第1名和第2名在淘汰赛首轮相遇
```

**自动生成路径强制同组回避**：无法满足时显式报错拒绝（BracketEngine 抛 IllegalArgumentException；
唯一例外：仅一个组贡献出线者时允许同组前二内战）。出线后手排（generate-knockout 自定义签位）与
draw-slots 手动重排均**不校验**同组回避，允许同组出线者首轮相遇——有意放开，面向线下特殊安排
（临时调签、凑场、避免等待等），不做硬约束也不产生警告。

## 4. 羽毛球专项规则

### 4.1 基本计分

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `pointsToWin` | 21 | 每局目标分 |
| `bestOf` | 3 | 三局两胜 |
| `gamesToWin` | 2 | 赢2局获胜 |
| `enableDeuce` | true | 启用追分 |
| `capPoint` | 30 | 封顶分 |

### 4.2 获胜条件

```
checkWinCondition(myScore, opponentScore):
  return myScore >= pointsToWin
    AND (myScore - opponentScore) >= 2   ← 必须领先 ≥2 分
```

### 4.3 追分与封顶

- **正常追分**: 20:20 → 继续打到一方领先2分为止
- **封顶**: 29:29 → 先到30分者胜（`capPoint = 30`）

### 4.4 单打淘汰赛特点

- 选手=个人，player 表一行即一个参赛者
- 创建赛事时粘贴选手名单（空格/换行/逗号分隔）
- 记分板：横屏双栏布局，点击己方分数区 +1分，发球权跟随

### 4.5 四半区站位沙盘（2026-10，双打/单打通用）

依据 BWF《Laws of Badminton》V5.0（条款号见 docs/plans/羽毛球双打拆分与四半区沙盘-可行性报告-20261025.md §3）：

- **发球半区（Law 10.1 / 11.1）**：发球方本局得分为偶数（含 0）→ 右发球区发球，奇数 → 左发球区；接发球员站斜对角（同名半区，Law 9.1.3/11.1.4）。
- **站位转移（Law 11.1.5 / 11.3.1）**：发球方得分 → 该侧两人互换左右半区（同一发球员换区继续发）；接发方得分 → 双方不换位，只转移发球权。系统不逐球记录发球员，站位由「比分奇偶 + 每侧锚点（当前谁站右发球区）」纯函数推导（pages/scoreboard/court-position.js），Law 11.4 发球次序循环作为不变量由单测保证。
- **换边（Law 8）**：局间自动换边 / 决胜局中点换边 / 手动换边均只镜像屏幕左右，锚点随参赛方走，不互换左右半区。
- **双打开局录入**：团体赛双打子项（playerCount=2）首次进入记分牌时强制弹窗——选先发球方 + 确认各队谁站右发球区，确认后落 `lineup_snapshot(reason:court_setup)` 事件（后端白名单既有类型，零迁移）。第 2/3 局默认延续站位（Law 11.6 允许局间重排，经「交换站位」按钮操作）。个人赛双打（V31，组别 `entry_player_count=2`）同样适用：创建时每行录入一组两人，record 详情带 `playerCountPerParticipant=2` 与双方成员名单，记分牌据此进入双打沙盘模式。
- **站位纠错（Law 12）**：记分牌「交换站位」按钮可交换任一侧两人半区，比分不变；落 `lineup_snapshot(reason:court_swap)` 事件，不入撤销栈。
- **单打**：同样显示沙盘（每侧 1 人，按奇偶落半区）；第一局第一分前可点选先发球方（挑边）。
- **降级**：旧比赛（事件流无站位数据）双打只显示组合名、不高亮；不做数据迁移。
- **屏幕映射**：左队右发球区在屏幕左下、右队右发球区在屏幕右上——同名半区呈斜对角，与俯视球场物理方向一致。

## 5. 排球专项规则

### 5.1 基本计分

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `pointsToWin` | 25 (前几局), 15 (决胜局) | 每局目标分 |
| `bestOf` | 3 | 三局两胜；也可选择五局三胜 |
| `gamesToWin` | 2 | 默认赢2局获胜；五局制时为3局 |
| `enableDeuce` | true | 启用追分 |
| `capPoint` | 99 | 排球追分封顶分 |

### 5.2 决胜局判定

```js
currentTargetPoints = (currentGameNo === bestOf && decidingPointsToWin)
  ? decidingPointsToWin
  : (pointsToWin || 25)
```

决胜局目标分可按赛事配置（`decidingPointsToWin`，默认 15），非决胜局用 `pointsToWin`（默认 25）。

### 5.3 发球权与轮转

```
接发方得分 → 顺时针轮转 → 发球权切换
发球方得分 → 不轮转
```

**场上位置映射** (court 数组 -> 球衣号码位):
```js
SLOT_POSITIONS = [4, 3, 2, 5, 6, 1]  // 数组索引 → 实际号位
// 前排: slot 0-2 (4/3/2号位)
// 后排: slot 3-5 (5/6/1号位)
```

### 5.4 换边机制（三种场景）

| 场景 | 时机 | 效果 |
|------|------|------|
| **局间换边** | 每局结束 → 下一局轮次填写前 | `swapMatchStateSides()` 交换全部状态 |
| **决胜局中途换边** | 决胜局任一方达到本局目标分的一半 | 弹窗提示→确认后交换两侧显示+记录 `side_switch` 事件；默认 15 分决胜局通常在 8 分提示 |
| **手动换边** | 首局/决胜局 lineup 页 | 用户点击"换边"按钮 |

**核心数据结构**: `screenLeftParticipantSide` — 记录"当前屏幕左侧对应的是原始 left 还是 right 参赛方"。所有事件的 side 字段均使用**参与者侧**，与屏幕显示位置无关。

## 6. 自由人系统（仅排球）

### 6.1 核心概念

自由人（Libero）是专门的后排防守球员，**不能**在前排、**不能**发球、**不能**进攻。

### 6.2 数据结构

```js
// 局前配置
liberoSetup = {
  pairIndexes: [2, 3],    // 两个副攻在 court 数组中的索引（必须对角位）
  libero1Id: 'm5',        // 自由人1 memberId
  libero2Id: 'm7',        // 自由人2 memberId (可选)
}

// 运行时状态（比赛中动态追踪）
liberoRuntime = {
  role1SlotIndex: 2,      // 副攻1当前在哪个 slot
  role2SlotIndex: 3,      // 副攻2当前在哪个 slot
  role1PlayerId: 'm2',    // 当前占据 role1 的是哪个球员
  role2PlayerId: 'm3',    // 当前占据 role2 的是哪个球员
}
```

### 6.3 自动换人规则

```
自由人上场条件:
  1. 该位置在后排 (slot 0-2 = 前排，slot 3-5 = 后排)
  2. 该位置不是发球方自己的 1号位 (slot 5)
     → 只有接发方在 1号位才可用自由人

触发时机:
  - 每局开始时 → buildInitialLiberoRuntime()
  - 每次轮转后 → rotateTeamLiberoRuntime()
  - 每次手动换人后 → settleTeamLibero()

关键节点:
  - 到前排位置 → 不使用自由人，恢复对应副攻
  - 到后排位置 → 按发球方状态和位置判断是否使用自由人
  - 到 1号位(slot 5) → 发球方使用副攻本人，成为接发方后才可使用自由人
```

### 6.4 自由人设置流程（lineup 页）

```
1. 6个位置全部填满 → "开始添加自由人"
2. 点击一个副攻位置 → 自动配对对角位
3. 从下方不在场的替补队员列表选择自由人1/自由人2
4. 规则：可不绑定、只绑定一名或分别绑定两名；当前校验允许同一替补同时绑定两个副攻
```

## 7. 队长管理（仅排球）

### 7.1 原始队长 vs 场上队长

- **原始队长**: 队伍 `captain` 标记（静态，创建赛事时指定）
- **场上队长**: 比赛中当前在场上的队长（动态运行态）

```
syncCaptainState():
```

```
  4. 记录 captain_change 事件（source: "auto"）

```

## 9. 撤销机制（记分板通用）

### 9.1 快照栈

```
每次操作前: pushHistory()  →  完整状态快照压栈
点击撤销:   historyStack.pop()  →  恢复上一步
栈上限:     40 条（超出 slice(-40)）——仅排球记分板（match-state.js MAX_HISTORY_ENTRIES）；
            羽毛球记分板：本地事件缓存按 300 条上限裁剪、保留最近 250 条
            （MAX_STORED_EVENTS=300 / KEEP_EVENTS_AFTER_PRUNE=250，match-events.js），
            恢复后撤销栈深度受此约束；本地 historyStack 本身无显式上限（use-scoreboard-state.js pushHistory）
```

### 9.2 防套娃

```
pushHistory 保存的快照不包含 historyStack 自身
→ 避免 "历史里嵌历史" 导致 Storage 爆炸
```

## 11. 事件同步策略（排球 / 羽毛球 / 接力共用管道）

### 11.1 同步流程

```
appendMatchEvent():
  → matchEvents.push({ syncStatus: 'pending' })
  → scheduleEventFlush(800ms)  ← 800ms 防抖批量提交

flushPendingEvents():
  → PUT /matches/{id}/events
  → 后端按 (match_id, event_seq) 幂等：同 seq 同内容跳过；同 seq 不同内容返回 409
    并整批拒绝，由前端重排本地序号后重试
  → 成功: syncStatus → 'synced'
  → 失败: 不阻塞现场操作

finish 前强制:
  → flushPendingEvents() ← 确保所有事件落库后再结束比赛
```

羽毛球与接力复用同构管道（pages/scoreboard/match-events.js，不改动排球代码）：

- 800ms 防抖、失败 1s→×2→30s 指数退避、409 按服务端最大序号自愈重排——与排球一致；
- 事件 payload 内嵌 runtime（动作后状态）+ prevRuntime（动作前状态）双快照，撤销栈可跨设备重建（排球无此设计）；
- 终局动作（制胜分/退赛）立即冲刷、不等防抖，防「最后一分后杀进程丢事件」；
- 接力注入自定义动作映射（RELAY_ACTION_EVENT_MAP：全部 score_snapshot 类型 + 自定义 reason），
  刻意不用 side_switch 类型——后端 undo 补偿会把 seq>revertToSeq 的 side_switch 事件从 record 剔除，
  而接力换边不进撤销栈，被连带剔除会丢换边记录（team-relay.vue / relay-recovery.js）。

### 11.2 Bootstrap 事件

进入比赛时自动确保两条基础事件：
1. `roster_snapshot` — 双方完整名单快照
2. `lineup_snapshot` — 每局开局站位快照

## 12. 羽毛球团体赛（苏迪曼杯式）

### 12.1 赛制概述

> 适用于 `participantType=1` + `sportType=0` + `teamMatchTemplate=1`

双方各派一支队伍，进行 **5 个单项**（男单 MS、女单 WS、男双 MD、女双 WD、混双 XD），**先赢得 3 项者获胜**。

### 12.2 创建与阵容

```
创建赛事:
  1. 创建者指定 N 支队伍（每队含多名队员）
  2. tournament.participantType = 1
  3. tournament.teamMatchTemplate = 1 (苏迪曼杯)
  4. 生成对阵表 → 每轮一场团体赛（parent match）

阵容编排 (team-lineup.vue):
  1. 双方从各自队员列表中选择每项的出场队员
  2. 单打项目（MS/WS）：每方选 1 人
  3. 双打项目（MD/WD/XD）：每方选 2 人；同一项目内不可重复选人，**跨项目暂不设兼项限制**（与 §23.2 自定义多项一致）
  4. 保存 → 生成 5 条 team_match_item 记录
```

### 12.3 子比赛创建与记分

```
开始单项比赛:
  1. 用户点击某项（如"男单"） → PUT /matches/{id}/team-items/MS/start
  2. 后端创建 child_match（match_record, stageType=2）
  3. 返回 childMatchId → 前端导航到普通羽毛球记分板

单项结束:
  1. 记分板调用 PUT /matches/{childMatchId}/finish
  2. 后端更新 team_match_item.status=2 + winnerSide
  3. 后端检查父比赛是否满足结算条件
```

### 12.4 团体赛结算

```
自动结算（子比赛结束时）:
  1. finishParentTeamMatchIfSettled() 统计所有子项
  2. 条件仅为全部子项已完成。淘汰赛阶段一方达到 3 胜（一般化 ceil(N/2) 门槛）的
     提前结算只能由手动结算接口触发（PUT /matches/{id}/team-match/settle）；
     子场完赛不会自动提前结算
  3. 胜方 = 赢项多的一方（leftWins vs rightWins）
  4. 父比赛 status → 2, winnerId = 胜方队伍 ID
  5. 淘汰赛中胜者自动晋级

手动结算（淘汰赛提前结算）:
  1. 前端"直接结算"按钮 → PUT /matches/{id}/team-match/settle
  2. 后端校验: 淘汰赛阶段 + 一方 ≥ 3 胜
  3. 立即结算剩余未完成项目视为无效
```

### 12.5 出线规则

```
循环赛: 按胜场数排名（胜一场得 1 分）
淘汰赛: 5 项中先赢 3 项者晋级
```

## 13. 羽毛球接力追分赛

### 13.1 赛制概述

> 适用于 `teamMatchTemplate=2`（接力追分赛）

每队 **N 名队员**（默认 6 人，3 ≤ N ≤ 12），按固定顺序**接力上场**。每段由**相邻两名队员**组成：队员1+队员2、队员2+队员3、...、队员N+队员1（闭环）。

比赛只计**总分**，不分局。目标分 = `pointsPerSegment × N 段`。先达到目标分的一方获胜。

### 13.2 阵容编排

```
接力链验证 (validateRelayChain):
  1. 每段是一个 pair [firstId, secondId]
  2. 相邻段共享: 当前段的 secondId == 下一段的 firstId
  3. 末段回环: 末段的 secondId == 首段的 firstId
  4. 首成员唯一: 每段的首成员（firstId）不得重复
  5. 最少 3 段

阵容保存:
  1. 前端生成 order[] → buildRelayItemsFromOrders() 生成 items
  2. 后端保存到 team_match_item（itemCode=R1..RN）
  3. 所有段共享同一目标分
```

### 13.3 记分规则

```
计分:
  - R1 段开始，双方从 0:0 开始累计计分
  - 每达到 segmentTarget = baseScore × currentSegmentNo 时自动切换下一段
  - 到达 targetScore 方获胜

段切换:
  1. 任一方达到 segmentTarget → segmentSwitchPending = true
  2. 弹窗提示"进入下一段"
  3. 记录当前比分到 segmentScores[]
  4. 继续计分，目标更新为下一段

换边:
  - 双方可在任意时刻手动换边（sidesSwapped toggle）
  - 不影响逻辑分（始终以原始 left/right 为准）

结算:
  - 一方达到 targetScore → 比赛结束
  - 同步到后端: gameScores 存储为 relaySegmentScores
```

### 13.4 赛事创建特殊处理

```
applyRelayRule():
  - bestOf = 1, gamesToWin = 1 (无局分概念)
  - enableDeuce = false (不追分)
  - capPoint = relayMemberCount（复用字段表示接力人数）
  - 校验: 每队报名人数 ≥ relayMemberCount
```

## 15. 赛段规则

> 适用于创建赛事时启用 `roundRuleEnabled=true` 的组别（V23 后规则为组别级；赛事级字段仅作异常数据兜底）。

### 15.1 规则粒度

```
组别默认规则（tournament_division.bestOf / gamesToWin / pointsToWin / decidingPointsToWin / enableDeuce / capPoint）
  → 默认适用于该组别所有比赛

tournament_round_rule 赛段规则（按 division_id 归属组别）:
  stageType=0, roundNum=0     → 小组赛统一规则
  stageType=1, roundNum=N     → 淘汰赛第 N 轮规则
```

### 15.2 规则解析

```
TournamentRuleResolver.resolveForMatch(tournament, match):
  1. match 缺少组别（division_id 缺失，V23 后属异常数据）→ 回退赛事级字段兜底
  2. 季军赛（match_role=1，子比赛先定位父比赛再判）→ 使用组别 third_place_* 快照字段
  3. division.roundRuleEnabled != true → 使用组别默认规则
  4. 团体赛子比赛(stageType=2) → 先定位父比赛，再按父比赛赛段解析
  5. 小组赛 → 查 stageType=0 + roundNum=0；淘汰赛 → 查 stageType=1 + match.roundNum
     （均按 division_id + stageType + roundNum 查询）
  6. 未命中分轮规则 → 回退组别默认规则
```

### 15.3 创建校验

- `roundRules[].stageType` 只接受 `0` 或 `1`
- 小组赛规则使用 `roundNum=0`
- 淘汰赛规则使用实际轮次号
- `gamesToWin = floor(bestOf / 2) + 1`
- `decidingPointsToWin` 必须在 `1..pointsToWin` 范围内（仅排球；羽毛球解析时该字段恒为 null）

### 15.4 覆盖性与关闭形态（divisions[] 多组别创建，2026-10-06）

divisions[] 模式下每个组别可独立启用分段规则设计（roundRuleEnabled + roundRules），
与单组别扁平路径共用后端契约（DivisionSpec.roundRuleEnabled/roundRules，同一套校验与落库）：

- 覆盖性：roundRules 必须与该组别作用域集合一一对应、不多不少——type1=小组赛(0,0)+
  淘汰 1..log2(knockoutSlots)；type0=淘汰 1..knockoutRounds；type2 不允许启用；
  接力追分团体赛（teamMatchTemplate=2）亦不允许启用。
  缺失/多出/重复 → 创建整单拒绝（"分轮规则必须完整覆盖"）；
- 关闭形态：roundRuleEnabled=false 时 roundRules 被后端忽略，解析回退组别默认规则。
  多组别关闭形态为：type1=小组赛用组别基础规则、淘汰各轮统一用组别淘汰赛规则
  （roundRuleEnabled=true + 固定两条结构），type0=不发任何 roundRule 字段；
- 季军赛规则独立于 roundRules（tournament_division.third_place_* 列快照）：
  thirdPlaceRule 缺省回退组别基础规则；网页端在分段启用时自动取决赛段规则；
- 规则创建期写一次、不可修改，重分组/重抽签不影响；运行期解析链见 §15.2。

网页端实现：分段设计抽屉抽为共享组件 RoundRuleDrawer（单组别与组别面板复用），
作用域推导/覆盖校验/扁平化在 utils/roundRules.js。

## 17. 羽毛球三局两胜自动换边

### 17.1 局间换边确认

```
每局结束后:
  1. finishGame(winnerSide) → 检测是否最后一场
  2. 若非最后一场:
     - gameEndPromptPending = true
     - UI 阻断，弹窗显示"第 X 局结束"和本局比分
     - 用户点击"换边继续"后:
       a. currentGameNo += 1
       b. 重置分数为 0:0
       c. serveSide 设为上一局的胜方（羽毛球规则：上一局获胜方下一局先发球）
       d. 第 2 局起的每一局（三局两胜/五局三胜均适用）调用 applySideSwitch() 交换左右显示
          （2026-10-13 修复：此前仅三局两胜局间换边，五局三胜的第 2/3/4 局不换边）
       e. 保存状态，继续下一局
  3. 若最后一场 → 进入比赛结束流程
```

### 17.2 决胜局中点换边

```
触发条件:
  - 当前为最后一局（bestOf=1 时为第 1 局，bestOf=3 时为第 3 局）
  - 任一方得分达到 ceil(pointsToWin / 2)
    - 21 分制 → 11 分
    - 15 分制 → 8 分
    - 11 分制 → 6 分
  - finalGameSideSwitchHandled = false

弹窗流程:
  1. shouldPromptFinalGameSideSwitch(score) → finalGameSideSwitchPending = true
  2. UI 阻断: 所有按钮 disabled，记分暂停
  3. 弹窗提示"第 X 局达到 N 分，是否交换场地？"
  4. 用户选择:
     - 不换边继续 → finalGameSideSwitchHandled = true，继续记分
     - 换边 → applySideSwitch() + finalGameSideSwitchHandled = true，继续记分
  5. 恢复正常记分
```

### 17.3 自动结算

```
比赛结束后的自动行为:
  1. 比赛锁定（isLocked = true）
  2. scheduleAutoSettlement() → 10 秒倒计时
  3. 倒计时结束 → 自动 syncAndBack() 同步到后端
  4. 页面卸载 → clearAutoSettlementTimer() 取消计时器
  5. 用户也可手动点击"同步结算"提前触发
```

## 18. 比赛操作权限

### 18.1 权限模型

所有比赛（match）的写入操作（记分、退赛、重置、结束、保存事件、填写对阵名单等）均须经过双重守卫：

1. **视图层守卫**（bracket.vue / groups.vue）：前端根据 canOperateMatches 标志拦截无权限的比赛点击，提示用户先录入裁判身份。
2. **页面层守卫**（各记分板 / 阵容页）：进入页面的 onLoad 中调用 GET /matches/{id}/can-operate，后端校验通过后才允许渲染操作 UI。
3. **执裁独占锁守卫**（V20 新增）：进行中的比赛同一时间仅允许一个执裁会话持有写锁。写接口要求 `X-Match-Lock-Token` 头与 `match_record.lock_token`、当前用户三者一致且未过期，否则返回 `code=403`（见 §18.6）。

双级口令模型下的编排权限收窄：淘汰赛预览、生成淘汰赛（含出线后自定义签位排签）属编排决策，仅创建者或赛务管理员（ADMIN）可操作，现场执裁裁判（SCORER）被拒（TournamentServiceImpl previewKnockoutForDivision / generateKnockoutForDivision；视图层下发的 `canManageKnockout` 同口径，TournamentRefereeService.fillMatchAccess）。draw-slots 手动重排签位与 manual-groups 重分组目前仍仅创建者可操作（TournamentDrawService.requireCreator），未放开给 ADMIN。

### 18.2 can-operate 接口

```
GET /api/v1/matches/{id}/can-operate  🔒
```

后端逻辑（MatchServiceImpl.canOperateMatch()，裁判授权判定同款逻辑收敛于 TournamentRefereeService）：

1. 比赛不存在 → false
2. 赛事已归档 → false
3. 当前用户为赛事创建者 → true
4. 当前用户已被授予裁判权限（tournament_referee_grant 表中存在记录） → true
5. 以上均不满足 → false

前端的 requireMatchOperator(matchId) 封装了 ensureAuth() + 调用此接口 + 失败 toast 的统一守卫逻辑。

### 18.3 裁判验证流程（双级口令模型）

赛事详情页（detail.vue）提供「裁判验证」入口，两级口令共用同一输入框，后端智能识别命中哪级即授予哪级角色（TournamentRefereeService.resolveGrantRole：先比对赛务编排密码，未命中再比对现场执裁密码）：

1. 非创建者用户点击 → 弹出密码输入面板
2. 输入不少于 8 位数字的密码（`^\d{8,}$`）→ POST /tournaments/{id}/referee-auth
3. 命中**赛务编排密码**（`admin_password_hash`）→ 授予 ADMIN（赛务编排管理员）：含执裁能力，另可执行出线覆盖、生成淘汰赛等编排操作；命中**现场执裁密码**（`password_hash`）→ 授予 SCORER（现场执裁裁判）：可做单场记分/阵容/战报等单场操作；两级均未命中 → 按失败计数（15 分钟内 5 次锁定）
4. 后端校验通过 → 在 `tournament_referee_grant` 表写入/更新授权记录（`upsertGrantWithRole`）：SCORER 输对编排密码**原地晋升**为 ADMIN；已是 ADMIN 的用户误输执裁密码**不降级**
5. 此后该用户在 bracket / groups 视图中 canOperateMatches=true，可操作该赛事下的比赛

改密精准吊销（`PUT /tournaments/{id}/referee-password`，仅创建者）：

- 修改哪一级密码**仅吊销哪一级**已授权记录（`revokeGrantsOfRole`），另一级互不影响；吊销同时清理被撤权人在该赛事下持有的全部活跃执裁锁（`clearMatchLocksByUsers`），防僵尸会话继续写分
- 两级密码不可相同（同时改两级直接校验；仅改一级时新密码与库中另一级做跨级撞车校验）
- 首次配置裁判密码时必须提供现场执裁密码（编排密码可选）

### 18.4 登录入口

三种身份入口（小程序微信登录 / Web 注册 / Web 密码登录，接口见 [[API接口.md]]）最终都签发同一种 JWT；后续比赛操作权限统一走 `AuthInterceptor → AuthContext → AuthGuard`。

### 18.5 归档只读

赛事归档后，所有 canOperateMatches 返回 false。前端在 bracket / groups 中拦截比赛操作，提示「已归档，只读查看」；已完成的排球比赛仍可进入记录页查看详情。

### 18.6 比赛执裁独占锁（同一时间仅一台设备可执裁）

每场比赛（`match_record`）增加一个带过期时间的独占写锁，防止多台设备同时对同一场比赛记分造成状态错乱。

- **字段**（`match_record`，V20 新增）：`locked_by_user_id`（持有者）、`lock_token`（会话 token）、`lock_expire_time`（过期时间，建索引 `idx_match_lock_expire_time`）。
- **获取**：`POST /api/v1/matches/{id}/lock`，请求体 `{lockToken}`（前端进入执裁页面时生成）。成功条件（任一）：锁空闲或已过期；当前用户即锁持有者（同账号换设备重取可顶掉自己仍有效的旧锁，返回 `kicked=true` 提示，前端 toast「已在其他设备打开该比赛，本设备已接管执裁」；token+userId 双匹配为同会话重进，幂等且不算顶锁）。创建者无特殊接管权（该能力已被有意移除）；创建者在写守卫上同样无豁免，也须先持锁。
- **续期**：`POST /api/v1/matches/{id}/heartbeat`，前端每 15s 一次；仅持有者可续期，把过期时间顺延 75s（`MatchLockService.MATCH_LOCK_SECONDS`）。心跳韧性：前后台切回若心跳已停（执裁权需重新取得），页面 onShow 会静默重取锁并续传未同步事件（scoreboard/index.vue）；弱网下上一跳未返回则跳过本跳、不并发心跳（startMatchLockHeartbeat 的 inFlight 防抖，match-lock.js）。
- **释放**：`POST /api/v1/matches/{id}/release`，仅 token 匹配时清空；页面卸载时前端**先冲刷未同步事件、冲刷完成（或失败）后再释放**（2026-10 B1：事件上云要求锁仍有效，释锁先到冲刷必 403；羽毛球/接力/排球三页面 onUnload 统一收口，冲刷失败释锁照发，75s 租约兜底，数据兜底仍是「本地缓存 + 下次进入续传」）。
- **写守卫**：`finish / restart / events / lineup-config / team-lineup / team-items/{itemCode}/start / team-match/settle` 均要求请求头 `X-Match-Lock-Token`，且 `lockedByUserId==当前用户 && lockToken==header && 未过期`，否则抛 `ForbiddenException` → `code=403`（提示「执裁会话已失效，请重新进入比赛」）。**创建者在写守卫上无豁免**，也须先持锁。
- **无执裁操作权的 403**（2026-10）：lock / heartbeat / release / lock-status 四个锁接口在用户已无该赛事执裁操作权（如被移出裁判名单）时返回 403「无权执裁该比赛，请确认仍在执裁名单中」（仅锁接口，其它比赛接口的权限失败仍为 400），与写守卫 403 并存；前端据此展示「已不在执裁名单」文案并禁用遮罩上的重试按钮——重试无意义，不再无限重试。被撤权遮罩的重试禁用不自动解除：管理员恢复授权后需退出页面重新进入（forbidden 状态随页面实例销毁；有意不做成 30s 冷却式自愈，避免低频版无限重试）。
- **终态清锁**：结算（finish）、团体赛结算（settle）、重启（restart 级联重置 `resetMatchResult`）成功后会清空锁字段。
- **不受锁守卫的写接口**：`report-meta`（战报元数据）、`report-seal`（战报封存）。
- **锁遮罩（前端，取代旧「只读模式」）**：抢锁失败（首次进入）或心跳发现失锁（执裁中）时，前端弹出**全屏遮罩**，不再进入只读横幅：进入失败遮罩与「执裁权已丢失」遮罩共用同一组件，均只保留「重试获取 / 重新获取执裁权」与「返回」两个出口。重试链路为 `GET /{id}/lock-status` 探测（带请求头 `X-Match-Lock-Token`）→ 若锁由**同账号另一台设备**持有（`sameAccount=true && sameToken=false`）则先弹「顶替确认」再抢锁（`sameToken=true` 为本机转交/幂等重进，直接重取、不弹确认）→ 抢锁成功后**强制重跑完整进入仲裁**（`loadMatchState`/`decideEntrySource`：被顶替场景锁 token 已换 → `sameSession=false` 必走服务端事件重放；同设备单纯锁过期则按水位判定可否本地续裁），且**遮罩保持到恢复完成之后**——恢复期间页面不可交互，所谓「旧内存状态续写」窗口被关闭；恢复失败则遮罩保留并提示「数据恢复失败，请重试」。顶替成功由页面 `beginLockSession` 统一提示一次（guard 不重复弹）。若锁由**其他账号**持有则重试按钮置灰 30 秒冷却。遮罩期间本地缓存不清除、事件停止外发堆积在本地，不覆盖服务器（符合"权限拒绝只拦截返回"约定）。锁状态探测接口见 [API接口 6.15.4](API接口.md)。
- **锁遮罩的两个例外与返回语义（走查补丁；2026-10 B3 起「是否本机转交」由服务端 `sameToken` 权威判定）**：以下两种情况**不弹**「顶替确认」——探测 `GET /{id}/lock-status` 时带请求头 `X-Match-Lock-Token`（本次将要 acquire 的 token），`locked && sameToken=true` 即「锁由本设备当前会话持有」，适用于：① 恢复失败后再次点重试时，锁仍在本设备手上；② 排球记分页 ↔ 名单页之间是 redirect **转交锁**（`transferringMatchLock`，不释放锁），新旧页面共用同一 token。原先「redirect URL 带本设备 `lockToken` 即跳过确认」的约定（`skipReplaceConfirm`）已废除，陈旧 URL 不再被信任；旧后端无 `sameToken` 字段时降级：同账号持锁一律弹确认（安全默认）。此外遮罩「返回」若因导航节流/名单提交中**未能真正离页**，遮罩会恢复，不留「无遮罩 + 按钮全禁」的死页。
- **多场并发**：锁为每场比赛一把，同一赛事的不同场次可由不同设备同时执裁。
- **离线续传的 restart 防护（W2，前端）**：进入比赛时 `/record` 拉取失败（离线）的会话中，本地未同步事件**不会立即续传**——事件管道在冲刷前会先探测一次 `/record`：服务端可达且事件为空（已被管理端 restart 清空）→ 触发「比赛已被重开」处理（本地缓存与比分整体丢弃，toast 提示），冲刷中止；服务端可达且有事件 → 正常续传（序号撞号由 409 自愈链重排）；仍不可达 → 本次不冲刷、保持 pending，下次冲刷再探测。堵住「restart 清空 + 离线续传」把旧一局比分复活进新事件的窗口。
- **同账号顶替策略复核（B4 决策，2026-10-25）**：维持「同账号可顶替 + 顶替确认弹窗 + kicked toast + 被顶设备心跳遮罩」的折中，不改代码。否决「禁止第二台」：设备故障（断电/崩溃）不发 release，换机需干等最多 75s 租约；两本裁判操作说明书已把「同账号顶替 + 顶替确认」作为正式操作路径交付，故障排查表假设「点重试立即抢回」；`docs/plans/裁判权限模型与收窄方案探讨.md` 两次讨论均反对收紧（「手机没电赛程就卡死」）。否决「静默顶替」：去掉确认弹窗会让误开第二台变成无声互踢。「被顶替 + 被撤权」叠加场景已由无权限 403 覆盖（上文）。

### 18.7 重开（restart）权限分级与限制

权限分级（`MatchAccessGuard.requireMatchRestartOperator`）：

- 未完赛（status<2，含未开赛/进行中）：创建者 / ADMIN / SCORER 均可重开，保留现场记分员纠错能力；
- 已完赛（status=2 正常结束 / 3 判定结束）：仅创建者或 ADMIN 可重开，防止普通执裁裁判抹掉已推进晋级的完赛结果。

三条硬限制（`MatchSettlementService.restartMatchInternal`）：

1. 淘汰赛已生成后，小组赛一律不可重开（重开会使 standings 与已生成签表脱钩）；
2. 轮空场次（已完结且单侧参赛者为空）不可重开：重置后单侧永远为空，且清下游槽位会让淘汰赛树缺人卡死；
3. 下游比赛正被持锁执裁时拒绝重开（避免对方 800ms 防抖窗口内幽灵事件写回）。

restart 同时清空本场锁字段（`resetMatchResult` 将 `locked_by_user_id` / `lock_token` / `lock_expire_time` 置 NULL）。

## 19. 三四名赛（季军赛）

### 19.1 触发条件

仅在**组别** `third_place_enabled = true` 时生成三四名赛（多组别赛事各组别独立启用），且要求 `knockout_rounds >= 2`（即至少 4 个淘汰赛参赛单位，必须有半决赛）。

### 19.2 生成逻辑（`appendThirdPlaceMatch`）

在淘汰赛赛程生成后（纯淘汰赛创建或小组赛生成淘汰赛时）追加：

1. 定位 `finalRound = knockout_rounds`。
2. 取半决赛：`stage_type=淘汰赛` 且 `round_num = finalRound - 1`，按 `match_index` 升序，必须恰好 2 场。
3. 新建三四名赛 `match_record`：
   - `id` 用 `IdUtil.simpleUUID()`（与引擎生成的比赛一致，非雪花 ID）；
   - `match_role = 1`（`MATCH_ROLE_THIRD_PLACE`）；
   - `round_num = finalRound`，`match_index = 决赛最大序号 + 1`，`status = 0`。
4. 接线：半决赛两场的败者分别流向三四名赛——
   - `semifinal[0].loser_next_match_id = 三四名赛id`，`loser_next_match_slot = "left"`；
   - `semifinal[1]` → `"right"`。

### 19.3 败者晋级链路

结算某场比赛时（`propagateLoserIfNeeded`）：胜者沿 `next_match_id / next_match_slot` 前进，**败者**沿 `loser_next_match_id / loser_next_match_slot` 前进。半决赛的两个败者因此进入三四名赛。普通场次 `loser_next_match_id` 为空，败者即出局。

### 19.4 规则与结算

- 三四名赛的计分规则独立：`TournamentRuleResolver` 命中 `match_role = 1` 时返回 `MatchRuleConfig.fromThirdPlace(division)`，使用 `tournament_division.third_place_best_of / games_to_win / points_to_win / deciding_points_to_win / enable_deuce / cap_point` 列（缺省逐字段回退组别基础规则）。
- 结束判定（`finishDivisionIfReady` → 聚合）：先判组别完结——启用季军赛的组别须决赛 + 季军赛全部完赛才置 `division.status = 2`；全部组别完结后才把 `tournament.status` 置为「已结束」。

## 20. 可配置排名模板

### 20.1 数据模型

- 表 `tournament_ranking_config`：每**组别**一条（`division_id` 唯一），仅 type1（小组赛+淘汰赛）与 type2（纯循环赛）组别存在排名配置；字段 `config_version`、`config_json`、`locked_at`。
- `config_json` 由 `RankingConfig.toJson()` 序列化，承载 `template`、`priorities`、`mathType`、`twoWayTieH2HFirst`、`withdrawPolicy`、`pointsSystem`、`systemFallbackCriterion`。
- 未配置过时，读取按 `RankingConfig.legacyDefault()`（CUSTOM + `胜场 → 净胜局 → 净胜分 → H2H`）。

### 20.2 支持范围与权限

- 仅 `tournamentType ∈ {1 小组赛+淘汰赛, 2 纯循环赛}` 支持（`updateRankingConfig` 校验）。
- `GET /ranking-config` 公开可读（归档赛事对创建者仍可读）；`PUT /ranking-config` 仅创建者。
- 保存后**清空晋级资格覆盖**（`clearQualificationOverrides`），因为排名判据变化会使旧的人工出线指定失效。此外，任一排名相关比赛（`stageType` 0/2）完赛或重开时，同样按组别清空全部覆盖记录（`MatchSettlementService.clearQualificationOverridesIfRankingMatch`）。

### 20.3 解析规则（`parseRankingConfig`）

- `template` 与 `priorities` 至少提供其一；都为空报错。
- 只给 `template` → 直接采用该预设。
- 给了 `priorities` → 强制落为 `CUSTOM`；`mathType` / `twoWayTieH2HFirst` / `withdrawPolicy` / `pointsSystem` 继承自 `template` 对应预设（未给 template 则继承 `legacyDefault`）。
- 自定义模板若缺「小分」类判据，系统自动补一个兜底 `systemFallbackCriterion`（个人 `POINT_WIN_RATE`，团体 `TEAM_CHILD_POINT_WIN_RATE`），保证排名一定收敛。

### 20.4 锁定

- `locked = 已有一场排名相关比赛结束（hasFinishedRankingMatch） || locked_at 非空`。
- 锁定后前端禁止再改模板，防止赛程中途改变排名口径导致名次漂移。

### 20.5 预设模板一览（`RankingConfig.preset`）

| 模板 | 判据序列 | mathType | withdrawPolicy |
|------|---------|----------|----------------|
| `BWF_BADMINTON` | 胜场 → 净胜局 → 净胜分 → H2H | DIFFERENCE | DELETE_ALL |
| `BADMINTON_COMMON_1` | 胜场 → 净胜局 → 得失分率 | DIFFERENCE | DELETE_ALL |
| `BADMINTON_TEAM_COMMON_1` | 胜场 → H2H → 场内大分净胜 → 场内局净胜 → 局内小分净胜 | DIFFERENCE | DELETE_ALL |
| `BADMINTON_RELAY_COMMON_1` | 胜场 → 两人直胜 → 小分得失比 | RATIO | DELETE_ALL |
| `CAMPUS_VOLLEYBALL` | 胜场 → 净胜局 → 净胜分 → H2H | DIFFERENCE | FORFEIT_SINGLE |
| `VOLLEYBALL_COMMON_1` | 胜场 → 胜局数 → 得失分率 | RATIO | FORFEIT_SINGLE |
| `FIVB_VOLLEYBALL` | 胜场 → 比赛积分 → 胜负局比 → 得失分率 → H2H | RATIO | FORFEIT_SINGLE |

> 「比赛积分」为 FIVB 口径：3-0/3-1 胜 3 分、3-2 胜 2 分、2-3 负 1 分、0-3/1-3 负 0 分。
>
> 弃权局分合成（withdrawPolicy=FORFEIT_SINGLE，GroupStandingEngine.normalizeForfeitMatch）：
> 弃权场（`retiredSide` 非空且 `gameScores` 为空）进入排名引擎时按组别分制合成局分——
> 场分合成为 0:gamesToWin（缺失时兜底 3），逐局合成为 0:pointsToWin（跟随组别分制，
> 排球 25 / 羽毛球 21；null/非正数回退 25）。DELETE_ALL 模板则把含弃权方的场次整体从排名输入剔除。

### 20.6 引擎实现

`GroupStandingEngine.rank(players, matches, qualifiersPerGroup, config)` 是唯一入口：先按 `withdrawPolicy` 处理退赛，再累计各判据统计量（个人/团体分支 `usesTeamItemStats` 区分），按 `priorities` 逐层分块排序，H2H / 多人 H2H 单独递归裁决，最后标记名次、出线与未决并列。第 2 节「当前模板语义」描述的就是该引擎在各类型下的结果。

## 21. 晋级资格覆盖（人工出线指定）

### 21.1 数据模型

表 `tournament_qualification_override`：`group_no`、`rank_slot`、`player_id`、`operator_user_id`；唯一约束 `(division_id, group_no, rank_slot)` 与 `(division_id, group_no, player_id)`。

### 21.2 用途与前置条件

当小组赛全部结束，但某个出线名次因并列无法用规则自动裁决（`tieUnresolved = true` 且卡在出线边缘）时，由创建者/裁判人工指定该名次归属。前置校验：

1. `tournamentType = 1`（小组赛+淘汰赛）；淘汰赛尚未生成。
2. 全部排名相关比赛已结束（`allRankingMatchesFinished`）。
3. 仅创建者或已认证裁判可操作。

### 21.3 覆盖校验（`updateQualificationOverrides`）

- 请求必须覆盖**每个**存在未决并列的小组（`requiredCountByGroup`），且每组的覆盖数量必须与该组「未决出线槽位」数量完全一致，不能多不能少。
- 每条 `rank_slot` 必须在 `1..qualifiers_per_group`，且只能落在未决槽位；`player_id` 必须属于该组且处于未决并列。
- 同一 `(groupNo, rankSlot)`、同一 `player` 均不可重复。

### 21.4 生效方式（`applyQualificationOverrides`）

渲染积分榜时：先对仍 `tieUnresolved` 的项 `clearManualTie()`，再逐条对覆盖记录调用 `Standing.applyManualQualification(rankSlot)`（置 `qualified=true`、`rank=rankSlot`、`manualQualified=true`）。覆盖生效后这些项不再被视为未决，从而放行 `generate-knockout`。

## 22. 战报签章（封存）

### 22.1 状态模型

战报元数据存于 `match_report_meta.meta_json`，其 `reportState` 对象含 `status`（`draft` / `sealed`）、`sealedAt`、`sealedBy`。默认 `draft`。

### 22.2 封存前置（`sealMatchReport`）

1. 仅创建者或已认证裁判可操作（`requireReportOperator`）。
2. 比赛必须已结束（`status = 2` 或 `3`）。
3. 战报必须完整（`ensureReportComplete`）：`reportSignatures` 满足下列之一——
   - 双方队长签名 + 裁判签名 + 比赛日期；或
   - 双方队长签名 + 主裁签名 + 副裁签名 + 比赛日期（两种情形均须日期；回退口径：排球链路
     签名区日期恒为空——lineup 赛前填报的「比赛时间」存在 meta 根节点 matchTimeText，
     封存校验在日期缺失时回退读取根级 matchTimeText，MatchReportAssembler.ensureReportComplete，
     2026-10-13 修复）。

### 22.3 封存效果

- 幂等：已封存再调用直接返回。
- 写入 `reportState.status="sealed"` 及封存时间/人。
- 封存后不可再改战报：`ensureReportDraft` 拦截 `PUT /report-meta`（抛「战报已封存，不能修改」）。
- 封存后不可重启比赛：`ensureReportNotSealed` 拦截 `PUT /restart`。

## 23. 羽毛球自定义多项团体赛（V24 新增）

### 23.1 赛制概述

> 适用于 `participantType=1` + `sportType=0` + `teamMatchTemplate=3`

支持主办方根据赛事规模自定义 **3 项、5 项或 7 项** 子比赛项目组合，先赢得 $\lceil N/2 \rceil$ 项的一方获胜（3 项赛先赢 2 胜、5 项赛先赢 3 胜、7 项赛先赢 4 胜）。

### 23.2 子项类型与出场人数

支持 7 类子项组合：
- 单打类（出场 1 人）：通用单打 `S`、男单 `MS`、女单 `WS`
- 双打类（出场 2 人）：通用双打 `D`、男双 `MD`、女双 `WD`、混双 `XD`

> **设计说明**：
> 1. 项目类型（S/D/MS/WS/MD/WD/XD）主要作为子项标识与展示名称规范，系统不强校验队员性别（标签语义）；
> 2. 当前阶段暂不设兼项限制（同一名队员可兼任多个单双打子项）；
> 3. 同一类型在比赛中仅出现 1 次时直接展示类型名（如“男单”），出现多次时自动按序号区分（如“男单1”、“男单2”）。

### 23.3 队伍人数与创建限制

- 每队报名人数至少 **3 人**（`members.size() >= 3`），队伍人数无上限；
- 创建时通过 `customItems` 传入子项列表，项数必须严格为 3、5 或 7 项，且不得包含 null 或空类型；非模板 3 请求传入 `customItems` 将被明确拦截拒绝。

### 23.4 结算与收官规则

- **整场统一规则**：整场团体赛的所有子项目采用同一套局分规则（如 3 局 2 胜 21 分）；
- **淘汰赛提前结算**：淘汰赛阶段，任一方胜场数达到 $\lceil N/2 \rceil$ 门槛时，允许主办方/裁判执行提前结算；亦可选择不提前结算而打满全部子项；
- **小组循环赛打满**：小组循环赛阶段必须打满所有子项，未打满前调用提前结算接口将被拒绝（400）。打满后由系统依据全部子项胜负结果自动完赛。

## 24. 排球暂停与撤销补偿（记分板）

### 24.1 暂停（仅排球）

- 每队每局 2 次暂停：`leftTimeouts / rightTimeouts` 初始为 2，每局开始时重置为 2；
- 请求暂停 → 扣减对应方剩余次数并记录 `timeout` 事件（side 为参与者侧）；次数用尽不可再请求；
- 无技术暂停（technical timeout）实现。

### 24.2 撤销幽灵事件补偿

撤销不仅回滚本地状态，还会以撤销后的本地事件水位 `revertToSeq` 追加一条
`score_snapshot`（reason=undo）事件：后端据此把此前已同步进库、seq 大于该水位的
换人/暂停/队长变更/换边标记为已撤销，避免记录页/战报继续显示幽灵事件。

- 撤销有 300ms 节流（连点会退两步并各写一条幽灵快照事件，300ms 内只认一次）；
- 撤销跨越换边边界时，快照只恢复球场/比分坐标，而 leftTeam/rightTeam 花名册引用
  是换边在快照之外原地交换的，须随屏侧翻转同步换回，否则名册与球场错位
  （后续换人资格校验与自由人结算都会张冠李戴）。

## 25. 排球小组赛打满三局与单组大循环出线（V32 新增）

### 25.1 打满三局（force_full_games）

- **适用范围**：仅排球、仅三局两胜（bestOf=3）、仅小组赛轮次生效——创建端对淘汰赛各轮强制关闭（防手搓 API 透传），季军赛恒不打满；
- **终场条件**：开启后由「先到 2 胜局完赛」改为「打满 3 局按胜局定胜负」，最终局分只能是 **3:0 或 2:1**；第三局仍为 15 分制决胜局（含 8 分换边），追分规则不变（领先 2 分、不设封顶）；
- **排名积分**（打满查表，拍板规则）：**3:0 = 3 分（负方 0）**、**2:1 = 2 分（负方 1）**；3:0 负方固定 0 不走积分配置；
- **退赛/弃权**：含 `retiredSide` 的场次不走打满查表，恒按 **3:0（3 分/0 分）** 的存量合成局分口径计分；
- **存储**：权威数据在 `tournament_division.force_full_games`，轮次粒度在 `tournament_round_rule.force_full_games`；`tournament.force_full_games` 为可空镜像占位列（仅 `MatchRuleConfig.fromTournament` 在组别数据缺失的异常兜底路径读取）；
- **入口**：小程序排球建赛「小组赛规则 → 打满三局」开关，admin-web 排球创建页「赛制与规则 → 打满三局」开关（均仅三局两胜时可用，默认关闭；存量数据默认 0，行为零变化）。

### 25.2 单组大循环出线名额扩展

- 「每组出线」（`qualifiersPerGroup`）在单组（大循环，组数 = 淘汰名额 ÷ 每组出线 = 1）赛制下支持 **4**；多组时仍限 1 或 2，创建端前后端一致拦截「每组出线超过 2 名仅支持单组(大循环)赛制」。
