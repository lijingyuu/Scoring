## 一、逐项验证结论

### P0-1 弃权（Retired）结算报 400 —— ✅ 缺陷真实存在，但机理与报告完全不同

**报告声称**：`validateFinishReq` 强校验 `leftWins == gamesToWin` 漏掉弃权旁路；前端会提交 `leftGameWins=0`；
测试"人工伪造 leftGameWins=2"掩盖了 bug。

**实际验证**：

1. **"前端提交 0 局"是错的**。两端记分台的 `retire()` 都会把胜方局数强制补满：
   - 排球 `frontend/src/pages/volleyball/composables/useScoreboard.js:2464-2470`：
     `rightGameWins.value = Number(info.value.gamesToWin || 2)`
   - 羽毛球 `frontend/src/pages/scoreboard/use-scoreboard-state.js:472-477`：同款写法。
   所以 `:709/:713` 的 `leftWins != gamesToWin` 校验在真实弃权提交中**能通过**。
2. **"测试伪造入参"不成立**。三处弃权测试（`MatchFinishIntegrationTest:288-311`、
   `MatchServiceImplTest:222-238`、`TournamentControllerIntegrationTest:1380-1413`）的入参
   均为"胜方局数 == 该赛事 gamesToWin"，与前端真实行为一致，不是伪造。
3. **真正的缺陷在另一处（报告没找到）**：前端 `retire()` 补满胜局但**不清空 `gameScores`**
   （`gameScores` 只在 `finishGame` push，`useScoreboard.js:2279-2287`）。
   于是"打完 ≥1 局后弃权"的真实提交形态是：`leftGameWins=2`（满）、`gameScores` 只有 1 局 →
   `MatchSettlementService.java:727` `gameScores.size() != leftWins + rightWins` → **400**。
4. **实测复现**（H2 集成测试，三局两胜、左队 25:20 拿下第一局后右队退赛，
   按前端真实形态提交）：HTTP 400 `"gameScores size does not match game wins"`；对照场景
   （一局未打即退赛，现有测试覆盖的形态）200 通过。测试跑完已删。
5. 排名引擎侧同样约定"退赛=胜方记满胜局"（`GroupStandingEngine.java:182-193`），
   与前端契约自洽；唯一断裂点就是 `:727/:755` 的一致性校验没有 retired 旁路。

**结论**：弃权缺陷真实存在且比报告描述的更易触发（只要打过任意一局后弃权必 400），
但根因、触发条件、报告给出的修复位置都要修正。**严重度：P0（真实场景必现）成立。**

### P0-2 轮空场重开导致淘汰赛树卡死 —— ⚠️ 服务端缺陷属实，但当前无 UI 触发路径

**代码层确认**：
- `restartMatchInternal`（`MatchSettlementService.java:459-474`）对轮空场无任何拦截：
  重置后 `status=0`、`winnerId=null`，且 `clearDownstreamAfterRestart` 已把晋级者从下游槽位清空。
- 再次完赛时 `ensureMatchParticipantsReady`（`:825-829`）因单侧参赛者为空抛
  `"match participants are incomplete"`，轮空场永远无法再次完赛，下游场次永远缺人。
- 全仓无手动补参赛者的修复接口。

**触发面修正**：
- 前端"重新开始"按钮已于 **2026-09-22 被产品下线**（`ScoreboardPad.vue:202`、
  `ScoreboardPhone.vue:202` 按钮注释，admin-web 无 restart 入口），后端 API 保留作兜底。
- 因此当前只有"创建者/裁判直接调 `PUT /api/v1/matches/{id}/restart` API"或未来恢复 UI 入口才会触发。

**结论**：降级为 **P1（API 级防御缺失）**——服务端必须加拦截（成本极低），
但"真实场景必崩"的说法在 UI 现状下不成立。

### P0-3 淘汰赛引擎 N=1/P=1 数组越界 —— ⚠️ 引擎层属实，生产链路不可达

**代码层确认**：
- `BracketEngine.java:133` `rounds.get(roundCount - 1)`：`n=1` 时 `p=1`、`roundCount=0` → `get(-1)` 越界；
  `generateKnockoutBracketBySlots` 的 `linkRounds:237` 同理（`p=1` 通过 `(p & (p-1)) == 0` 断言）。

**上游校验反证**：
- 直接创建淘汰赛：`TournamentCreationFactory` 个人赛 `entries.size() < 2` 拒绝（`:912-914`）、
  团体赛 `teams.size() < 2` 拒绝（`:295/:594`）→ n≥2 恒成立。
- 小组赛出线生成淘汰赛：`TournamentServiceImpl.loadGroupedKnockoutContext` 有三重闸门——
  小组赛未完 / 有未解决并列 / `plan.slots().size() != knockoutSlots` 均拒绝；
  且创建时 `knockoutSlots` 必须是 ≥2 的 2 的幂（`TournamentCreationFactory:1190-1191`）→ p≥2 恒成立。

**结论**：降级为 **P2（深度防御缺失）**——引擎应加前置断言，防未来新调用方绕过校验时抛
语义化 400 而非 IndexOutOfBounds 500。

### P1-1 团体父子场 AB-BA 交叉死锁 —— ✅ 属实

**锁序实证**（`MatchSettlementService.java`）：
- 子场完赛：`requireMatchForUpdate(子场)`(L116) → 更新子场(L156) → 更新 `team_match_item`(L165) →
  `selectByIdForUpdate(父场)`(L360)。
- 父场重开：`requireMatchForUpdate(父场)`(L460) → `resetChildMatchForRestart` 内
  `resetMatchResult(子场)` UPDATE(L594) 加子场行锁。
- 两个方向锁序相反，并发时 InnoDB 死锁检测会回滚一方（用户看到 500，重试可恢复）。
- 另注意 `settleTeamMatch`（父→items）与子场完赛路径（子→item→父）同样交叉。

**结论**：属实。严重度 P1（偶发 500、可重试恢复，非永久锁死）。报告"MySQL 必定抛错回滚其中一方"描述准确。

### P1-2 REPEATABLE READ 快照读导致父场结算漏判 —— ✅ 属实

**实证**：
- 生产 MySQL（`application-prod.yml`），无 isolation 覆盖 → 默认 REPEATABLE READ。
- `finishMatchInternal` 事务内第一个普通 SELECT 是 `requireMatchOperator` 里的
  `tournamentMapper.selectById`（L118），快照在此建立；
  `countTeamMatchScore`（L368→L415 `teamMatchItemMapper.selectList`）用该旧快照统计子项。
- 两个裁判几乎同时完赛两个子场：T2 的快照建立于 T1 提交前 → T2 看不到 T1 的子项完赛 →
  双方都判"未全完"→ 父场永久停在 status≠2。
- 缓解：存在手动兜底接口 `settleTeamMatch`（`PUT /api/v1/matches/{id}/settle-team`），不算彻底死锁，
  但自动结算链路确实会断，需人工发现并干预。

**结论**：属实，触发概率不低（两裁判同时点完赛即可），"永久停滞"略夸大（有手动兜底）。

### P1-3 队伍编辑无视赛事生命周期 —— ⚠️ 部分属实（闸门缺失属实，影响面被夸大）

**属实部分**：
- `TournamentTeamEditService.updateTeam`（`:49-74`）仅有 `requireCreator` + `requireNotArchived`
  两个守卫，判的是 `archived` 布尔旗标而非 `status`；
- 完赛（status=2）与归档（archived=true，需手动且要求 status==2）之间存在窗口，
  此窗口内创建者可改队名、球衣号、增删成员；前端 `team-edit.vue` 也无门禁。

**夸大部分**：
- **球衣号/队员名不会追溯改写历史战报**：记分开始前前端写入 `roster_snapshot` 事件固化
  id/name/jerseyNumber（`useScoreboard.js:1882-1892`），读侧优先用快照合并
  （`MatchDetailAssembler.java:628-667` 注释明言"赛后编辑球衣号不再追溯改写历史记录"）。
- **真正会追溯变化的只有队名**（战报表头实时联查 `Player`，`MatchDetailAssembler:111-112`）；
  轮转网格标签是硬编码 "A队/B队"（`:357-358`），历史比分是数字，均不受影响。
- "已归档战报错位"自相矛盾：archived=true 时 `requireNotArchived` 直接拦截。
- 报告提到的 `deleteTeam`/`removePlayer`/`addPlayer` 后端不存在（只有 `updateTeam` 一个入口，
  内部 `applyRename/applyAddMembers/applyUpdateMembers` 共用同一对守卫）。

**结论**：闸门缺失是真实缺口（完赛未归档窗口），但数据错位影响仅限队名显示层。P1→P2。

### P2 列表无分页 + LIKE '%kw%' —— ✅ 属实（OOM 说法夸大）

- 全后端无任何分页机制（无 PageHelper/IPage/分页插件）。

### P2 执裁锁多端静默顶锁 —— ✅ 属实（细节修正）

- `MatchLockService.acquireMatchLock`（`:44-56`）：同 `userId` 加锁无条件走覆盖分支，
  新 token 直接覆写，旧 token 立即失效；旧设备下次写请求 403（`requireActiveMatchLock:94-105`）。

**结论**：属实，属产品体验缺陷而非安全缺陷。P2-P3。

### P2 战报 Base64 签名内联 —— ✅ 属实（量级修正）

- 签名未走文件上传（后端 MultipartFile 仅头像），Base64 直塞 `meta_json`
  （`MatchReportAssembler.java:101-128`）；V7 建 TEXT（64KB）→ **V19 专门扩容 MEDIUMTEXT**

  `GET /{id}/team-lineup` 更是在同一请求里对该行做两次 `selectOne` + 两次整体解析
  （`TeamMatchServiceImpl.java:462/487`），且把参与者签名重复输出两遍。
- **报告未发现的加重项**：前端每次保存把同一张图写两个字段
  （`record.vue:491-506`，`teamLeftCaptainSignature` 与 `reportLeftParticipantSignature` 同源），
  后端两处都落库 → **同一签名在 meta_json 存 2 份**，4 个签名位最多 8 份。
- 量级修正：960×320 稀疏笔迹 PNG 实际多在几 KB~几十 KB/图（`@Size(200000)` 是上界），
  "单图数百 KB"是最坏上界；整条记录数十~数百 KB 的判断成立。
- 采集端无压缩：`signature/index.vue:259-266` `fileType:'png', quality:1`（quality 对 PNG 无效）。

**结论**：属实，I/O 与网络放大真实存在。P2 合理。

## 二、修复方案（按批次）

### 批次一：真实缺陷速修（改动极小，建议随下次发版）

#### 修复 1：弃权结算校验补 retired 旁路【P0，本次最优先】

- **文件**：`backend/src/main/java/com/scoring/backend/service/match/MatchSettlementService.java` `validateFinishReq`（:694-758）
- **改法**：当 `retiredSide` 非空时——
  1. 保留 `:708-718` 胜方局数校验（前端契约"退赛=胜方记满胜局"，与排名引擎一致）；
  2. `:727` 放宽为 `gameScores.size() <= leftWins + rightWins`（弃权时已打局数必然少于满局数）；
  3. `:755` 放宽为 `countedLeftWins <= leftWins && countedRightWins <= rightWins`
     （弃权时逐局统计必然小于补满的 wins）；
  4. 单局基本校验（非负、无平局、单局 winner 与比分一致，`:733-752`）原样保留。
- **测试**：
  - 转正本次的复现用例：三局两胜、赢 1 局后退赛（断言改 200）；
  - 补 1 局/2 局、胜方落后再退赛（0:1 落后方对面退赛）、五局三胜变体；
  - 回归：正常完赛路径（retiredSide 为空）全部原有用例不受影响。
- **风险**：低。仅弃权分支行为变化，存量正常完赛校验不动。

#### 修复 2：轮空场重开拦截【P1，API 兜底防御】

- **文件**：`MatchSettlementService.restartMatchInternal`（:459-474）
- **改法**：在 `ensureReportNotSealed` 前加：
  ```java
  // 轮空自动判胜场重置后单侧参赛者为空，永远无法再次完赛，且下游槽位已被清空 → 拒绝重开
  if (Integer.valueOf(2).equals(match.getStatus()) || Integer.valueOf(3).equals(match.getStatus())) {
      if (StrUtil.isBlank(match.getLeftPlayerId()) || StrUtil.isBlank(match.getRightPlayerId())) {
          throw new IllegalArgumentException("轮空场次不支持重开");
      }
  }
  ```
- **测试**：轮空场（status=2、单侧空、winner 已晋级）restart → 400；正常已完结场 restart → 200（沿用现有 restart 测试）。
- **风险**：极低。

#### 修复 3：引擎单槽位前置断言【P2，深度防御】

- **文件**：`BracketEngine.java`
  - `generateKnockoutBracket`（:43 前）：`Assert.isTrue(players.size() >= 2, "淘汰赛至少需要2个参赛单位")`；
  - `generateKnockoutBracketBySlots`（:183 后）：`Assert.isTrue(p >= 2, "slots size must be at least 2")`。
- **测试**：n=1 / p=1 → IllegalArgumentException（而非 IndexOutOfBounds）。
- **风险**：无（当前生产链路本就到不了 p=1）。

### 批次二：并发正确性（建议独立提交 + 预发验证）

#### 修复 4：统一"父→子"锁序 + 子项当前读【P1-1 + P1-2 一起解决】

- **文件**：`MatchSettlementService.java`、`TeamMatchItemMapper.java`
- **改动 1（锁序）**：`finishMatchInternal` 开头（`:116` 锁子场**之前**）先无锁探查：

  后续逻辑不变（`:159` 的 findTeamChildItem 复用探查结果即可）。
- **改动 2（快照读）**：`TeamMatchItemMapper` 新增

  `countTeamMatchScore`（`:414-433`）改用该方法——父场锁已持有，锁定读强制看到并发事务已提交的子项状态。

- **实施注意**：

- **测试**：
  - 并发集成测试：两线程（CountDownLatch 对齐）各自完赛同一团体父场的两个子场，断言父场最终 status=2；
  - 循环 N 次并发冒烟（死锁/漏结算均断言不发生）；

- **风险**：中。锁序调整需仔细 review 事务边界；H2 与 MySQL 锁行为有差异，并发用例在 CI 只能做冒烟，

### 批次三：数据治理与性能（可与下一阶段列表改版合并）

#### 修复 5：列表分页与上限

- **文件**：`TournamentServiceImpl.java`（`:186-199` 搜索、`:243-288` 三个 mine 列表）、前端两个调用方
- **改法**：
