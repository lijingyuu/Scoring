# 手写签表改造方案（淘汰赛 · 一阶段 · 网页端）

> 状态：**已实施**（后端 P0 + admin-web 前端；测试见 `ManualDrawIntegrationTest`）｜ 范围：羽毛球/排球纯淘汰赛（`tournamentType=0`）｜ 录入端：`web/admin-web`
> 关联：[[业务规则.md]] §1/§3 · [[数据库.md]] §2.2/§2.19 · [[API接口.md]] §5 · [[组别层级改造方案.md]]

## 1. 背景

小比赛普遍线下抽签（纸条、抽扑克牌、抽对阵卡片）。系统当前创建纯淘汰赛时强制
`Collections.shuffle` 自动排签，线下抽好的对阵无法录入。本方案为淘汰赛增加
"手写签表"：组织者把线下抽签结果按签位填进系统，其余记分/晋级/排名全部复用现有机制。

## 2. 需求边界

**本期做：**

- 仅 `tournamentType=0`（纯淘汰赛）；羽毛球（个人/团体）与排球通用——参赛单位统一是
  `player` 行，机制天然同构；
- **一阶段**：创建赛事时名单与签位一次提交，直接生成完整签表、`status=1`；
- **开赛前可编辑**：首场比赛开赛前，允许网页端整体重提交签位（见 §6.2/§8）；
- **轮空 = 空槽**：框架按「≥ 人数的最小 2 的幂」生成，不填的槽位即轮空（无人）；
- 仅网页端暴露入口；小程序只读展示，不加任何录入入口。

**本期不做：**

- 小组赛手写分组、循环赛手写编号（后者现状"seed=抽签号"即免费达成）、小组出线后
  手排淘汰赛（已有 `generate-knockout` 的 `slots[]` 换位能力）；
- 小程序端录入；后端按调用端区分权限（接口不区分端，前端只放网页入口即可）；
- 双败淘汰、抢号/预选轮、OCR 手写识别、拍照存档（后者需先建文件存储基建）。

## 3. 术语与容量规则

- **签位（slot）**：首轮一场比赛的一个参赛位，编号 `1..knockoutSlots`；
- **轮空（bye）**：空槽位；生成后按既有 `propagateWinnerToParent` 坍缩，对位轮空者直接晋级；
- **框架容量规则（服务端强制）**：`knockoutSlots == 最小 2^k ≥ 名册数`。
  例：填 50 人 → 64 槽、14 个轮空。该规则保证轮空数 < 名册数，"相邻双轮空"永远可以通过
  合理摆放避免（摆放失误由 §7.5 校验拦截）；同时免去组织者自选容量的负担（64 还是 128
  由人数推导）。本期容量上限 `knockoutSlots ≤ 64`（轮数 ≤ 6）。

## 4. 流程

```
创建（一阶段）：
网页端创建赛事 → 赛制=淘汰赛 + 勾选"手写签表"
  → 录入名单（现有粘贴板/逐条）
  → 系统按人数给出 2^k 槽签位框架（50 人 → 64 槽）
  → 组织者把名单放入签位（空格 = 轮空）
  → 提交：后端校验 → 跳过 shuffle，按签位直接物化全部比赛 → status=1

编辑（开赛前）：
网页端签表页"调整签位" → 整体重提交签位数组
  → 后端校验"零开赛"（§8）→ 原地更新首轮两侧，match id 与晋级链不动
```

## 5. 数据模型（V27 迁移，已实施）

```sql
ALTER TABLE tournament_division
  ADD COLUMN draw_mode TINYINT NOT NULL DEFAULT 0 COMMENT '签表模式 0=自动 1=手写';
```

- 仅组别级，不镜像 `tournament`（非聚合状态；业务读写以组别为准，沿 V23 惯例）；
- **不加草稿表**：一阶段没有草稿态，签表就是 `match_record` 本身，无第二事实源。

## 6. API 契约

### 6.1 创建（扩展既有接口，无新路由）

`POST /api/v1/tournaments` — `DivisionSpec` 新增可选字段：

```jsonc
{
  "drawMode": "manual",             // 缺省 "auto"，缺省时行为与现状完全一致
  "knockoutSlotOrder": [0, 3, null, 2, 1, null, ...]
  // 长度 = knockoutSlots；元素 = 本组别 players[]/teams[] 的数组下标；null = 轮空
}
```

### 6.2 开赛前编辑（新路由）

```
PUT /api/v1/tournaments/{tid}/divisions/{did}/draw-slots
body: { "knockoutSlotOrder": ["<playerId>|null", ...] }   // 元素是 player.id 字符串，null=轮空（创建接口是名册下标）
```

- 权限：`TournamentAccessGuard.requireCreator` + `requireNotArchived`（裁判不可改签）；
- 语义：**全量替换**。同容量下签表结构（轮次/场次/晋级链）不变，实现为原地
  `UPDATE` 首轮各场的 `left_player_id/right_player_id`，不删行、不改 match id；
- 事务内对赛事/组别行加锁，防 TOCTOU（审查清单在册前科）；
- 幂等：相同内容重复提交无副作用。

## 7. 校验规则（后端全量把守）

1. `drawMode=manual` 仅允许 `tournamentType=0`；
2. 名册数 ≥ 2；`knockoutSlots == 最小 2^k ≥ 名册数` 且 `≤ 64`；
3. `knockoutSlotOrder.length == knockoutSlots`；
4. 非空元素恰好为名册下标全集、各出现一次（每人恰一位，无遗漏、无重复）；
5. **首轮任何一对对位不得同时为 null**（双轮空会产生空胜者并沿晋级链级联，赛事永远无法完结）；
6. `manual` 模式忽略 `seed` 字段（种子是自动抽签概念，不参与生成，仅留展示）；
7. 编辑接口附加"零开赛"守卫（§8），违例拒绝；
8. 创建与编辑全程事务 + 行锁。

## 8. "零开赛"可判定条件

该组别**同时满足**以下全部，才允许编辑：

- 不存在任何 `match_event` 行；不存在阵容/lineup 配置行；不存在 `team_match_item` 行；
- 该组别所有 `match_record` 无记分痕迹：`game_scores IS NULL`、`score_display IS NULL`、
  `left/right_game_wins IS NULL`、`retired_side IS NULL`、`locked_by_user_id IS NULL`、`lock_token IS NULL`。
  **注意 `winner_id/status` 不作为开赛信号**——手写签表创建时的轮空坍缩就会写这两个字段；
  真实完赛必然伴随 `game_scores/score_display`，退赛伴随 `retired_side`。

任一违例 → 拒绝，提示「已有比赛开始，签表不可再编辑」。

## 9. 引擎适配

- `BracketEngine.generateKnockoutBracketBySlots` 扩展：槽位列表允许 `null` = 轮空，
  坍缩复用既有 `propagateWinnerToParent`（自动路径的 bye 逻辑已在，仅放行显式空位）；
- 三四名赛 `appendThirdPlaceMatch` 照常（扫半决赛生成，与签表来源无关）；
- 记分、晋级传播、排名、执裁锁**零改动**（运行时与签表来源解耦）；
- 手写签表打完全程与自动抽签赛事行为完全一致（验收用例 5 验证）。

## 10. 前端落点

**admin-web（本期唯一录入端）**：

- `CreateTournamentView`：赛制=淘汰赛时提供「手写签表」开关；开启后名单录入完成即渲染
  2^k 槽签位框架，每格下拉选人，附「剩余随机填入」辅助按钮；
- 已建赛事详情：满足 §8 时显示「调整签位」入口。

**小程序：零改动。** `bracket.vue` 对空侧渲染「待定」，手写签表天然可渲染；
64 槽大签表依赖既有 movable-area 平移/缩放视口（验收用例 10 冒烟）。

### 13.2 六条核心设计决策（扩展时保持一致）

1. **签表 = `match_record` 读模型**：不加签表实体、不加草稿表，一阶段创建即物化，无第二事实源；
2. **容量 = 最小 2^k ≥ 名册数，自动推导**（组织者不自选），上限 64；由此保证轮空数 < 首轮场数，
   双轮空永远可通过摆放避免，坍缩（`propagateWinnerToParent`）**只发生在首轮、单层传播**；
3. **轮空 = 空槽（null）**，不引入显式轮空标记；创建时对单侧轮空直接写 `winner_id + status=2`；
4. **编辑 = 全量替换 + 原地 UPDATE**：match id 与晋级链不动，正在签表页的用户无感；
5. **契约二元**：创建传名册**下标**（下标即提交顺序），编辑传 **playerId**——文档已写死，前端勿混；
6. **零开赛判定以"痕迹"为准**：`game_scores/score_display/game_wins/retired_side/lock_*` +
   `match_event/lineup/team_match_item` 行；**`winner_id/status` 不是开赛信号**（轮空坍缩创建时就写）。

### 13.3 实施中踩过的坑

- **测试环境是 H2（READ COMMITTED），生产 MySQL 默认 RR**：RR 下事务首条普通 SELECT 建立的快照
  会让 FOR UPDATE 之后的守卫读到旧数据 → 编辑接口显式 `isolation = READ_COMMITTED`；
- **锁序**：记分/结算运行时是"先锁比赛行再锁组别行"，编辑接口必须同序，否则交叉死锁（code review 发现）；
- 测试侧：`List.of` 不接受 null（用 `Arrays.asList`）；`match_event.serve_side/payload_json` 非空；
  双轮空样例必须落在**同一场的对位**（slot i 与 i+1），断言左右侧前先核对引擎写入方向；
- 前端子代理按契约"盲写"，构建通过 ≠ 契约一致 → 上线前必须本地前后端联调；
- 编辑页从 bracket 反推签位：取 `roundNum=1 且 matchRole=0`，按 matchIndex 排序展开 `[left,right]`。

### 13.4 type1 扩展路径（手写分组 + 出线手排）

**A. 手写分组（创建时，真缺口）**
- 落点：`CreateTournamentReq.DivisionSpec` 加 `groups: [[名册下标...], ...]`；
  `TournamentCreationFactory.assignGroups` 加分支：有手写分组时跳过"种子蛇形+shuffle"直接写
  `group_no/group_position`（选手仍按提交顺序插入，顺序保证已具备）；
- 校验：组数 = `knockoutSlots / qualifiersPerGroup`；每组 ≥ max(2, qualifiers) 但**允许组间不均**
  （线下常态，不要按 group_size 硬卡）；每人恰属一组；`draw_mode` 语义需扩展（0/1 不够，
  建议升为字符串 `auto | manual-bracket | manual-groups`，或拆两列）；
- 编辑时机：type1 生成淘汰赛前小组赛就在进行，"零开赛"规则不适用——分组重抽窗口 =
  **该组别任何小组赛开赛前**（复用 `TournamentDrawService` 的守卫骨架换条件）。

**B. 出线后手排淘汰赛（基本已支持）**
- 后端 `POST .../generate-knockout` 已收 `slots[]`（语义=重排出线者，**必须与出线集合完全一致**
  ——这是正确约束，禁止放松）；`GenerateKnockoutReq.generationMode` 一直闲置可正式接线；
- 前端 `frontend groups.vue` 已有 MANUAL 换位 UI，只需把交互换成 DrawSlotEditor 同款
  （点签位激活 + 名单面板），提交时扁平化为 slots；
- 时机锁对齐 `qualification-overrides` 惯例：排名相关首场结束后锁定。

**C. 直接复用**：守卫模式（身份/归档/manual/结构不变式/幂等全量替换）、`DrawSlotEditor`
（面板改成"点组别列"即可）、双轮空→"同组对位"类的成对校验思路、全量测试 + 本地联调的验证节奏。

## 14. type1 扩展实施记录（手写分组 + 出线后签位重排，已实施）

> 范围：`tournamentType=1`（小组赛+淘汰赛）｜ 录入端：仅 admin-web ｜ 小程序零改动 ｜ 测试见 `ManualGroupsIntegrationTest`

### 14.1 已落地能力

| 能力 | 契约 | 位置 |
|---|---|---|
| 创建时手写分组 | `drawMode="manual-groups"` + `groups[[名册下标...]]`（扁平/divisions 双路径）；组数=knockoutSlots/qualifiers，每组 ≥ max(2,qualifiers)，允许组间不均；组内顺序=groupPosition | `TournamentCreationFactory.assignManualGroups` |
| 分组重抽 | `PUT .../divisions/{did}/group-assignments`，body `{groups:[[playerId...]]}`；窗口=首场小组赛开赛前（痕迹法仅查 stage_type=0）；重写 group_no/position 后**全删全建**小组赛赛程；幂等（内容未变不重建） | `TournamentDrawService.updateGroupAssignments` |
| 出线后签位重排 | 复用 `PUT .../draw-slots`（type1 分支）：淘汰赛已生成 + 零场淘汰赛开赛；禁 null 轮空、集合必须=当前首轮参赛者；原地 UPDATE，match id/晋级链不动 | `TournamentDrawService.updateGroupTournamentDrawSlots` |
| draw_mode 语义 | 0=auto，1=manual-bracket(type0)，2=manual-groups(type1)；TINYINT 扩值无需改类型（V28 仅刷注释） | V28 迁移 |

### 14.2 与 type0 的关键差异（复用时注意）

1. **开赛判定按 stage_type 分域**：type0 查整组别痕迹；type1 重分组只查 `stage_type=0`、重排签位只查
   `stage_type=1`（小组赛完赛不阻塞淘汰赛重排，反之亦然）；
2. **group-assignments 的 match id 会变**（组间人数变化必然改变赛程结构，原地更新无意义）——与
   draw-slots 的"match id 不动"刻意不同；幂等通过"内容未变直接返回"保证；
3. **type1 淘汰赛无轮空**（签位数=出线数）：draw-slots 校验禁 null，集合必须与首轮参赛者一致
   （从首轮 match 行反推，无需重算 standings）；
4. **type1 重排签位不要求 drawMode=manual-groups**（auto 生成排错同样需要补救窗口），与
   group-assignments 仅限 manual-groups 不同；
5. 前端 `DrawSlotEditor` 复用时 type1 需收窄 roster 为出线者集合（`bracket.players` 含未出线者），
   并传 `allowBye=false`；
6. **同组回避只在自动生成时 best-effort**：出线手排与 draw-slots 手动重排均不校验同组回避，
   允许同组出线者首轮相遇——有意放开（小型赛事的线下特殊安排），见 [[业务规则]] §3.2。

1. **P1 战报草稿孤儿**：`saveMatchReportMeta` 允许未开赛写草稿，而重分组痕迹守卫不查
   `match_report_meta`、全删又只删 `match_record`——草稿随重建成为永久孤儿。修复：重分组时按旧
   match id 连带删除草稿（"随旧赛程作废"而非"算开赛痕迹"，避免草稿把重分组永久卡死）；
2. **draw-slots type1 死守卫**：`assertZeroStarted` 内层已抛通用文案，下一行专属文案永不可达且
   三表 COUNT 双跑——删除重复调用；
3. **归档写操作 500→409**：`TournamentAccessGuard.requireNotArchived` 与
   `MatchAccessGuard.requireTournament` 改抛 `ConflictException`（归档是可预期业务状态，原先
   IllegalStateException 被兜底成 500 + "系统异常"文案）；
4. **淘汰赛生成后禁止重开小组赛**：`restartMatchInternal` 对 `stage_type=0` 且
   `knockoutGenerated=true` 的重开拒绝（否则 standings 与已生成签表脱钩，签位重排锚点失效）；
5. **创建侧契约硬化**：drawMode 非 manual-groups 时携带 `groups` 直接 400（原先静默忽略）；
   `divisions[]` 与顶层混用黑名单补 `drawMode/groups/knockoutSlotOrder/knockoutSlots/qualifiersPerGroup`；
6. **group_size 口径拍板：维持 ceil(人数/组数) 均值展示口径**（审查时曾改为"最大组人数"，与
   BadmintonCreationChaosTest 的 DIV_GROUP_SIZE 不变式冲突后回退）。该值在重分组时**不改写**——
   重分组不改变人数与组数，均值恒定；前端按"平均每组人数"理解，组间不均以实际分组为准；
7. **前端提前禁编辑**：组别摘要新增 `groupStageStarted`（行内痕迹列近似判定，权威判定仍在后端
   守卫），重抽页据此显示"小组赛已开赛"提示并禁用保存。

### 14.6 推广到多组别赛事（2026-10-05）

手写签表/手写分组从"仅单组别创建可用"推广到羽毛球多组别赛事的每个组别。
`draw_mode` 本就是组别级字段、后端创建/重提交链路天然按组别支持，本次**无业务代码改动**，
工作量在前端暴露与测试补齐：

**前端（admin-web）**

- 创建页多组别表单从纵向卡片堆叠改为**组别标签页**（`DivisionFormPanel` 抽为独立组件，
  行为等价重构与功能接入分两个 commit）：顶部赛事基础信息只出现一次，横排标签切换组别，
  单个组别的填法对齐单组别（羽毛球个人赛）形态；
- 每组别独立"手写签表"(type0)/"手写分组"(type1)开关与编辑器（复用 DrawSlotEditor/
  GroupAssignmentEditor），手写状态挂组别草稿（`d.manualDrawEnabled/manualSlots/manualGroups...`），
  切标签不丢失；赛制切换清掉不适用模式，轮数/名额/名单变化时组内自动对齐（轮数超 64 签位
  上限自动关闭）；
- 多组别 payload 每组别携带 `drawMode/knockoutSlotOrder/groups`（与顶层字段互斥契约不变；
  注意 type0 组别签位容量口径为 `1 << knockoutRounds`，与单组别页"人数向上取幂"不同，
  见 `utils/divisionForm.js`）；校验与提交拦截逐组别执行，弹窗可跳转定位到问题组别，
  标签页带问题圆点；
- 排名配置从全赛事共享（`divisionRankingTemplate`）改为**每组别独立选择**（后端
  `DivisionSpec.rankingTemplate` 本就按组别收取）；
- 大厅"调整签位/调整分组"入口对多组别赛事（`divisionCount>1`）全放开：下沉
  `tournamentType` 只是首组别占位值，逐组别精确过滤由 DrawSlots/GroupAssignments 页内兜底。

**测试**

- `ManualDrawIntegrationTest`/`ManualGroupsIntegrationTest` 各补 2 例：多组别混合模式
  创建（各组别 draw_mode 落库、签位摆放/轮空坍缩/分组座次逐组正确）与重提交隔离
  （manual 组别重排后其他组别逐场不变）；
- `BadmintonCreationChaosTest` 新增多组别混沌入口 `runBadmintonMultiDivisionCreationChaos`
  （随机 2~4 组别 × 匹配 drawMode 物化不变式 + 8 类逐组别恶意探针，journal 独立落盘，
  固定种子可复现）；`mvn test -Dchaos.seed=20261005` → 14+22+2 全部通过。

**边界（不变）**：多组别本身仍仅支持羽毛球个人赛；manual 仅 type0、manual-groups 仅 type1、
循环赛无手写形态；小程序端保持零改动只读。
