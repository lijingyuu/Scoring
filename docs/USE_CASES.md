# USE_CASES.md — 核心业务用例

> 用途：把“用户实际要完成的事”写清楚，作为业务需求、页面流程、接口和后端实现之间的共同语言。  
> 关联：[[ARCHITECTURE.md]] · [[BUSINESS_RULES.md]] · [[DATABASE.md]] · [[API.md]] · [[CLASS_DIAGRAMS.md]]

## 1. 用例边界

本文只记录当前系统的核心用例，不覆盖所有按钮和展示细节。挑选原则：

- 能改变核心业务状态：创建赛事、生成赛程、结束比赛、晋级、归档。
- 涉及复杂规则：小组出线、淘汰晋级、团体赛、接力追分、排球轮转和自由人。
- 涉及权限共识：创建者、裁判授权、归档只读。
- 能帮助检查“代码实现是否符合业务预期”。

通用参与者：

| 参与者 | 说明 |
|------|------|
| 游客 | 未登录用户，可查看公开赛事列表、详情、签表、部分记录，不可写入 |
| 普通用户 | 已登录并完善资料的用户，可创建赛事、收藏赛事 |
| 赛事创建者 | 创建赛事的用户，拥有赛事配置、记分、裁判管理、归档权限 |
| 授权裁判 | 通过赛事裁判密码验证的用户，可操作该赛事下的比赛 |
| 系统 | 前端页面、后端服务、赛程引擎、数据库共同完成的自动行为 |

通用状态：

| 对象 | 状态 |
|------|------|
| 赛事 `tournament.status` | `0` 未开始，`1` 进行中，`2` 已结束 |
| 比赛 `match_record.status` | `0` 未开始，`1` 进行中，`2` 已结束 |
| 赛事 `archived` | `false` 正常显示，`true` 已归档且只读 |

## UC-01 登录并获得系统身份

### 目标

用户获得一个可被后端识别的身份，用于创建赛事、收藏赛事、裁判授权和比赛操作。

### 参与者

普通用户、系统。

### 前置条件

- 小程序端用户可调用微信 `wx.login()`。
- H5/Web 用户可使用账号密码注册或登录。

### 主流程

1. 用户进入需要身份的功能，例如创建赛事、收藏赛事或进入记分页。
2. 前端检查本地是否已有 `scoring_token`。
3. 如果没有 Token：
   - 小程序端调用 `POST /api/v1/auth/wechat-login`，用微信临时 `code` 换取 JWT。
   - H5/Web 端调用 `POST /api/v1/auth/register` 或 `POST /api/v1/auth/password-login`。
4. 后端校验登录来源，找到或创建 `app_user`。
5. 后端签发 30 天有效 JWT。
6. 前端把 Token 写入本地存储，后续请求通过 `Authorization: Bearer <token>` 传给后端。
7. 如果用户资料未完善，前端弹出资料补全流程，调用 `POST /api/v1/auth/profile`。

### 分支与限制

- 游客可以查看赛事大厅、赛事详情、签表、小组赛和比赛记录，但不能执行写操作。
- 后端开发环境可通过 `DevMockAuthFilter` 注入模拟 Token，生产环境不能依赖该行为。
- 需要“创建赛事”的用例必须要求用户已登录且资料已完善。

### 验收核对点

- 所有写接口最终都应能从 `AuthContext` 取到用户 ID。
- 前端请求封装应统一注入 Token，并统一处理 `code !== 0` 的错误提示。
- 登录方式不同不应影响后续权限模型；后续权限只看用户 ID、创建者身份和裁判授权记录。

## UC-02 查看赛事大厅并进入赛事

### 目标

用户在首页发现赛事，进入详情，再选择查看队伍、签表、小组赛或比赛记录。

### 参与者

游客、普通用户、赛事创建者、授权裁判、系统。

### 前置条件

- 系统中已经存在至少一个赛事。
- 未归档赛事可出现在赛事大厅。

### 主流程

1. 用户打开赛事大厅。
2. 前端调用 `GET /api/v1/tournaments` 获取赛事列表。
3. 用户可以按关键字搜索赛事名称或地点。
4. 列表卡片展示赛事名称、地点、状态、运动类型、赛制、收藏数等摘要。
5. 用户点击赛事进入详情页，前端调用 `GET /api/v1/tournaments/{id}`。
6. 详情页根据赛事类型提供入口：
   - 淘汰赛进入对阵图。
   - 小组赛或循环赛进入小组赛页面。
   - 团体赛事可查看队伍和队员。
   - 已结束排球比赛可进入比赛记录页。

### 分支与限制

- 游客看到的 `favorite`、`creator` 等当前用户标识应为 `false`。
- 已归档赛事不应出现在普通赛事大厅。
- 已归档赛事只有创建者能在“我的归档”中继续查看。

### 验收核对点

- 赛事列表和详情中的 `sportType`、`tournamentType`、`participantType`、`teamMatchTemplate` 足以决定页面入口。
- 归档赛事要从大厅和“我的创建”中隐藏，避免普通用户继续进入操作路径。
- 列表展示只负责导航和轻量操作，不应承担复杂业务判断。

## UC-03 收藏、取消收藏和查看我的赛事

### 目标

用户管理自己关注的赛事，并区分“我收藏的”和“我创建的”。

### 参与者

普通用户、赛事创建者、系统。

### 前置条件

- 用户已登录并完善资料。
- 被收藏的赛事未归档。

### 主流程

1. 用户在赛事大厅、详情页或我的列表中点击收藏。
2. 前端调用 `POST /api/v1/tournaments/{id}/favorite`。
3. 后端检查赛事存在且未归档。
4. 后端写入 `tournament_favorite`，并增加赛事 `favorite_count`。
5. 用户再次点击取消收藏。
6. 前端调用 `DELETE /api/v1/tournaments/{id}/favorite`。
7. 后端删除收藏记录，并减少 `favorite_count`。
8. 用户进入“我的收藏”，前端调用 `GET /api/v1/tournaments/mine/favorites`。
9. 用户进入“我的创建”，前端调用 `GET /api/v1/tournaments/mine/created`。

### 分支与限制

- 重复收藏应保持幂等，不应重复增加收藏数。
- 取消不存在的收藏不应导致业务失败。
- 已归档赛事不可新增收藏。

### 验收核对点

- 收藏数和收藏关系要同时维护，不能只改前端状态。
- 我的列表不应混入已归档赛事；归档赛事由专门页面承接。

## UC-04 创建羽毛球个人赛

### 目标

创建一个以个人选手为参赛单位的羽毛球赛事，并生成对应赛程。

### 参与者

赛事创建者、系统。

### 前置条件

- 用户已登录并完善资料。
- 至少录入 2 名选手。

### 主流程

1. 创建者进入创建羽毛球页面。
2. 选择“个人赛”。
3. 填写赛事名称、地点。
4. 选择赛制：
   - `tournamentType=0`：纯淘汰赛。
   - `tournamentType=1`：小组赛 + 淘汰赛。
   - `tournamentType=2`：纯循环赛。
5. 填写选手名单，可带种子序号。
6. 配置基础规则：几局几胜、目标分、是否追分、封顶分。
7. 可选配置裁判密码。
8. 前端调用 `POST /api/v1/tournaments`，提交 `sportType=0`、`participantType=0`。
9. 后端创建 `tournament`、`player`，并根据赛制生成 `match_record`。
10. 创建成功后，前端跳转赛事详情。

### 分支与限制

- 个人赛不接受 `teams` 队伍列表。
- 淘汰名额应为 2 的幂，例如 4、8、16。
- 小组赛每组出线人数只能是 1 或 2，且每组人数必须大于出线人数。
- 循环赛用 `roundRobinRounds` 区分单循环和双循环。

### 验收核对点

- 个人赛的参赛单位是 `player` 表的一行，不应创建队员表记录。
- 创建后应立即拥有可查看的签表或小组赛赛程。
- 规则字段要能被后续 `finish` 和 `TournamentRuleResolver` 读取。

## UC-05 创建羽毛球团体赛（苏迪曼杯五项）

### 目标

创建以队伍为参赛单位的羽毛球团体赛，每场团体对抗包含男单、女单、男双、女双、混双五个单项。

### 参与者

赛事创建者、系统。

### 前置条件

- 用户已登录并完善资料。
- 至少录入 2 支队伍。
- 每支队伍有足够队员支撑五项阵容编排。

### 主流程

1. 创建者进入创建羽毛球页面。
2. 选择“团体赛”。
3. 选择“苏迪曼杯五项”模板。
4. 填写赛事名称、地点、赛制和计分规则。
5. 录入队伍，队伍成员可包含队长标记。
6. 可选配置裁判密码和赛段规则。
7. 前端调用 `POST /api/v1/tournaments`，提交 `sportType=0`、`participantType=1`、`teamMatchTemplate=1`。
8. 后端创建 `tournament`、队伍型 `player`、`tournament_team_member`。
9. 后端按队伍生成团体赛父比赛 `match_record`。
10. 创建成功后进入详情页，再进入对阵图或小组赛。

### 分支与限制

- 团体赛不接受个人赛 `players` 列表。
- 五个单项不会在创建赛事时全部生成子比赛；只有进入某场团体赛并开始单项时才生成子比赛。
- 团体赛父比赛的胜负由五个单项结果汇总决定。

### 验收核对点

- 队伍本身是参赛者，队员是队伍明细，不应把每个队员当成独立赛事参赛者。
- `teamMatchTemplate=1` 应让后续团体赛页面显示 MS、WS、MD、WD、XD。
- 创建后产生的是父比赛赛程，不是五倍数量的普通比赛赛程。

## UC-06 创建羽毛球接力追分赛

### 目标

创建一种特殊团体赛：双方按固定队员顺序组成连续双打段落，整场只累计总分。

### 参与者

赛事创建者、系统。

### 前置条件

- 用户已登录并完善资料。
- 至少录入 2 支队伍。
- 每队报名人数不少于接力人数。

### 主流程

1. 创建者选择羽毛球团体赛。
2. 选择“人员流转追分赛”模板。
3. 设置轮转人数，默认 6 人。
4. 设置每段基础目标分。
5. 前端提交 `sportType=0`、`participantType=1`、`teamMatchTemplate=2`。
6. 后端调用接力规则转换：
   - `bestOf=1`
   - `gamesToWin=1`
   - `enableDeuce=false`
   - `capPoint` 复用为接力人数
7. 后端校验每队人数容量并生成团体赛父比赛。
8. 创建成功后，后续由接力阵容和接力记分页面完成实际比赛。

### 分支与限制

- 接力赛不使用苏杯五个单项。
- 接力赛不创建普通羽毛球子比赛。
- 每段必须首尾衔接，最后一段回到第一名队员，形成闭环。

### 验收核对点

- 接力人数的存储复用 `capPoint`，阅读代码和文档时不能误解为封顶分。
- 接力赛最终比分是总分，不是局分。
- 创建页展示的“目标分”应和后续接力段目标一致。

## UC-07 创建排球赛事并录入队伍

### 目标

创建排球赛事，录入队伍、球衣号、队长和自由人标记，并生成赛程。

### 参与者

赛事创建者、系统。

### 前置条件

- 用户已登录并完善资料。
- 至少 2 支队伍。
- 每支队伍 6 到 12 名队员。
- 每队恰好 1 名队长。

### 主流程

1. 创建者从运动选择页进入排球创建页。
2. 填写赛事名称、地点。
3. 选择赛制：淘汰赛、小组赛 + 淘汰赛或循环赛。
4. 配置排球规则：
   - `bestOf` 通常为 3 或 5。
   - `gamesToWin = floor(bestOf / 2) + 1`。
   - 常规局 `pointsToWin` 默认 25。
   - 决胜局 `decidingPointsToWin` 默认 15。
5. 录入每支队伍的队员、球衣号、队长、自由人标记。
6. 前端调用 `POST /api/v1/tournaments`，提交 `sportType=1`。
7. 后端固定排球为团体赛，创建队伍、队员、赛程。
8. 创建成功后进入赛事详情。

### 分支与限制

- 排球赛事固定 `participantType=1`。
- 球衣号需要在队内唯一且有效。
- 每队必须恰好一名队长。
- 排球使用队员和轮次配置，不使用羽毛球团体赛五项模板。

### 验收核对点

- 排球赛事的 `player` 表表示队伍，不表示单个球员。
- `tournament_team_member` 必须包含队员、球衣号、队长、自由人等信息。
- 排球记分前必须先完成阵容/轮次填写。

## UC-08 配置赛段规则

### 目标

同一赛事内，不同阶段或不同轮次可以使用不同计分规则。

### 参与者

赛事创建者、系统。

### 前置条件

- 创建赛事时启用 `roundRuleEnabled=true`。
- 创建请求包含 `roundRules`。

### 主流程

1. 创建者在创建赛事时打开赛段规则配置。
2. 为小组赛配置统一规则：
   - `stageType=0`
   - `roundNum=0`
3. 为淘汰赛某一轮配置规则：
   - `stageType=1`
   - `roundNum=实际轮次`
4. 前端随创建请求提交 `roundRules`。
5. 后端校验规则合法性并写入 `tournament_round_rule`。
6. 当进入比赛或创建团体赛子比赛时，后端通过 `TournamentRuleResolver.resolveForMatch()` 解析当前比赛应使用的规则。

### 分支与限制

- `roundRuleEnabled=false` 时，所有比赛使用赛事级规则。
- 团体赛子比赛 `stageType=2` 时，需要先定位父比赛，再按父比赛阶段解析规则。
- 找不到匹配的赛段规则时，回退到赛事级规则。

### 验收核对点

- 小组赛规则不能用具体小组号表达，只能用 `stageType=0, roundNum=0` 表达。
- 淘汰赛规则应按轮次匹配，不应按页面显示名称匹配。
- `gamesToWin` 必须和 `bestOf` 一致，避免出现“三局三胜”等无效规则。

## UC-09 裁判授权与比赛操作权限校验

### 目标

保证只有赛事创建者或授权裁判能操作比赛，普通观看者只能查看。

### 参与者

赛事创建者、授权裁判、普通用户、系统。

### 前置条件

- 赛事存在。
- 创建者可设置 8 位数字裁判密码。
- 普通用户已登录。

### 主流程

1. 创建者在创建赛事时设置裁判密码，或后续调用 `POST /api/v1/tournaments/{id}/referee-password` 设置/更新。
2. 非创建者进入赛事详情，点击裁判验证入口。
3. 用户输入 8 位数字密码。
4. 前端调用 `POST /api/v1/tournaments/{id}/referee-auth`。
5. 后端校验密码，成功后写入 `tournament_referee_grant`。
6. 用户进入对阵图、小组赛或记分页。
7. 前端在列表/签表视图根据 `canOperateMatches` 控制比赛入口。
8. 进入记分、阵容、团体赛控制台等写页面时，前端调用 `GET /api/v1/matches/{id}/can-operate`。
9. 后端确认当前用户是创建者或已授权裁判，且赛事未归档，返回 `true`。

### 分支与限制

- 游客不能获得操作权限。
- 已归档赛事即使是创建者或裁判，`can-operate` 也应返回不可操作。
- 创建者可以查看裁判列表并移除授权。
- 裁判授权作用于整个赛事，不是单场比赛。

### 验收核对点

- 写页面不能只依赖前端按钮隐藏，必须调用后端 `can-operate` 或写接口内部鉴权。
- 所有比赛写操作都应复用同一套“创建者或裁判”权限模型。
- 归档只读要压过创建者/裁判权限。

## UC-10 完成普通羽毛球单场记分并推动淘汰晋级

### 目标

裁判完成一场羽毛球普通比赛记分，系统保存比分，并在淘汰赛中自动把胜者推进下一轮。

### 参与者

赛事创建者、授权裁判、系统。

### 前置条件

- 比赛已存在。
- 当前用户有该比赛操作权限。
- 淘汰赛中当前比赛的双方已就位。

### 主流程

1. 用户从对阵图或小组赛点击一场可操作比赛。
2. 前端调用 `GET /api/v1/matches/{id}/can-operate`。
3. 校验通过后进入羽毛球记分板。
4. 记分板根据赛事规则显示目标分、几局几胜、追分和封顶。
5. 裁判逐分操作，前端维护当前局分和局胜负。
6. 一方达到胜利条件后，记分板锁定比赛，提示结算。
7. 前端调用 `PUT /api/v1/matches/{id}/finish`，提交：
   - `winnerSide`
   - 双方赢局数
   - `gameScores`
   - 可选 `retiredSide`
8. 后端更新当前 `match_record`：状态、胜者、比分展示、局分明细。
9. 如果当前比赛有 `next_match_id`，后端把胜者写入下一场的 left/right 槽位。
10. 如果下一场双方都已就位，后端把下一场状态置为进行中。
11. 如果当前比赛是决赛，后端把赛事状态置为已结束。

### 分支与限制

- 退赛时，非退赛方直接成为胜者。
- 比赛结束后再次操作应受到 UI 锁定和后端状态约束。
- 小组赛结束不推动淘汰晋级，只影响积分榜。

### 验收核对点

- 淘汰晋级必须由后端依据 `next_match_id` 和 `next_match_slot` 推动，不能只靠前端改页面状态。
- 决赛结束后赛事应进入 `status=2`。
- `scoreDisplay` 和 `gameScores` 要能支撑积分榜、签表显示和赛后记录。

## UC-11 小组赛结束后生成淘汰赛

### 目标

小组赛全部完成后，系统按积分榜选出晋级者并生成淘汰赛对阵。

### 参与者

赛事创建者、授权裁判、系统。

### 前置条件

- 赛事类型为小组赛 + 淘汰赛。
- 所有小组赛比赛已结束。
- 积分榜没有未解决的出线边界平局。
- 当前用户有赛事比赛操作权限。

### 主流程

1. 用户进入小组赛页面。
2. 前端调用：
   - `GET /api/v1/tournaments/{id}/groups`
   - `GET /api/v1/tournaments/{id}/group-standings`
3. 页面展示每组比赛和积分榜。
4. 系统根据胜场、净胜局、净胜分、H2H、名字序等规则计算排名。
5. 当所有小组赛完成且无未解决平局时，页面显示生成淘汰赛入口。
6. 用户点击生成淘汰赛。
7. 前端调用 `POST /api/v1/tournaments/{id}/generate-knockout`。
8. 后端收集每组晋级者。
9. 后端采用蛇形交叉方式排列晋级者，避免同组第一和第二在淘汰首轮相遇。
10. 后端生成淘汰赛 `match_record`，设置 `currentStage=1`、`knockoutGenerated=true`。
11. 用户进入对阵图查看淘汰赛。

### 分支与限制

- 小组赛未全部结束时不能生成淘汰赛。
- 出线边界存在无法判定的平局时不能生成淘汰赛。
- 已生成淘汰赛后不应重复生成。
- 纯循环赛没有生成淘汰赛流程。

### 验收核对点

- 排名计算必须从 `match_record.game_scores` 聚合，不能只看 `scoreDisplay` 文本。
- 平局阻断逻辑必须覆盖“卡在出线边界”的情况。
- 生成淘汰赛后页面状态应能从小组赛阶段切换到淘汰赛阶段。

## UC-12 排球轮次填写、自由人配置和比赛信息保存

### 目标

排球比赛开始前，裁判完成首发阵容、发球方、自由人和比赛报告元数据配置。

### 参与者

赛事创建者、授权裁判、系统。

### 前置条件

- 排球赛事和比赛已存在。
- 当前用户有比赛操作权限。
- 双方队伍和队员已录入。

### 主流程

1. 用户从对阵图或小组赛点击排球比赛。
2. 前端先进入 `pages/volleyball/lineup`。
3. 页面调用 `GET /api/v1/matches/{id}/can-operate` 校验权限。
4. 页面读取比赛和双方队员信息。
5. 用户填写第 1 局双方 6 个场上位置。
6. 用户选择发球方。
7. 用户可配置自由人：
   - 先选择一对对角副攻位置。
   - 再选择自由人 1、自由人 2，可单绑、双绑或不绑定。
8. 用户填写比赛时间、主裁、副裁等报告元数据。
9. 前端调用 `PUT /api/v1/matches/{id}/report-meta` 保存报告信息。
10. 前端调用 `PUT /api/v1/matches/{id}/lineup-config` 保存阵容配置。
11. 保存成功后进入排球记分板。

### 分支与限制

- 如果查询某一局阵容不存在，`GET lineup-config` 可回退到最近一局配置。
- 自由人只能在后排相关规则下自动替换，不能成为前排进攻角色。
- 发球方和位置配置会影响后续轮转逻辑。

### 验收核对点

- 排球比赛不能绕过 lineup 直接进入记分板。
- `match_lineup_config` 要按 `matchId + gameNo` 保存。
- 比赛报告元数据和阵容配置是两类数据，不能混存。

## UC-13 排球实时记分、轮转、事件同步和结算

### 目标

裁判在排球记分板完成实时记分，系统处理发球权、轮转、自由人、换边、事件记录和最终结算。

### 参与者

赛事创建者、授权裁判、系统。

### 前置条件

- 当前用户有比赛操作权限。
- 第 1 局阵容和发球方已保存。
- 双方队员数据完整。

### 主流程

1. 用户进入 `pages/volleyball/scoreboard`。
2. 前端加载后端签表、阵容配置和本地缓存状态。
3. 裁判给某一方加分。
4. 系统根据得分方和当前发球方判断：
   - 发球方得分：继续发球，不轮转。
   - 接发方得分：发球权切换，接发方顺时针轮转。
5. 系统根据自由人规则自动换人或恢复副攻。
6. 裁判可记录换人、暂停、队长变更、换边等事件。
7. 前端把事件写入本地队列，800ms 防抖后调用 `PUT /api/v1/matches/{id}/events` 批量同步。
8. 决胜局达到换边分时，系统提示是否换边，并记录 `side_switch` 事件。
9. 一局结束后，系统提示局间换边并进入下一局阵容确认。
10. 一方达到整场胜利条件后，记分板锁定。
11. 结束前前端强制同步未提交事件。
12. 前端调用 `PUT /api/v1/matches/{id}/finish` 保存整场结果。
13. 后端更新比赛状态，并在淘汰赛中推动胜者晋级。

### 分支与限制

- 事件同步失败不应阻塞现场继续记分，但结算前必须尽量 flush。
- 决胜局目标分使用 `decidingPointsToWin`，非决胜局使用 `pointsToWin`。
- 换边改变屏幕显示侧，不改变原始 left/right 参与者身份。
- 记分页仅在结算成功、重新开始、用户明确放弃当前记分时清理本地缓存；权限拒绝或资料未完善时只拦截返回，不清缓存。

### 验收核对点

- 排球核心状态应集中在 `useScoreboard.js`，Phone/Pad 组件只做 UI 差异。
- `match_event` 的 `side` 应表示参与者侧，而不是屏幕左/右。
- 比赛记录页应能通过事件、阵容快照和比分重建关键过程。

## UC-14 团体赛阵容编排、单项开始和父比赛结算

### 目标

在苏迪曼杯式团体赛中，裁判为某场团体对抗编排五项阵容，逐项开始子比赛，并由系统结算父比赛。

### 参与者

赛事创建者、授权裁判、系统。

### 前置条件

- 羽毛球团体赛已创建，且 `teamMatchTemplate=1`。
- 当前用户有该父比赛操作权限。
- 父比赛双方队伍已确定。

### 主流程

1. 用户从对阵图或小组赛点击某场团体赛父比赛。
2. 前端进入 `pages/tournament/team-match`，调用 `GET /api/v1/matches/{id}/team-lineup`。
3. 若阵容未完成，用户进入 `team-lineup` 页面。
4. 用户为 MS、WS、MD、WD、XD 分别选择双方出场队员：
   - 单打项目每方 1 人。
   - 双打项目每方 2 人。
5. 前端调用 `PUT /api/v1/matches/{id}/team-lineup` 保存阵容。
6. 用户回到团体赛主页，点击某一单项开始比赛。
7. 前端调用 `PUT /api/v1/matches/{id}/team-items/{itemCode}/start`。
8. 后端检查该单项阵容完整。
9. 如果还没有子比赛，后端创建 `stageType=2` 的 child match，并绑定到 `team_match_item.child_match_id`。
10. 前端进入普通羽毛球记分板完成该子比赛。
11. 子比赛调用 `PUT /api/v1/matches/{childMatchId}/finish` 结束后，后端更新对应 `team_match_item`。
12. 后端统计五项比分。
13. 如果五项全部完成，或淘汰阶段一方已达到 3 胜，后端结算父比赛。
14. 父比赛结束后，如果处于淘汰赛，胜方队伍自动晋级。

### 分支与限制

- 接力追分赛不使用子比赛开始接口。
- 单项阵容未完成时不能开始子比赛。
- 手动结算只适用于淘汰阶段一方已达到 3 胜的场景。
- 父比赛结算后不应继续开始新的单项。

### 验收核对点

- 子比赛胜负必须回写 `team_match_item`，再由父比赛汇总。
- 父比赛的胜者 ID 应是队伍 `player.id`，不是某个队员 ID。
- 团体赛提前结算应只在满足 3 胜条件时允许。

## UC-15 接力追分赛阵容编排、分段切换和结算

### 目标

在接力追分赛中，裁判编排双方接力队员顺序，按段进行总分追分，并在达到目标分后结算父比赛。

### 参与者

赛事创建者、授权裁判、系统。

### 前置条件

- 羽毛球团体赛已创建，且 `teamMatchTemplate=2`。
- 当前用户有该比赛操作权限。
- 每队队员人数不少于接力人数。

### 主流程

1. 用户进入接力赛阵容页面。
2. 前端调用 `GET /api/v1/matches/{id}/team-lineup` 获取双方队伍和已有接力段。
3. 用户为双方分别选择接力顺序。
4. 前端根据顺序生成段落：
   - 第 1 段：队员 1 + 队员 2。
   - 第 2 段：队员 2 + 队员 3。
   - ...
   - 最后一段：队员 N + 队员 1。
5. 前端调用 `PUT /api/v1/matches/{id}/team-lineup` 保存 R1..RN。
6. 用户进入 `pages/tournament/team-relay`。
7. 记分从 0:0 开始，只累计总分。
8. 当任一方达到当前段目标分，页面提示进入下一段。
9. 系统记录当前段比分，切换到下一段参赛组合。
10. 一方达到最终目标分，比赛结束。
11. 前端调用 `PUT /api/v1/matches/{id}/finish`，把接力段比分作为 `gameScores` 变体同步。
12. 后端按普通比赛完成逻辑更新父比赛状态，并推动淘汰晋级。

### 分支与限制

- 接力链必须满足相邻段共享队员、首尾闭环、首成员不重复。
- 接力赛不追分、不分局。
- 换边只影响显示，不影响 left/right 总分归属。

### 验收核对点

- 接力阵容保存在 `team_match_item`，而不是排球阵容表。
- 接力记分页不应调用苏杯子比赛接口。
- 最终比分应能反推出每段切换点，便于赛后核查。

## UC-16 重开比赛、退赛和撤销类异常处理

### 目标

处理现场误操作、弃赛和需要重赛的情况，并保证赛程链路能回到一致状态。

### 参与者

赛事创建者、授权裁判、系统。

### 前置条件

- 当前用户有比赛操作权限。
- 赛事未归档。

### 主流程：重开比赛

1. 用户在比赛页面触发重新开始。
2. 前端调用 `PUT /api/v1/matches/{id}/restart`。
3. 后端校验操作权限。
4. 后端清除当前比赛结果：
   - `scoreDisplay`
   - `winnerId`
   - 双方赢局数
   - `gameScores`
   - `retiredSide`
   - 比赛状态
5. 后端删除当前比赛相关产物：
   - 排球事件
   - 排球阵容配置
   - 比赛报告元数据
6. 如果当前比赛胜者已晋级到下游比赛，后端递归清理下游槽位和结果。
7. 后端把赛事状态恢复为进行中。

### 主流程：退赛

1. 裁判在记分板选择某方退赛。
2. 前端锁定比赛，非退赛方成为胜者。
3. 前端调用 `PUT /api/v1/matches/{id}/finish`，提交 `retiredSide`。
4. 后端按正常结束比赛流程保存结果并推动后续赛程。

### 分支与限制

- 重开会清理下游晋级链路，避免下一轮保留错误胜者。
- 排球重开会清理事件、阵容和报告元数据，需要重新填写。
- 已归档赛事不能重开。
- 普通撤销是前端记分板本地历史栈行为，尚未同步到后端前不会改变数据库。

### 验收核对点

- 重开不是简单把当前比分清空，还必须清理下游晋级影响。
- 退赛仍要形成完整比赛结果，不能只在 UI 上标记。
- 排球缓存清理仅覆盖结算成功、重新开始、用户明确放弃等路径；权限拒绝或资料未完善时只拦截返回，不清缓存。

## UC-17 结束赛事后归档和取消归档

### 目标

赛事结束后，创建者可以把赛事从主列表隐藏，保留只读查看和恢复能力。

### 参与者

赛事创建者、系统。

### 前置条件

- 当前用户是赛事创建者。
- 赛事 `status=2`。

### 主流程：归档

1. 创建者进入已结束赛事详情。
2. 页面显示归档入口。
3. 创建者点击归档。
4. 前端调用 `PUT /api/v1/tournaments/{id}/archive`。
5. 后端校验赛事存在、当前用户是创建者、赛事已结束。
6. 后端设置 `archived=true`。
7. 赛事从赛事大厅和“我的创建”隐藏。
8. 赛事出现在“我的归档”。

### 主流程：取消归档

1. 创建者进入“我的归档”。
2. 前端调用 `GET /api/v1/tournaments/mine/archived`。
3. 创建者点击取消归档。
4. 前端调用 `PUT /api/v1/tournaments/{id}/unarchive`。
5. 后端设置 `archived=false`。
6. 赛事恢复到正常列表。

### 分支与限制

- 未结束赛事不能归档。
- 非创建者不能归档或取消归档。
- 已归档赛事只读，比赛写操作权限应全部失效。
- 已归档赛事只有创建者能从归档列表访问。

### 验收核对点

- `archived=true` 是强约束，不只是前端隐藏。
- `can-operate` 对已归档赛事必须返回不可操作。
- 归档不能删除赛事、选手、队伍、比赛记录和事件。

## UC-18 配置小组排名模板

### 目标

创建者按赛事类型选择或自定义小组排名判据，并使其在赛程推进后自动锁定。

### 参与者

赛事创建者、系统。

### 前置条件

- 赛事类型为「小组赛+淘汰赛」或「纯循环赛」。
- 当前用户为创建者。

### 主流程

1. 创建者进入小组赛/排名配置页（`pages/ranking/custom`）。
2. 前端调用 `GET /api/v1/tournaments/{id}/ranking-config` 读取当前模板。
3. 创建者选择一个预设模板，或自定义判据序列。
4. 前端调用 `PUT /api/v1/tournaments/{id}/ranking-config` 保存。
5. 后端校验赛事类型与权限，序列化为 `config_json` 落库，并清空该赛事已有的晋级资格覆盖。
6. 保存后返回最新 `TournamentRankingConfigVO`；若已有一场排名比赛结束，`locked=true` 且禁止再改。

### 分支与限制

- 非「小组赛+淘汰赛」或「纯循环赛」的赛事不支持排名配置。
- 已有排名比赛结束后配置锁定，避免中途改变排名口径。
- 自定义模板缺「小分」类判据时，系统自动补 `systemFallbackCriterion` 保证排名收敛。

### 验收核对点

- 配置按赛事隔离，不能跨类型复用模板（见 BUSINESS_RULES §2.1）。
- 锁定标志 `locked` 与 `hasFinishedRankingMatch` 一致。
- 保存会清空晋级资格覆盖。

## UC-19 人工指定出线（晋级资格覆盖）

### 目标

小组赛结束时若出线名次存在无法自动裁决的并列，由创建者/裁判人工指定该名次归属。

### 参与者

赛事创建者、授权裁判、系统。

### 前置条件

- 赛事类型为「小组赛+淘汰赛」，淘汰赛尚未生成。
- 全部排名相关比赛已结束。
- 积分榜存在 `tieUnresolved=true` 的未决出线并列。

### 主流程

1. 用户进入小组赛积分榜，看到标记为「未决」的出线名次。
2. 用户为每个未决名次选择一个该组内处于并列的选手。
3. 前端调用 `PUT /api/v1/tournaments/{id}/qualification-overrides`，提交 `overrides[]`。
4. 后端校验覆盖必须恰好覆盖每个未决小组的全部未决名次，且无重复。
5. 落库 `tournament_qualification_override`；此后积分榜按人工名次展示，未决并列消除。
6. 用户再走 UC-11 生成淘汰赛。

### 分支与限制

- 覆盖数量不匹配、名次槽位非法、选手不在该组或不在并列中，均被拒绝。
- 淘汰赛已生成后不可再改覆盖。
- 修改排名模板会清空覆盖。

### 验收核对点

- 覆盖生效后 `tieUnresolved` 消失，`generate-knockout` 被放行。
- 唯一约束防止同一名次/选手被重复指定。

## UC-20 生成淘汰赛预览

赛事创建者、授权裁判、系统。

## UC-21 填写并封存战报

### 目标

比赛结束后，操作者填写裁判/挑边/签名等战报信息，并封存防止后续篡改。

### 参与者

赛事创建者、授权裁判、系统。

### 前置条件

- 比赛已结束（`status=2/3`）。
- 当前用户为创建者或已认证裁判。

### 主流程

1. 用户进入战报页（个人赛 `individual-record` / 团体赛 `team-record` / 接力 `relay-record`）。
2. 用户填写裁判姓名、挑边结果、队长与裁判签名、比赛日期等。
3. 前端调用 `PUT /api/v1/matches/{id}/report-meta` 保存草稿。
4. 用户点击「封存战报」。
5. 前端调用 `PUT /api/v1/matches/{id}/report-seal`。
6. 后端校验战报签名与日期完整，写入 `reportState.status="sealed"` 及封存时间/人。
7. 封存后战报只读，不可再改、不可重启比赛。

### 分支与限制

- 签名区须满足「双方队长 + 裁判 + 日期」或「双方队长 + 主裁 + 副裁」之一。
- 封存幂等，重复调用直接成功。
- 封存后 `report-meta` 与 `restart` 均被拦截。

### 验收核对点

- 未填写完整时封存失败，并提示缺哪一项。
- 封存状态持久化在 `meta_json.reportState`，刷新后仍为 sealed。

## UC-22 季军赛生成与结算

### 目标

启用季军赛的赛事，在生成淘汰赛时自动追加三四名决赛，半决赛败者进入该场。

### 参与者

系统、赛事创建者、授权裁判。

### 前置条件

- `third_place_enabled=true`，`knockout_rounds>=2`。

### 主流程

1. 生成淘汰赛（UC-11 或创建赛事）时，系统追加一场 `match_role=1` 的三四名赛。
2. 两场半决赛的 `loser_next_match_id/slot` 指向三四名赛。
3. 半决赛结算时，胜者前进，败者自动流入三四名赛。
4. 三四名赛使用独立规则参数（`third_place_*`）记分。
5. 决赛与三四名赛都结束后，赛事才标记为「已结束」。

### 分支与限制

- `knockout_rounds<2`（无半决赛）时启用季军赛会报错。
- 三四名赛不进入 `next_match` 晋级链，属于终局场次。

### 验收核对点

- 半决赛败者正确进入三四名赛左右槽位。
- 赛事结束判定在三四名赛完成前保持进行中。

## 3. 当前最值得人工检查的需求点

这些点不是代码错误结论，而是用例层面最容易产生“实现符合代码但不符合你预期”的地方：

1. 接力追分赛把 `capPoint` 复用为接力人数。这个实现节省字段，但产品说明中必须讲清楚，否则会和羽毛球封顶分混淆。
2. 排球重开会清除阵容配置、事件和报告元数据。若现场只想撤销比分而保留阵容，当前用例不是这个语义。
3. 归档后创建者也不能继续操作比赛，只能查看和取消归档。这是“只读归档”模型。
4. 团体赛苏杯五项的子比赛是按需创建，不是创建赛事时一次性创建。
5. 小组赛生成淘汰赛会被未解决平局阻断；现已提供「晋级资格覆盖」（UC-19）作为手动指定出线的入口，创建者/裁判可指定未决名次后再生成。
6. 裁判授权作用于整个赛事，不是某一场比赛。如果你希望按场授权，当前权限模型需要调整。
