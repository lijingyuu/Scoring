### 1.3 恶化趋势（这是本维度最关键的量化事实）

archive §4.2 backlog 中巨类当时记录为 1323/1239/1055/882 行，现已涨至 **1583/1385/1229/959**——**欠账在变大而非收敛**（月增幅约 +15%~+20%）。这直接决定了策略选型必须包含「棘轮式守门」，否则任何一次性重构成果都会被新需求重新淹没。

### 1.4 问题模式归纳（软件工程理论视角）

1. **「失败不发声」反模式（Silent Failure）**：YAML 解析无人验证、异常吞 500、JSON 降级无日志、Flyway validate 关闭——共同特征是失败路径不产生任何可观测信号。修这类问题收益/成本比最高。
2. **DRY 三层违规**：常量层（6+ 类复制）、方法层（4 类复制助手）、类层（巨类内部多个本应独立的职责挤在一起，SRP 违规）。
3. **「记录 ≠ 收敛」**：backlog 与实际发现重合度高说明自查有效，但缺少制度性约束（CI 守门），导致技术债利息持续累积（技术债量化理论：debt grows compound interest）。
4. **验证面 ≠ 运行面**：CI 不激活 prod profile 是 YAML 地雷的直接成因（结构性根因在维度6 解决，本维度负责其中的「守门测试」环节）。

## 3. 候选策略（3 个主策略 + 1 个辅助策略）

### 策略 A：止血 + 守门（最小主义）

**思路**：只修两个 P1（YAML 缩进、异常分支）并补齐日志，然后立即建立守门体系（YAML 解析测试、ArchUnit 依赖规则、行数棘轮），**巨类冻结不拆**——棘轮锁死当前行数，新代码只能往新模块加。

**理论依据**：技术债管理「先止息、再还本」；破窗理论（Broken Windows，Wilson & Kelling：可见失序会加速恶化——本仓 1323→1583 的恶化曲线正是实证）；「制度优于意志力」（process over willpower，靠 CI 而非自觉）。

**优点**：1~2 天完成、约 10 工时；零回归风险；立刻消除发布事故地雷；棘轮从制度上终结恶化趋势。

**缺点**：1583 行与 14 参构造器带来的**可用性问题原样保留**（改一个赛制要在巨型工厂类里翻找）；只冻结不偿还，维护成本峰值不变；面试叙事单薄——「我加了个测试防恶化」远不如「我在不停机前提下把 1583 行类拆到 800 并零回归」。

**成本评估**：⭐（~10h）｜投产价值：中｜面试价值：低｜风险：极低

### 策略 B：渐进式重构（特征测试保护 + 小步 Extract Class + 棘轮守门）★ **推荐**

**思路**：Phase 0 先执行策略 A 的全部内容（止血与守门是渐进重构的前置安全网），随后按「复杂度 × 变更频率 × 面试价值」排序，**每周末拆一个巨类**：先补特征测试钉住当前行为 → IDE 自动化重构（Extract Class / Introduce Parameter Object）→ 跑 498 用例 + 千场混沌仿真 → 独立 commit（可单独 revert）→ 下调棘轮基线。常量与方法层复制在守门建立后集中收敛。

**理论依据**：
- Fowler《重构（第2版）》：行为不变的代码移动 + 小步 + 测试安全网；「重构与新增功能分开提交」
- Feathers《修改代码的艺术》：遗留代码 = 无测试代码；特征测试（characterization test）先钉行为再动刀
- Kent Beck：「For each desired change, make the change easy, then make the easy change」——棘轮与单源化就是 make the change easy
- SRP（单一职责原则）：巨类拆分的切分依据
- Strangler Fig（Fowler）：CreationFactory 按「运动项目」分形时新旧并存的过渡模式

**优点**：
- 三层安全网摊薄风险：498 既有用例 + 新补特征测试 + 每类独立可 revert 的 commit；
- 投产价值即时兑现（每个 Phase 都独立可发布，不存在长期分支与线上修复的合并地狱——单人 shared-trunk 开发的关键约束）；
- 面试叙事完整闭环：量化技术债（1323→1583）→ 决策矩阵选型 → 特征测试 → 小步重构 → 制度守门，每一步都有真实数据与产物可展示；
- 与项目现有混沌仿真资产天然协同（重构后跑千场仿真比对，这是同龄人项目里罕见的验证手段）。

**缺点**：周期 6~8 周；要求持续纪律（每周固定投入半天到一天）；中间状态下新旧结构并存需要克制（不追求一步到位）。

**成本评估**：⭐⭐⭐（总计 40~60h，摊到 6~8 个周末，每周末 5~8h 符合课余节奏）｜投产价值：高｜面试价值：高｜风险：中低（有安全网）

### 策略 C：领域模块化重写（Modular Monolith + DDD 战术建模）

**思路**：按限界上下文（赛制创建 / 比赛执行 / 晋级结算 / 读模型渲染 / 鉴权）重组整个 service 包为 feature 模块（package-by-feature），引入聚合根、领域服务、仓储接口分离，可选用 Spring Modulith 做模块边界验证，读模型侧显式 CQRS 化。

**理论依据**：DDD 战术设计（Evans）；模块化单体（相对微服务的低风险演进路径）；CQRS 读写分离。

**优点**：终态架构最清晰、模块边界强制隔离；理论上「架构」面试话题最深。

**缺点**：
- 单人 6~8 周内完成风险极高：498 个用例断言对象大量改名/搬包，等于把测试资产重写一遍；
- 项目**正在投产**，大范围重组意味着长周期内每个线上修复都要在两套结构间移植；
- 诊断确认分层纪律已达标（薄 Controller、事务规范、Guard 收口）——大重写解决的不是当前最痛的问题（最痛的是 P1 地雷与巨类可用性），收益/成本比最差；
- 面试风险：讲不出生产验证细节的「大架构」容易被追问穿（「模块间事件如何保证一致性？」「为什么需要 CQRS？」），反而不如渐进重构的每一步都有实证。

**成本评估**：⭐⭐⭐⭐⭐（100h+）｜投产价值：中（结构收益大但过程风险大）｜面试价值：中高但易翻车｜风险：高

### 策略 D（辅助）：纯工具化卫生

Unicode 转义还原（48 处/2 文件）、`log.warn` 补齐、命名清理。不解决任何结构问题，**不作为独立策略**，并入策略 B 的 Phase 1。列出仅为说明「为什么把它从候选里降级」：它修的是症状舒适度，不动病因。

### Phase 3：巨类拆分 Top3（第 3~8 周，每周末一个类，~30h）

**拆分顺序依据**（复杂度 × 变更频率 × 面试价值综合排序）：

**3a. TournamentCreationFactory（1583 行，14 参构造器）→ 目标 ≤800 行**

- 切分维度：**按运动项目**拆 `BadmintonCreationStrategy` / `VolleyballCreationStrategy`（Strangler Fig：新类逐步接管分支逻辑，工厂保留为组合根/入口 Facade，公共 API 不变）；
- **Introduce Parameter Object**：14 参构造器 → `CreationContext` 参数对象（一次独立小提交，先行做）；
- 特征测试先行：现有 controller/engine 测试覆盖创建链路，先 grep 用例覆盖缺口（羽毛球/排球 × 各赛制矩阵），补齐后再动刀。

**3b. MatchDetailAssembler（1229 行）→ 目标 ≤700 行**

- 切分维度：**按渲染块**拆 4 个子装配器（基本信息 / 局分与比分 / 事件流 / 成员与展示），原类保留为 Facade 组合四者，输出 VO 结构不变（读模型，天然无状态，最适合练手且风险最低）。

**3c. TournamentServiceImpl（1385 行）→ 目标 ≤750 行**

- 切分维度：**按用例簇**拆（查询类 / 赛制配置类 / 状态流转类），Controller 委托目标类名不变或仅内部路由调整；
- 放在 3a/3b 之后：此类的特征测试成本最高（跨 63 端点中的大多数），用 3a/3b 练出的流程降低执行风险。

**每类统一执行流程（模板化 7 步，钉死纪律）**：

1. `git branch refactor/split-<ClassName>`（与线上修复隔离，周期 ≤1 周内合回，避免长期分叉）；
2. 补特征测试至核心分支覆盖（用覆盖率报告找缺口，只补「行为钉子」，不追百分比）；
3. IDE 自动化重构（Extract Class / Move Method），**禁止手工剪切粘贴**；
4. 本地全量 `mvn test`（498 用例）全绿；
5. 跑一轮千场混沌仿真，产物与重构前比对（积分/晋级/排序结果零差异）；
6. 合并，commit message 按仓库规范（`refactor(backend): TournamentCreationFactory 按运动拆分为 Strategy，行为零变化`）；单个 commit 可独立 revert；
7. 下调 `ratchet-baseline.txt` 中该类上限（如 1583→800），棘轮锁定成果。

- **风险登记册**：

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| 特征测试覆盖不足导致行为漂移 | 中 | 高 | 步骤 5 混沌仿真是第二道网；任何一步红立即停手上一个绿点 |
| 拆出的类之间出现循环依赖 | 中 | 中 | ArchUnit 已有包依赖规则；拆分时单向依赖（Strategy→Context） |
| 重构期间线上出紧急修复 | 高（单人） | 中 | 每周末一个类、周内不合主线不长期分叉；紧急修复优先，重构分支 rebase |
| 时间被考试周打断 | 中 | 低 | 每 3a/3b/3c 独立，可整体顺延不影响已交付 Phase |

- **工时**：3a≈12h、3b≈8h、3c≈10h，共 ~30h。

## 7. 面试叙述要点（STAR 法）

- **S（情境）**：单人开发的羽毛球/排球赛事记分系统（Spring Boot + uni-app 小程序）真实投产使用；对全仓做代码级审计，发现 9 个 500+ 行巨类，且一个月内最大类从 1323 行涨到 1583 行——技术债不但存在还在**加速恶化**；同时发现 CI 验证面与生产运行面不重合导致的 prod 配置解析地雷。
- **T（任务）**：在系统不停机、单人维护、每周末时间片的三重约束下，还清结构性技术债并建立防复发机制。
- **A（行动）**：
  1. **量化优先**：用审计数据（file:line 级问题清单、行数恶化曲线）而非感觉驱动决策；
  2. **加权决策矩阵选型**：止血+守门 / 渐进重构 / 模块化重写三方案按「投产价值×面试价值×成本×风险×可维护性」评分，选渐进重构，并显式论证为什么不选「看起来更酷」的 DDD 重写；
  3. **安全网先行**：特征测试 + 既有 498 用例 + 千场混沌仿真三层保护，IDE 自动化重构小步移动；
  4. **制度防复发**：ArchUnit 依赖规则 + 行数棘轮基线进 CI，「只许降不许升」，把纪律固化为流水线；
  5. **顺手拆雷**：修复 YAML 地雷并补「全 profile 解析测试」，把一次事故预案变成一类问题的终结。
- **R（结果）**：Top3 巨类行数减半（1583→800 / 1385→750 / 1229→700），全程 498 用例 + 混沌仿真零回归；CI 守门上线后技术债从「恶化中」转为「棘轮收敛中」；异常语义修正让线上告警不再被 500 噪声污染。
- **可被追问的深度点**：特征测试如何设计（钉行为不钉实现）；为什么 Extract Class 优先于重写；棘轮基线如何避免误伤（基线=当前值起步）；混沌仿真在重构验证中的角色（等价类比对）；Strangler Fig 与一次性替换的取舍。
