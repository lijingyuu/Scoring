### 1.3 问题模式归纳（软件工程视角）

1. **假安全感（false sense of security）比缺失更危险**：P2-② 的 `@Valid` 空挂让人以为「校验已做」，实际 0 字节超长字符串可直穿到 service 层。修复必须两层同时做（注解 + 端点挂载）+ 守门测试防复发。
2. **风险定价决定顺序**：P2-① 是唯一不可逆放大的项（泄露窗口 30 天且无任何补救手段），必须最先处理；P2-③ 反而是**健康的工程权衡**（注释自认约束），需要的是把约束升级为「扩容前置检查清单」这种制度产物。
3. **纵深防御缺口在校验层而非鉴权层**：鉴权（Guard）、传输（HTTPS）、存储（BCrypt 类）均已达标；唯独输入校验层形同虚设——修复后即形成完整分层。

## 3. 候选策略（3 个）

### 策略 A：最小加固（只修最痛）

**思路**：只做 G1 的前半（给 12 个 DTO 补注解）+ G2 的前半（JWT 默认改 7 天），不建守门、不做吊销、不动 P3。

**理论依据**：帕累托改进（20% 工作覆盖 80% 风险）；「先修最高风险敞口」。

**优点**：~4h 完成；token 泄露窗口立即从 30 天缩到 7 天。

**缺点**：**吊销仍然缺位**——7 天窗口内泄露依旧无补救（踢人、改密都不失效）；校验修复无守门，新 DTO 还会裸奔（本仓 12 个裸奔 DTO 正是「无守门累积」的实证）；P3 信息泄露项遗留。

**成本**：⭐（4h）｜投产价值：中高｜面试价值：低（无体系叙事）｜风险：极低

### 策略 B：分层加固 + 制度守门 ★ **推荐**

**思路**：按纵深防御分层补齐，每层配一个「制度产物」固化：校验层（12 DTO 全量修复 + 守门测试）、会话层（7 天 + tokenVersion 吊销 + 兼容灰度设计）、传输契约层（pc/status 改 POST）、运维层（凭据治理 + 单机约束 ADR 化）、信息层（P3 三项）。全程不新增中间件。

**理论依据**：
- 纵深防御（Defense in Depth）：校验/鉴权/会话/运维四层各自设防，单层失效不致全线失守
- OWASP API Security Top 10（2023）：API4 资源消耗无限（限流已有）之外的 **API8「缺乏自动化校验」** 正对应 P2-②；API1 BOLA 已由 Guard 体系覆盖——用业界框架定位问题，面试可对标讲述
- NIST SP 800-63B 会话管理思想：会话凭据寿命应与风险匹配且可撤销
- 「使制度而非使自觉」：守门测试把安全约束编译进 CI，杜绝人的遗忘
- ADR（Architecture Decision Record）：把「单实例内存态限流」从注释升级为可检索的决策记录，附带失效条件（何时必须重估）

**优点**：
- 唯一同时关闭「泄露窗口」与「补救手段」两个子问题的方案；
- 守门测试一次建成，永久拦截「新端点忘挂 @Valid / 新 DTO 忘加注解」这类回归；
- 每层工作量小而独立（4~6h 级），适配课余时间片；
- 面试叙事完整：纵深防御 × OWASP 对标 × 无状态吊销设计 × 克制的非目标论证（不引 Redis）——安全工程的「判断力」比「堆技术」更稀缺。

**缺点**：总周期 3~4 周；tokenVersion 涉及用户表加列（与维度3 迁移编号协调）与一次存量 token 兼容设计（有解，见 Phase 1）。

**成本**：⭐⭐（~17h/4 周）｜投产价值：高｜面试价值：高｜风险：中低

### 策略 C：企业级安全体系

**思路**：Redis 集中限流与锁定、JWT jti 黑名单白名单双向、refresh token 轮换（含盗用检测）、全量审计日志管道、CI 挂 SAST（SpotBugs+OWASP dependency-check）与定期 DAST。

**理论依据**：零信任架构思想；大厂安全合规基线。

**优点**：终态完备；「高并发/多实例」面试话题。

**缺点**：
- **与部署现实错配**：单实例 systemd 部署引入 Redis = 多一个需要运维、监控、备份的组件，故障面扩大，与「大三学生单人维护」矛盾；
- jti 黑名单需要存储+过期清理+每请求查询；tokenVersion 一列即等效覆盖全部吊销场景（改密/踢人/全部登出），无状态更优；
- refresh token 轮换对 code2session 模式无收益（微信侧就是轮换器）；
- SAST/DAST 的正确子集（gitleaks 已有 + 依赖漏洞扫描）在维度6 CI 方案中以合适成本纳入。
- 面试风险：堆了 Redis/黑名单这些词却答不好「为什么需要」，比「论证了为什么不需要」更减分。

**成本**：⭐⭐⭐⭐（40h+ 且引入运维债）｜投产价值：不升反降｜面试价值：表面高实际易翻车｜风险：高

## 4. 加权决策矩阵与选型结论

权重论证与维度1 一致（投产 0.30 / 面试 0.25 / 成本 0.25 / 风险 0.10 / 可维护 0.10），安全维度另注：**风险项按「加固后残余风险敞口」计分**。

| 评分维度（权重） | 策略 A 最小加固 | 策略 B 分层加固+守门 | 策略 C 企业级体系 |
|---|---|---|---|
| 投产价值（0.30） | 3.5 | **4.5** | 2.5（引入新故障面） |
| 面试展示价值（0.25） | 2.0 | **4.5** | 3.0（易被追问穿） |
| 实现成本可行性（0.25） | **5.0** | 4.0 | 1.5 |
| 残余风险安全度（0.10） | 2.5 | **4.5** | 4.5 |
| 长期可维护性（0.10） | 2.5 | **4.5** | 2.0（Redis 运维债） |
| **加权总分** | 3.30 | **4.40** | 2.80 |

**选型结论：策略 B。** 关键增量论证：A 与 B 的成本差仅 ~13h，但 A 遗留「7 天不可吊销窗口 + 校验裸奔复发」两个已知问题；B 用守门测试和 ADR 把修复成果制度化的边际成本极低。C 的全部「看起来更安全」的组件在单实例场景下均为负收益，其有价值的子集（依赖扫描、gitleaks 钉版）已由维度6 方案承接——**克制的非目标本身是安全工程判断力的展示**。

## 7. 面试叙述要点（STAR 法）

- **S（情境）**：真实投产的赛事记分小程序后端（Spring Boot）；全仓安全审计发现：JWT 30 天不可吊销（payload 仅 userId+exp）、12 个写 DTO 校验「形式在场实质缺位」（Controller 挂了 @Valid 但 DTO 零注解，等于没挂）。
- **T（任务）**：在不引入任何新中间件、不强制全员重新登录的前提下，把 token 泄露的影响窗口从「30 天且无补救」压缩为「7 天且可即时吊销」，并让校验缺失这类问题**无法再被无声地新增**。
- **A（行动）**：
  1. 用「概率×影响」给风险定价，锁死 JWT 为第一优先（唯一不可逆放大的项）；
  2. 选 tokenVersion 而非 jti 黑名单：一列数据库字段无状态地覆盖改密/踢人/全体登出全部吊销场景，黑名单方案要存储、清理和每请求查询——用更少的状态解决同样的问题；
  3. 设计存量兼容灰度：无 claim 视为 version 0 + DB 默认 0，上线零强制登出；
  4. 写守门测试（反射扫描所有 @RequestBody 端点必须 @Valid 且 DTO 必须有注解），把安全约束从「人记得」变成「CI 拦截」；
  5. 克制的非目标：论证为什么单实例场景不引入 Redis 集中限流（FailureLockTracker 注释自认约束 → 我把它升级为 ADR + 扩容前置清单）。
- **R（结果）**：泄露窗口 30 天→7 天且应急可全体吊销（一条 SQL）；12 个 DTO + 全部写端点校验闭环且 CI 守门；带副作用的 GET 消除；凭据离开明文脚本。
- **可被追问的深度点**：tokenVersion 校验放 AuthGuard 而非 Interceptor 的原因（保持 Interceptor 只解析的架构契约）；为什么 7 天不是 2 小时（PC 扫码会话真实成本 vs 风险）；OWASP API Top 10 中本项目各层的对应覆盖；守门测试为什么用反射而不用 ArchUnit（ArchUnit 管类型依赖关系，参数级元数据用反射更直接）。
