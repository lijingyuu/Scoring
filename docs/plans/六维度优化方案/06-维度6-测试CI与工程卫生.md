### 1.3 问题模式归纳（软件工程视角）——本维度承载诊断报告的核心结构性判断

1. **CI 验证面 ≠ 生产运行面（诊断 §4.2 全仓结构性问题的宿主）**，五个不重合：
   ①prod profile 不验证（→YAML 地雷直接产物）②Flyway 不执行 ③mp-weixin 不构建 ④admin-web 不进 CI ⑤H2/MySQL 双轨。
   **本方案的主线就是把这张「不重合清单」逐项清零**——不是加几个 job，是把 CI 的验证面对齐到生产的运行面。
2. **金字塔中层厚实、单点位有洞、部署验证层缺失**：498+488 用例构成高质量中层（service/engine/controller），但基础工具模块（JsonUtils 等 6 个）裸奔，且「迁移可执行、配置可解析、小程序可构建」这类部署级验证完全缺席。
3. **供应链可复现性是 CI 自身的卫生**：`latest` 镜像让「同一 commit 两次 CI 结果不同」成为可能——守门者自己先要可信。

### 2.2 非目标

- ❌ 不自托管 runner（GitHub hosted 免费额度对当前规模充裕，自托管=多一台要运维的机器）
- ❌ 不做覆盖率强门禁（对存量 498 用例库设阈值必然误伤；覆盖率信息性展示列为可选）
- ❌ 不做 CD 全自动发布——**发布保持人在环**（微信审核、服务器 systemd 操作、外发动作，单人项目的最后一道防线；`prepare-release.ps1` 只做「与 CI 能力对齐」瘦身，见 T2.3）
- ❌ nightly 混沌仿真搬 CI 列为**可选项**（若仿真脚本依赖本地环境则不搬，保持本地夜间纪律——不为搬而搬）

## 3. 候选策略（3 个）

### 策略 A：路线图逐项补丁

**思路**：按诊断报告第 5 章清单逐个加 job/修卫生项，加完即止。

**优点**：每项 ~1h，一周见效；无前置设计成本。

**缺点**：无 job 拓扑设计 → 复制粘贴式增长、时长失控（今天 8min 半年后 25min）；守门散落各 job 无统一入口（本地复现 CI 状态困难）；「验证面对齐运行面」的映射关系只存在于作者脑中——三个月后自己都不知道哪个 job 防的是哪个生产面。

**成本**：⭐（6h）｜投产价值：中｜面试价值：低｜风险：低

### 策略 B：「CI = 运行面镜像」蓝图先行 + 分批落地 + 守门聚合 ★ **推荐**

**思路**：先落纸《验证面↔运行面对照表》与 job 拓扑/时长预算，再分 3 个 PR 落地；所有守门（本维度 2 件 + 维度1/2/3/4/5 各 1~3 件）聚合到 `scripts/checks.sh` 统一入口，实现「本地一条命令 = CI 全量守门」；供应链钉版与模板对齐作为第一批。

**理论依据**：
- Dev/Prod Parity（12-Factor）的**操作化**：把抽象原则转成可勾选的对照表（每个生产运行面 ← 至少一个 CI 验证项）；
- 蓝图先行（Architecture Blueprint before incremental patching）：增量修改若无目标拓扑约束会退化成补丁堆（Software Entropy）；
- 测试金字塔（Fowler/Hammant）：部署级验证（迁移/构建/配置解析）是金字塔的「部署验证层」，本仓恰好整层缺失；
- 可复现构建（Reproducible Build / SLSA 供应链思想的最小实践）：钉 digest；
- 「本地 CI 同构」：开发者在本地用与 CI 完全相同的入口跑守门，缩短反馈回路（Shift-Left 的执行层）。

**优点**：主线直接命中全仓唯一结构性问题（§4.2）；蓝图文档本身是面试高价值产物（展示「把原则操作化」的能力）；守门聚合让后续五个维度的制度产物有统一挂载点；分批 PR 每批独立可回滚。

**缺点**：蓝图设计 2h 前置；对照表需要随生产面变化维护（挂进发布 checklist 缓解）。

**成本**：⭐⭐⭐（~17h/4 周）｜投产价值：高（直接消除发布事故类风险）｜面试价值：高（CI/CD 是高频面试题且有 DORA/12-factor 可对标）｜风险：中低

### 策略 C：DevOps 全面化

**思路**：自托管 runner、测试分片并行、覆盖率门禁+SonarQube、CD 全自动（打 tag 即发布）、nightly 混沌仿真 CI 化。

**优点**：终态「大厂化」。

**缺点**：自托管 runner 增加一台需要运维的机器（与学生单人现实相反）；覆盖率门禁对存量库误伤；CD 全自动把「外发动作」从人的手里拿走——微信审核与 systemd 生产操作恰恰需要人在环；仿真搬 CI 若依赖本地环境则为搬而搬。**正确子集已被 B 吸收**（nightly 仿真列为可选项、覆盖率列信息性）。

**成本**：⭐⭐⭐⭐⭐（40h+ 持续运维）｜投产价值：中｜面试价值：中｜风险：高

## 4. 加权决策矩阵与选型结论

权重沿用全局（投产 0.30 / 面试 0.25 / 成本 0.25 / 风险 0.10 / 可维护 0.10）。

| 评分维度（权重） | 策略 A 逐项补丁 | 策略 B 蓝图+聚合 | 策略 C DevOps 全面化 |
|---|---|---|---|
| 投产价值（0.30） | 3.5 | **4.5** | 3.0 |
| 面试展示价值（0.25） | 2.0 | **4.5** | 3.5 |
| 实现成本可行性（0.25） | **5.0** | 4.0 | 1.0 |
| 风险安全度（0.10） | 4.0 | **4.5** | 2.5 |
| 长期可维护性（0.10） | 2.0 | **4.5** | 3.0 |
| **加权总分** | 3.35 | **4.40** | 2.85 |

**选型结论：策略 B**。决定性论证：prod YAML 地雷的因果链（「CI 不验 prod profile → 错误只在上线的启动瞬间暴露」）证明了这不是「加几个 job」的问题而是「验证面对齐」的问题——B 的对照表让对齐可检查，守门聚合让对齐可持续，钉版让守门者自身可信。C 的可取子集（nightly 仿真、覆盖率信息展示）以可选项并入。

## 7. 面试叙述要点（STAR 法）

- **S（情境）**：投产项目的 CI 只有「测试+H5 构建+密钥扫描」三个 job；一次全仓审计发现 prod 配置里埋着 YAML 缩进地雷——**CI 永远不可能发现它，因为 CI 从不激活 prod profile**。由此提炼出结构性判断：CI 验证面与生产运行面存在五个不重合（prod profile/Flyway/mp-weixin/admin-web/H2-MySQL 双轨）。
- **T（任务）**：把五个不重合清零，并让「对齐状态」本身可持续维护。
- **A（行动）**：
  1. 把 12-Factor 的 Dev/Prod Parity **操作化**为《验证面↔运行面对照表》——左列生产面、右列验证项，一页纸可审计；
  2. 蓝图先行再分批落地：7-job 拓扑 + 时长预算（并行 wall ≤10min），三个 PR 各自可回滚；
  3. 守门聚合 `scripts/checks.sh`：本地一条命令=CI 全量守门（反馈回路左移）；
  4. 守门者自证可信：gitleaks 从 `latest` 钉到 digest（可复现构建的最小实践）；
  5. 每个新守门上线都做一次「故意破坏」实验（防永绿灯）；
  6. 克制的非目标：不 CD 全自动（微信审核与 systemd 是人在环的最后防线）、不自托管 runner、覆盖率只做信息展示。
- **R（结果）**：五盲区清零；迁移错误/配置错误/小程序构建错误/契约漂移全部在 push 时暴露；发布检查单从「重复 CI」瘦身为「真正的最后一公里」；同类发布事故（YAML 地雷型）在结构上不可能再发生。
- **可被追问的深度点**：为什么覆盖率不做强门禁（存量库误伤+指标代理失效风险）；为什么发布保持人在环（外发动作的不可逆性）；nightly 仿真为什么可能不搬 CI（依赖本地环境的诚实权衡）；「验证面对齐」如何度量（对照表项数+盲区计数趋势）。
