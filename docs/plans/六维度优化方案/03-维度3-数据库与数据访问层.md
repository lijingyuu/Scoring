### 1.3 问题模式归纳（软件工程视角）

1. **好纪律缺制度兜底**：迁移编写纪律（无断号、单意图注释）是六维度最佳，但 validate 关闭 + CI 不执行 Flyway = 纪律全靠自觉，漂移（20 vs 21）正是「无强制力纪律」的必然产物。
2. **死 schema 是慢变量债**：死表、死索引不影响正确性，但每次新人（或三个月后的自己）读 schema 都要付「这是什么」的认知税；诊断 §4.2 的「最后一公里卫生」模式在 DB 维度的体现。
3. **决策悬置比错误决策更贵**：`match_runtime_state`「拍板保留」却无接线计划——既不删除也不接线的悬置状态让 V21 的认知成本永久化。本方案提供决策框架强制其落地。

### 2.1 目标

| # | 目标 | 度量 | 截止 |
|---|---|---|---|
| G1 | 迁移 checksum 纪律恢复 | prod 环境 `validate-on-migrate: true`（环境分层：主配置 true、dev profile false）；故意改动已应用迁移 → 启动失败用例演示 | 1 周 |

| G5 | 枚举载体规范 | 《数据库规范》落纸：新表枚举统一 TINYINT+注释映射（存量不动）；新迁移 checklist（时间列必带、单一意图、索引命名） | 2 周 |
| G6 | 热点批量写入 | 循环单条 INSERT 的 3~4 处逐一评估，仅「单事务 ≥50 行」热点改 MyBatis foreach 批量（缩短事务持锁时间），其余记录不改 | 4 周 |

### 2.2 非目标

- ❌ 不引入读写分离/分库分表/连接中间件（单实例、千级用户量，负收益）
- ❌ 不做全部存量枚举载体统一迁移（TINYINT↔VARCHAR 大规模 DDL 改写风险 > 收益，规范只约束新表）
- ❌ 不动并发保护体系（FOR UPDATE + CAS + 唯一键三层是本仓资产，诊断确认无裸读改写窗口）
- ❌ 不把 49 个 H2 测试类迁 Testcontainers（见 §3 策略 C 的否决论证）
- ❌ 不引入 Flyway 之外的迁移工具或重构 ORM

## 3. 候选策略（3 个）

### 策略 A：卫生修复（最小主义）

**思路**：只做 G1/G2/G3——开 validate（分层配置）、V32 补时间列、死表死索引处置。schema 双轨保持现状（手工同步）。

**理论依据**：先修可见痛点；变更面最小化。

**优点**：~5h 完成；全部是低风险 DDL/配置改动；立竿见影。

**缺点**：**双轨漂移的根因未动**——`schema-h2.sql` 仍靠手工同步，下一张新表诞生时 20 vs 21 变成 20 vs 22；迁移语法错误依然只能上线时暴露（CI 仍不执行 Flyway）；诊断 §4.2 指出的结构性问题「CI 验证面与生产运行面不重合」在 DB 维度原样保留。

**成本**：⭐（5h）｜投产价值：中｜面试价值：低｜风险：极低

### 策略 B：卫生修复 + schema 单轨化 + 漂移守门 ★ **推荐**

**思路**：A 的全部内容，加上让「迁移目录」成为唯一 schema 事实源的两件制度产物：①CI「迁移可执行性」job——GitHub Actions **services 侧挂 MySQL 8 容器**（非 Testcontainers，论证见后）跑 `flyway migrate` + 断言表数；②**表集合比对守门**——CI 脚本 diff「MySQL 迁移后 information_schema 表集合」vs「schema-h2.sql 的 CREATE TABLE 名集合」，漂移即红。`schema-h2.sql` 保留（快测试仍有价值）但从「事实源」降级为「派生缓存」，其正确性由守门保证。

**理论依据**：
- 单一事实源（Single Source of Truth）：两个 schema 文件必然漂移（Conway 式必然），只能选一个当源、另一个当派生物；
- 12-Factor Dev/Prod Parity：CI 验证面必须覆盖真实 MySQL 方言——H2 兼容模式验证不了 `ENGINE=InnoDB`、`ON UPDATE CURRENT_TIMESTAMP` 等 MySQL 特有语法；
- 测试左移（Shift-Left）：迁移错误从「上线时崩溃」提前到「push 时 CI 红」；
- 环境分层配置（profile-specific config）：prod 严 dev 宽的 validate 策略——纪律强度与环境污染风险成正比。

**为什么 services 侧挂而非 Testcontainers**：GitHub Actions 的 `services:` 由 runner 直接提供容器，无需 Docker-in-Docker、无 JVM 端 Testcontainers 依赖、冷启动快约 1~2 分钟；Testcontainers 的优势（本地可复现、版本任意）在本场景（CI-only 的迁移冒烟）用不到。**正确的子集选择**。

**优点**：根除双轨；每个 PR 自动验证迁移可执行性；守门脚本 ~30 行 shell 零框架依赖；面试叙事强（「为什么不用 Testcontainers 全量替换」是真实工程判断题）。

**缺点**：CI 时长 +2~3 分钟；初次对齐 `schema-h2.sql` 需补 `match_runtime_state`（或先删死表则反向对齐）；守门脚本本身需要一次「故意漂移」自测。

**成本**：⭐⭐（~12h/4 周）｜投产价值：高｜面试价值：高｜风险：中低

### 策略 C：全量 Testcontainers 化（彻底同构）

**思路**：49 个 H2 测试类全部改 Testcontainers MySQL，物理消灭 `schema-h2.sql`，测试即生产方言。

**优点**：理论最大同构；方言差异类 bug 全消。

**缺点**：①本地 Windows 开发强依赖 Docker Desktop（单人开发的可用性硬伤）；②每个测试类容器冷启动使本地单测从分钟级膨胀到十几分钟级，摧毁「快速回归」价值——测试金字塔的底座必须快；③49 类改造 ≈ 维度1 一次巨类拆分的工作量，收益却主要是「方言确认」——而 CI 侧挂方案已用 2 分钟覆盖了同样的方言确认需求。**过度工程**。

**成本**：⭐⭐⭐⭐（30h+）｜投产价值：中｜面试价值：中｜风险：高（测试基建大改）

## 4. 加权决策矩阵与选型结论

权重沿用全局（投产 0.30 / 面试 0.25 / 成本 0.25 / 风险 0.10 / 可维护 0.10）。

| 评分维度（权重） | 策略 A 卫生修复 | 策略 B 单轨化+守门 | 策略 C 全量 Testcontainers |
|---|---|---|---|
| 投产价值（0.30） | 3.0 | **4.5** | 3.5 |
| 面试展示价值（0.25） | 2.0 | **4.5** | 3.5 |
| 实现成本可行性（0.25） | **5.0** | 4.0 | 1.5 |

**选型结论：策略 B**，Phase 0 即策略 A 的全部内容（每阶段独立可交付）。C 的正确子集（CI 内真实 MySQL 验证）已被 B 以 services 侧挂形式吸收——「吸收而非采纳」与维度1/2 的选型逻辑一致：**用最小成本摘取大方案中唯一有价值的子集**。

## 5. 选定策略 B 的分阶段实施计划（WBS）

> 迁移编号协调（全方案总口径，维度2/6 引用）：**V32 = match_record 时间列**｜**V33 = user.token_version（维度2 Phase 1）**｜**V34 = 死表死索引处置**。原则：一个迁移一个意图。

### Phase 0：卫生修复（第 1 周，~5h）

| 任务 | 内容 | 涉及文件 |
|---|---|---|
| T0.1 | **validate 环境分层**：`application.yml` 的 `flyway.validate-on-migrate` 改 `true`（默认=生产纪律）；`application-dev.yml` 显式覆盖 `false`（dev 库允许实验性手工改表，写入配置注释说明理由）。**验证**：本地 dev profile 启动正常；临时篡改一个已应用迁移文件 → prod 配置启动失败（用例演示后还原） | `application.yml`、`application-dev.yml` |
| T0.2 | **V32 补时间列**：`ALTER TABLE match_record ADD COLUMN create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP, ADD COLUMN update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP`。MySQL 8 对带 DEFAULT 的 ADD COLUMN 走 INSTANT 算法，存量行自动回填默认值，万级行数秒级完成；对应实体 `MatchRecord` 补两个字段与 `selectTime` 断言（若用戾手写映射） | `V32__match_record_add_time_columns.sql`（新增）、`MatchRecord.java` |
| T0.3 | **schema-h2.sql 过渡对齐**：补 `match_runtime_state` 建表（20→21），使 Phase 1 守门上线时基线干净；顺手评估把该文件从 `src/main/resources` 迁至 `src/test/resources`（它只被测试引用——迁移前 grep 确认无 main 引用） | `schema-h2.sql` |
| T0.4 | **死表决策启动**：按 Phase 2 决策框架预填两栏（删除的代价 / 接线的成本），发给未来的自己一周冷静期 | `docs/adr/ADR-match-runtime-state.md`（新增草稿） |

- **验收标准**：V32 在本地 MySQL 执行成功且 `SHOW CREATE TABLE match_record` 含两列；全量回归绿（498 用例）；dev/prod 两 profile 启动行为符合预期。
- **测试策略**：既有零漂移测试（实体↔DDL 抽查）自动覆盖新列；手测一次「篡改迁移→启动失败」留存截图（面试素材）。
- **风险与回滚**：V32 为纯增量 DDL（ADD COLUMN + DEFAULT），回滚 = `ALTER ... DROP COLUMN`（或整体 revert 迁移文件后 flyway repair——单人 dev 库可接受）；风险极低。
- **工时**：5h。

### Phase 1：CI 迁移可执行性 + 漂移守门（第 2~3 周，~5h；CI 落地动作与维度6 同一 PR）

| 任务 | 内容 | 涉及文件 |
|---|---|---|
| T1.1 | **CI「迁移可执行性」job**：`ci.yml` 新增 job——`services: mysql:8.4`（health-check 就绪）→ `mvn -DskipTests package` 或直接 `flyway:migrate`（用 Maven Flyway 插件或 spring-boot 启动触发，取更简者）→ `mysql -e "SELECT COUNT(*) FROM information_schema.tables WHERE table_schema=DATABASE()"` 断言 = 21（数字写死即守门：新表不加断言即红） | `.github/workflows/ci.yml`（与维度6 方案协同） |
| T1.2 | **表集合比对守门**：同 job 内追加脚本——从 MySQL `information_schema` 取表名集合，从 `schema-h2.sql` grep `CREATE TABLE` 取表名集合，`diff` 非空即 exit 1。~15 行 shell | 同上（内联脚本或 `scripts/check-schema-parity.sh`） |
| T1.3 | **守门自测**：临时删掉 h2 里一张表 → 确认 CI 红 → 还原（验证守门真的在守，防「永绿灯」） | 一次性操作 |
| T1.4 | 本地等价入口：`scripts/check-schema-parity.sh` 支持本地跑（连本地 MySQL 或仅做 h2 侧静态检查的降级模式） | `scripts/` |

- **验收标准**：PR 触发的 CI 中迁移 job 绿且耗时 <4 分钟；故意漂移实验红过一次（留档）。
- **测试策略**：守门自测即测试；T1.1 断言数字 21 是显式棘轮（加表必须改断言 → 强制意识到「我在新增 schema 事实」）。
- **风险与回滚**：services 容器偶发未就绪 → health-check 重试参数；job 独立不影响既有测试 job，可单独 disable。
- **工时**：5h。

### Phase 3：热点批量写入评估（第 4 周，~3h）

| 任务 | 内容 | 涉及文件 |
|---|---|---|
| T3.1 | 定位循环单条 INSERT 的 3~4 处（报告未列具体位置，先 `grep -rn "for.*insert\|save(.*);" --include="*ServiceImpl.java"` 粗筛 + 人工确认） | service 层 |
| T3.2 | 逐一评估三问：单事务行数 ≥50？事务持锁时长可感知？表是热点吗？**三问全 yes 才改** MyBatis foreach 批量（改写收益：网络往返 N→1、行锁持有窗口缩短）；否则记录「不改理由」 | 对应 Mapper XML |
| T3.3 | 改造处补「批量插入 + 部分失败回滚」用例（批量写入的正确性边界：任一行失败整事务回滚 vs 分片提交的取舍，按业务语义定） | 集成测试 |

- **验收标准**：改造处集成测试绿 + 混沌仿真无差异；未改造处有记录理由。
- **风险与回滚**：foreach 批量在 MySQL 驱动需 `rewriteBatchedStatements=true` 才真批量（连接串参数——注意 `.env.example` 联动，维度6 已列）；回滚 revert。

## 7. 面试叙述要点（STAR 法）

- **S（情境）**：单人运维的生产 MySQL（31 个 Flyway 迁移、21 张表），审计发现：迁移验证关闭（改了已应用迁移生产不报错）、测试 schema 与真实 schema 双轨且已漂移（20 vs 21 张表）、一张主代码零引用的悬置死表。
- **T（任务）**：在没有 DBA、不引入重型设施的前提下，把「迁移目录」恢复为唯一 schema 事实源，并让漂移在 push 时而非上线时暴露。
- **A（行动）**：
  1. 环境分层开 validate：prod true / dev false，纪律强度与环境风险成正比；
  2. CI 增「迁移可执行性」job：GitHub Actions **services 侧挂 MySQL 而非 Testcontainers**——论证取舍（无 Docker-in-Docker、冷启动快、CI-only 场景够用）；
  3. 表集合比对守门 + 表数硬断言（21 写死）：`schema-h2.sql` 从「第二事实源」降级为「被守门的派生缓存」；
  4. 死表用两问决策框架强制落地（季度内有接线需求吗？重建成本多低？），推翻三个月前「拍板保留」的旧决策并用 ADR 记录推翻理由——**决策可以反悔，但不可悬置**；
  5. 一个迁移一个意图的编号规划（V32 时间列/V33 安全列/V34 死表处置）。
- **R（结果）**：schema 双轨→CI 强制单轨；迁移错误暴露点从生产启动提前到 PR 的 CI；死 schema 清零；`match_record` 获得时间审计能力。
- **可被追问的深度点**：为什么 H2 兼容模式不能替代真实 MySQL 验证（方言 DDL）；MySQL 8 INSTANT ADD COLUMN 与重建表算法差异；rewriteBatchedStatements 对批量写入的实际影响；为什么敢删「拍板保留」的表（新证据 + 重建成本量化 + dump 兜底）。
