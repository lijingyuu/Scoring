# 羽毛球「双打选手拆分存储 + 四半区实时沙盘」可行性报告

- 日期：2026-10-25
- 调研方式：3 个子 Agent 并行取证（羽毛球模块现状 / 排球沙盘实现 / BWF 官方规则与 GitHub 开源项目），全部结论附 `file:line` 或来源 URL。
- **总结论：可行，且改动面可控。** 核心洞察有三个：
  1. 站位不需要新增持久化表——排球的事件流（`match_event`）+ runtime 快照机制羽毛球已经在用，初始站位可以落成 `lineup_snapshot` 事件（该类型**已在后端白名单里**），后端可以做到零迁移甚至零改动（除创建链路外）；
  2. 羽毛球站位可以完全由「比分奇偶 + 每侧一个『谁在右区』锚点」确定性推导，无需记录每一球的发球员（开源项目 bup 已验证该模型）；
  3. 排球沙盘是纯 CSS Grid 实现，样式资产与「上比分、下沙盘」布局可直接搬用。

---

## 1. 需求复述

1. 双打参赛单位在「创建比赛 / 录入名单」阶段识别为「一组两人」，**两人名字分别存储**（现状：组合只是名字字符串，或成员藏在团体赛子项 JSON 里）。
2. 羽毛球记分牌页从单一比分展示，改为「上：比分展示；下：简化沙盘」——场地分左右两侧（中间隔网），每侧一条横线分为上下两半，共 **4 个半区**，对应双打 4 名选手站位 / 单打每侧 1 人。
3. 沙盘要体现**发球站位规则**（发球方分数偶数→右发球区、奇数→左发球区），权威来源为 BWF《Laws of Badminton》。
4. 双打开局时需要把 4 名选手分别填入 4 个半区（同组两人谁左谁右不固定）。

## 3. 权威规则梳理（BWF《Laws of Badminton》V5.0，2025-04-26 生效）

主来源：BWF Statutes 官网 PDF（corporate.bwfbadminton.com/statutes → Section 4.1 Laws of Badminton V5.0）。⚠️ 搜索排名很高的 worldbadminton.com/rules 镜像是 15 分制「Alternative Laws」，不可作标准来源。

### 3.1 计分与换边

| 规则 | 条款 |
|---|---|
| 三局两胜；每球得分制；先得 21 分胜该局 | 7.1–7.3 |
| 20 平后先净胜 2 分者胜；29 平时先得第 30 分者胜 | 7.4 / 7.5 |
| **上一局胜方在下一局先发球** | 7.6 |
| 换边时机：第一局结束；第二局结束（打第三局时）；**第三局一方先得 11 分时** | 8.1.1–8.1.3 |
| 漏换边：发现且球不在空中时立即换，**既有比分有效** | 8.2 |
| 局间休息 ≤120s，11 分技术暂停 ≤60s | 16.2 |

现状代码已完全覆盖（`pointsToWin=21 / capPoint=30 / enableDeuce`，`finalGameSideSwitchThreshold = ceil(pointsToWin/2)`）。

### 3.2 单打发球站位（Law 10）

- **10.1.1** 发球员本局未得分或得分为**偶数** → 从**右发球区**发球并接发；**10.1.2** 得分为**奇数** → **左发球区**。
- **10.3.1** 发球方得分 → 同一发球员**换到另一发球区**继续发；**10.3.2** 接发方得分 → 得分并成为新发球方（回到 10.1.1/10.1.2 按分数奇偶）。
- 10.2.1 发球/接发之后回击可站任意位置（站位限制只存在于发球瞬间）。

### 3.3 双打发球站位（Law 11，本次核心）

- **11.1.1 / 11.1.2**：发球方本局未得分或**偶数 → 右发球区**发球；**奇数 → 左发球区**（与单打一致）。
- **11.1.3**（连续性锚点）：*接发方*「上次发球的队员必须站在他上次发球的同一发球区，其同伴反向站位」——这就是「换发后由与分数奇偶对应半区的队员发球」的规则来源。
- **11.1.4**：接球员 = 与发球员**斜对角**发球区的队员。
- **11.1.5**：*只有在己方处于发球状态且赢分时，同一队两人互换左右发球区*；接发状态赢球不换位（只是拿到发球权）。
- **11.3.1 / 11.3.2**：发球方赢 → 同一发球员从**另一发球区**继续发；接发方赢 → 得分并成为新发球方。
- **11.4.1–11.4.5** 发球次序循环：**首发球员 → 首接球员的同伴 → 首发球员的同伴 → 首接球员 →** 循环。
- **9.5**：发球瞬间同伴可站己方场区**任意位置**（只要不遮挡视线）→ 沙盘里同伴的半区只是「习惯站位提示」，规则不强制。
- **11.6**：下一局**胜方任一队员**都可先发、**负方任一队员**都可先接 → 局间允许重排站位。
- **换边（Law 8）不导致队员互换左右半区**：换边只交换网两侧场地，左右归属仍由「分数奇偶 + 11.1.3/11.1.5 连续性」决定（这是条款集合的推论，实现时应以「分数奇偶 + 每侧锚点」为唯一真源）。
- 站错区/错序（Law 12）：发现时纠正，**既有比分有效** → 需要手动纠错入口。

### 3.4 位置推导模型（核心算法，沙盘的灵魂）

不需要记录每一球的发球员。**每侧只存一个锚点：「当前站在本方右发球区的选手 id」（`rightPlayerId`，另一人自动在左区）**，加上 `serveSide + 双方比分` 即可完整推导（开源项目 bup 用单布尔 `player1_even` 验证了此模型）：

```
加分转移（双打）：
  若 发球方 == 得分方：得分方 rightPlayerId 与另一人【互换】；比分+1；serveSide 不变
  若 接发方 == 得分方：双方都【不互换】；比分+1；serveSide = 得分方

任意时刻推导：
  发球员   = 发球侧中，分数偶数 ? rightPlayerId : 左区选手
  接发球员 = 接发侧中，与发球员【同区名】（同名半区即屏幕上的斜对角）的选手
  半区高亮 = 发球员所在半区强高亮；接发球员半区次高亮；同伴半区弱化（9.5）

单打退化：无锚点；每人所在半区 = （发球时）本方分数奇偶；接发方站斜对角同区名半区
换边（局间/决胜局11分）：只交换屏幕左右参赛方显示，锚点不动
局间：锚点默认延续；首发球方 = 上局胜方（7.6）；允许手动交换（11.6）
```

自检：0-0 时双方右区选手发/接（斜对角 ✓）；持续应用该规则，11.4 的发球次序循环 `[首发, 首接同伴, 首发同伴, 首接]` 会自动涌现——可写进 fuzzer 断言（仓库已有 `badminton-fuzzer.js` 混沌测试基建，直接扩展）。

### 3.5 单/双打发球区边界差异（沙盘提示文案用）

- 双打发球区：**短而宽**——前发球线（距网 1.98m）到双打后发球线（距底线 0.76m），横向用外边线（宽 6.1m）。
- 单打发球区：**长而窄**——前发球线到**底线**，横向用内侧单打边线（宽 5.18m）。
- 「发球员站哪个半区（偶右奇左）」两者规则一致，高亮逻辑可复用；文案建议区分。

### 3.6 前瞻：2027 年三局 15 分制

BWF 已发布 V6.0（2027-01-04 生效），改为 3×15（Olympics.com 报道）。对本功能影响：**发球半区奇偶规则不变**；中点换边阈值公式 `ceil(pointsToWin/2)` 自动适配（15→8）；分制本就可配置——无需预先开发，但沙盘文案不要硬编码「21 分」。

## 5. 方案设计

### 5.1 数据模型与存储（选手拆分）

**推荐：参赛方 `player` 行保留（继续作为签表/排名/记分的原子单位），选手明细复用 `tournament_team_member` 表**（它本来就是 `participant_id → 成员列表`，羽毛球团体赛已在写，V11 起 jersey 可空、display_order 现成）：

- 个人赛新增「单打 / 双打」参赛模式（新迁移 `V25`：`tournament`（或 `tournament_division`）加 `entry_player_count TINYINT DEFAULT 1`）。
- `CreateTournamentReq.PlayerEntry` 增加 `members: [{name}]`；双打校验每参赛方恰 2 人、名字非空。
- `TournamentCreationFactory`：双打个人赛在 persistDivision 时调用现成的 `insertTeamMembers` 落成员。
- **不做存量数据迁移**：无成员的参赛方照旧按组合名字符串运转，沙盘降级显示（见 5.5）。
- 团体赛子项双打已有成员明细（`team_match_item.*_member_ids_json`），无需新存储，只需把成员名传进记分牌页。
- 顺带修正 `docs/数据库.md:94`「tournament_team_member 仅排球」的过期表述。

**双打的判定不新增 matchType 字段**，沿用现有组合：个人赛 = `entry_player_count==2`；团体赛 = `item_code ∈ {D,MD,WD,XD}` / `player_count==2`；接力追分赛排除（见 D8）。

### 5.2 站位状态机与事件流（后端零迁移）

- `use-scoreboard-state.js` 状态扩展：`mode: 'singles'|'doubles'`、`leftAnchor/rightAnchor`（= 每侧 rightPlayerId）、双方成员名单（来自 record 装配或 URL 传递）；`addScore` 中按 5.4 模型互换/不互换锚点。
- 新增纯函数模块 `pages/scoreboard/court-position.js`：`deriveCourtView(state)`（返回 4 半区 → 选手、发球员、接发球员、高亮建议），**无副作用、可独立测试**；`badminton-fuzzer.js` 加断言（11.4 次序循环涌现、斜对角恒成立、锚点互换只在发球方得分时发生）。
- 事件落库**零后端改动**：初始站位 = `lineup_snapshot` 事件（payload 含 4 人半区 + 首发球方）；锚点与派生视图进 `score_snapshot` 的 `runtime` 快照（已有机制，undo 走 `prevRuntime` 自动回滚站位）；换边 = 现有 `side_switch`。三类都在白名单（`MatchServiceImpl.java:780`）。
- 手动纠错 = 追加一个 `lineup_snapshot`（或 `score_snapshot(reason:'swap-positions')`）事件，比分不动（对应 Law 12「纠正、比分有效」）。
- 不使用排球的 `match_lineup_config` 表（6 人语义 + 每局重录阵容，羽毛球不需要）；`match_runtime_state`（V21）也继续闲置。

### 5.3 记分牌 UI（上比分、下沙盘）

- 沿用现有页面骨架，在 `games-strip`（逐局比分条）下方插入沙盘卡片（横屏布局，宽度充裕）。
- 沙盘 = CSS Grid：外层 flex 左半场 | 竖网 `.court-net` | 右半场；每半场 `grid-template-rows: 1fr 1fr` 两个槽位。样式（槽位描边、徽章、底色、发球标记）全部搬排球。
- **朝向映射（推荐物理俯视正确版）**：左队面朝右 → 其右发球区 = 屏幕左下、左发球区 = 左上；右队右发球区 = 右上、左发球区 = 右下。这样「同名半区」在屏幕上天然呈**斜对角**，0-0 发球时左下 ↔ 右上高亮，视觉即规则。每个槽位标注小字「右发球区 / 左发球区」（各自以本队视角）。
- 高亮：发球员半区强高亮（发球边框/底色 + 🏸 图标）、接发球员半区次高亮、同伴半区常亮但弱化、双打规则提示行文案区分单/双打发球区边界（3.5）。
- 换边（局间自动 / 决胜局 11 分 / 手动按钮）：交换左右参赛方的显示与锚点归属（复用现有换边逻辑），沙盘随 state 重渲染，锚点不动。
- 单打：每侧只渲染 1 个有效槽（按奇偶落在对应半区），另一槽弱化置空。

### 5.4 初始站位录入交互（双打开局）

复用排球 `lineup.vue` 的「站位网格逐格点人」范式，简化为一步式弹窗/子页（只在双打、`currentGameNo==1`、双方比分 0:0 且尚无 lineup_snapshot 时强制）：

1. 选首发球方（规则上由挑边决定，现状首局 serveSide 来源待查证——见 D12）；
2. 4 个半区槽位，从两侧各 2 人名单中点选填入（首发球方的右发球区选手即自动成为首个发球员，对面右区选手即首个接发球员——无需单独再选发球员）；
3. 确认 → 写 `lineup_snapshot` 事件 + runtime 锚点初始化 → 进入正常记分。
4. 第 2/3 局开始：默认延续上局锚点（首发球方自动 = 上局胜方，7.6），提供轻量「交换两人站位」入口（11.6 允许局间重排）。

### 5.5 恢复重放与撤销兼容

- runtime 快照加 `pos` 字段（mode + 两锚点 + 成员 id）；**旧事件无 `pos` → 判定 legacy，沙盘降级**：双打显示组合名横跨半区、不高亮，比赛照常记分。恢复仲裁逻辑（`decideEntrySource`）不动。
- undo 已走 `prevRuntime` 追加式回滚（`match-events.js:15-16`），锚点进快照后自动随之回滚，无需新机制。
- 换设备重进：服务端事件重放重建（`buildRecoveredState` 以最新 `runtime` 为权威）→ 站位天然恢复。

## 6. 边界条件与风险

1. **个人赛双打波及面**：分组/签表/排名/战报/记录页现均假设「参赛方 = 单名」，显示层需逐处适配（组合名显示为「张三 / 李四」）。签表与排名引擎以 player.id 为原子单位，**不需要动**——这是复用 player+members 方案的最大红利。
2. **接力追分赛**：复用 `capPoint` 为接力人数、非真实羽毛球计分语义——沙盘与发球规则必须 gate 掉（按 `team_match_template==2` 排除）。
3. **首局发球方现状待查证**：状态机里「局开始 serveSide = 上局胜方」，第一局的初始值来源未见明确交互（可能默认 left）。规则上应由挑边决定，建议并入初始站位步骤让裁判选。
4. **迟到纠错（Law 12）**：站错区/错序发现后比分有效、只纠正站位 → 必须给「交换同侧两人半区」手动按钮；记录页可考虑展示站位纠错事件以备争议。
5. **漏换边（8.2）**：现有手动「换边」按钮已可处理；比分不变。
6. **旧比赛/旧数据**：无成员明细、事件无 `pos` → 沙盘降级，不做迁移。
7. **2027 新赛制**：奇偶规则不变；换边阈值 `ceil(pointsToWin/2)` 自适应（15→8）；避免硬编码 21 分文案。
8. **混双 XD**：与双打站位逻辑完全一致，无额外规则。
9. **「实时」的含义要对齐预期**：现状无观众端/大屏端，沙盘的实时性 = 执裁端本机即时 + 跨设备事件重放恢复；若要「观众大屏实时看沙盘」是另一档工作量（需新增轮询或推送基建）。
10. **语音播报**：现已有换发球/局点/赛点播报；可选加「发球员姓名」，注意小程序 TTS 稳定性。
