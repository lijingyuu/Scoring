# 羽毛球执裁链路对齐排球：事件上云与服务端恢复方案

> **状态**：✅ **已落地 + 两轮对抗审查闭环**（事件上云/服务端恢复/锁体验对齐 + 后端 409 加固；前端全量 400 项、后端全量 486 项 0 失败，修复记录见 §7/§8，2026-10-20）  
> **议题来源**：羽毛球个人赛「比分只在本机」缺陷（2026-10 试裁场景复盘后遗留任务）
> **关联文档**：[[API接口.md]] · [[数据库.md]] · [[羽毛球状态机与赛制全生命周期混沌测试指南.md]]

## 1. 问题与目标

羽毛球个人赛（及团体赛子项，二者共用 `pages/scoreboard/index.vue`）的执裁状态全程只存在
本机 `uni storage`（`badminton_scoreboard_state_<matchId>`），唯一上云时刻是终局 `PUT /finish`。

执裁锁（`MatchLockService`）本身与排球一致，但「锁交接」与「分数交接」脱节：

| 场景 | 改造前 |
|---|---|
| 同设备退出再进 | 恢复（本地缓存） |
| 换设备顶锁接管 / 锁过期接管 | 比分从 0:0 重来 |
| 清缓存 / 卸载重装 | 全部丢失 |
| 终局未结算即杀进程 → 他设备接管 | 前一份结果静默蒸发 |

目标：把排球那套「每分事件上云 + 进入时服务端重放恢复」移植到羽毛球，使锁交接与分数交接配套。

**范围外**：接力赛 `pages/tournament/team-relay.vue`（独立状态机、按段记分、无「局」概念），下一轮跟进。

## 2. 关键结论（后端零迁移）

调研确认排球的事件通道本就是运动无关的，羽毛球可直接复用：

- `match_event` 表无 `sport_type` 列，`UNIQUE KEY uk_match_event_seq(match_id, event_seq)`；
- `saveMatchEvents` 校验链（行锁 → 操作人 → 执裁锁 → 可结算态 → 分数/局号/发球方/类型白名单/payload 合法 JSON → 同 seq 幂等跳过、异内容 409 整批回滚）与运动无关；
- `GET /record` 只做 `requireMatchReadable`，**不需要执裁锁**；返回事件列表 + 派生视图，重放在前端；
- `restart` 已自动清理 `match_event`，无需新增逻辑；
- 羽毛球记录页 `individual-record.vue` 已在用 `/record`，该接口对羽毛球本就可用。

因此后端无表结构变更。仅做一处加固（并发同 seq 唯一键冲突由 500 归位为 409）与文档同步。

## 3. 事件契约（羽毛球）

只使用既有白名单类型，不新增 `eventType`：

| 动作 | eventType | payload.reason | 说明 |
|---|---|---|---|
| 首次进入开局 | `score_snapshot` | `init` | 记录规则基线 + 双方名称 |
| 得分 | `score_snapshot` | `score` | `scoringSide` |
| 撤销 | `score_snapshot` | `undo` | `revertToSeq` = 撤销生效后保留的事件水位 |
| 局末「换边继续」 | `side_switch` | `between_games` | 同时表达局边界（与排球一致，不设专门局结束事件） |
| 手动换边 | `side_switch` | `manual` | 计入撤销栈 |
| 决胜局技术换边 | `side_switch` | `deciding_technical` | 不计入撤销栈 |
| 退赛 | `score_snapshot` | `retire` | `retiredSide`；零后端改动（payload 自由字段） |

每条事件 `payload` 内嵌两份**全量运行时快照**：

- `runtime`：动作生效后的状态；
- `prevRuntime`：动作生效前的状态（撤销栈重建的唯一来源）。

快照字段（**一律参赛方原始坐标**，`sidesSwapped` 单独记录，避免换边后语义漂移）：

```
leftTeam/rightTeam, leftScore/rightScore, leftGameWins/rightGameWins,
currentGameNo, gameScores[], serveSide, sidesSwapped, retiredSide,
matchEnded, winnerName, matchStartTime, matchDuration,
finalGameSideSwitchHandled/Pending, gameEndPromptPending/Handled, matchRules{}
```

事件顶层 `leftScore/rightScore/serveSide/gameNo` 也取原始坐标，供 runtime 缺失时兜底重放。

### 三条照抄排球的不变式

1. 事件序号全局单调，整批 PUT 所有未同步事件，409 时按服务端最大序号重排后重试一次；
2. 一局结束不单独发事件，由下一局 `side_switch(between_games)` + runtime 内 `gameScores` 表达；
3. 撤销不重写历史，只追加 `undo` 快照；`historyStack` 不上云，由事件重放重建。

## 4. 实施内容

### Phase 1 事件管道（`src/pages/scoreboard/match-events.js`）

镜像排球 `useScoreboard.js` 的事件管道：800ms 防抖批量 PUT、失败指数退避（1s→×2→30s）、
409 序号冲突自愈（解析「服务端最大序号 N」或回退 `GET /record`）、只读停发、
`flushImmediately()` 供结算前强制冲刷。

### Phase 2 进入恢复（`src/pages/scoreboard/badminton-recovery.js`）

纯函数集合：

- `buildRecoveredState(record)`：取最新事件 `runtime` 作为当前状态；`historyStack` 由
  「计入撤销栈的事件」的 `prevRuntime` 顺序重放、遇 `undo` 弹栈得到；`nextEventSeq = max+1`；
- `shouldUseLocalCache(record, cached, { sameSession })` 仲裁：

| 条件 | 数据源 |
|---|---|
| 服务端无事件（maxSeq=0）且本地有缓存 | 本地（部署过渡保护，防老比赛被清零） |
| `status ∈ {2,3}` 已结算 | 服务端（引导战报页） |
| `sameSession && 本地 lastSyncedEventSeq ≥ 服务端 maxSeq` | 本地（同设备续裁，含未同步事件） |
| 其余（换设备 / 顶锁 / 本地落后） | 服务端重放 |

### Phase 3 锁体验对齐（`index.vue`）

- `acquireMatchLock` → `acquireMatchLockWithRetry`（3 次 / 300ms，与排球一致）；
- 锁 token 持久化（`load/save/clearMatchLockToken`），重进可判 `sameSession`；
- **首次抢锁失败 → 拒绝进入**（全屏遮罩「当前比赛正由其他设备执裁，请稍后再试」+ 重试/返回），
  与排球 `denyMatchEntry` 一致；比赛中途心跳丢失仍降级只读横幅（排球同）；
- 结算成功后 `flush 事件 → finish → 停心跳 → 清 token → 释放锁 → 清本地缓存`；
- `onShow` 在心跳已停且仍持锁职责时重新取锁。

### Phase 4 后端加固与文档

- `saveMatchEvents` 并发同 seq 撞唯一键时捕获 `DuplicateKeyException` → `ConflictException(409)`
  并回带服务端最大序号（排球同样受益）；
- `docs/API接口.md` §6.8 补羽毛球事件语义表，§6.15 补羽毛球拒绝进入语义。

### Phase 5 测试

- 实际交付：`badminton-events-recovery.test.js`（28 项：恢复矩阵/事件管道/跨设备端到端/审查回归，合并覆盖原计划的 recovery 与管道两个测试文件）；fuzzer 双阶段审计由确定性跨设备端到端测试替代（同场景可断言，见 §7 说明）；
- 后端：`MatchEventIntegrationTest` 补羽毛球形状用例与 409 加固用例（`reason=retire`/`between_games`/DuplicateKeyException→409）。

## 5. 验收场景

| 场景 | 期望 |
|---|---|
| 同设备退出再进 | 本地/服务端一致恢复 |
| 换设备顶锁接管、锁过期接管 | 当前比分 + 各局记录 + 发球方 + 规则全部恢复 |
| 只读设备 | 拒绝进入（与排球一致） |
| 清缓存 / 卸载重装 | 服务端恢复 |
| 终局未结算杀进程 → 他设备接管并结算 | 从真实比分继续，不再 0:0 |
| 弱网 | 退避重试，恢复不丢分 |

## 6. 行为变化提示

- `TournamentDrawService` 以「存在 match_event」作为开赛痕迹守卫：羽毛球比赛进行中（事件已上云）后
  签表调整会被拒。语义正确，且顺带堵住了改造前「羽毛球比分为本机态时签表仍可改」的漏洞。
- 羽毛球局中服务端 `scoreDisplay` 仍为空（只在 `finish` 落库），恢复一律靠前端重放事件——与排球一致。

| # | 核实 | 处置 |
