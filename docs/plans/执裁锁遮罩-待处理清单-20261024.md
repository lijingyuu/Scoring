## A. 建议做（结论已核实，可直接动手）

### A1（重写）权限被移除的裁判进入无限重试遮罩，且文案误导

**事实链（已逐行核对）**

- `frontend/src/utils/request.js:82 / :91 / :105 / :117`：所有失败路径都是 `reject(new Error(message))`，**错误对象不带任何状态码**。
- `frontend/src/composables/use-lock-guard.js:105-115`：`probeLockStatus` catch 后一律 `return null` → 「断网」「旧后端缺接口」「无权限」三者在 guard 眼里完全一样，都走降级直抢。
- **权限失败的真实 HTTP 码是 400，不是 403**：`backend/src/main/java/com/scoring/backend/service/match/MatchAccessGuard.java:32` 抛 `IllegalArgumentException("only creator or referee can modify this match")`，由 `backend/src/main/java/com/scoring/backend/common/GlobalExceptionHandler.java:31-36` 映射为 `400`。
- `GET /lock-status`（`MatchLockService.java:101-112`）与 `POST /lock`（`:40-64`）**全链路不可能返回 403**。403 只属于写接口的锁失效：`MatchLockService.java:125`、`TeamMatchServiceImpl.java:650`「执裁会话已失效，请重新进入比赛」。
- 因此用户实际看到的文案是 `frontend/src/pages/scoreboard/index.vue:390`「暂时无法取得执裁权，请稍后再试。」，或遮罩重试分支 `RETRY_FAILED`「获取执裁权失败，请稍后重试」（`use-lock-guard.js:23 / :210`）——**不是**「正由其他设备执裁」（那句只在 acquire 返回 `success=false` 时出现，`index.vue:387`）。
- 严重性：被移出裁判名单的人每次重试必然再 400，遮罩永不消失，**只能退出**。这是「死循环」而不是「文案不准」。

**改法（推荐 ①+②，③ 按需）**

1. **后端局部**：`MatchLockService` 的 4 处 `requireMatchOperator`（第 43 / 70 / 88 / 103 行）用 try-catch 把 `IllegalArgumentException` 转成 `ForbiddenException`（语义就是「无权执裁该比赛」），**不动全局守卫**，避免影响战报等其它入口；顺带把该英文文案中文化。
   - 风险已核：全仓前端没有任何按 403/400 分支的代码（`grep -rn "403" frontend/src` 仅命中 2 处注释），改状态码无连带。
2. **前端 `request.js`**：三处 reject 给 Error 挂 `statusCode`（`:91`、`:117`、`:82`）；`body.code !== 0`（`:105`）另挂 `bodyCode`，以便区分「HTTP 200 + 业务错误码」。
3. **guard**：`probeLockStatus` 失败时返回 `{ ok:false, forbidden:true }` 之类的最小信息；`showDenied` / `retry` 命中 403 时改文案「你已不在该比赛的执裁名单，请联系赛事创建者或管理员」，并置 `retryDisabled = true`（重试无意义，不给死循环入口）。

**验收**

- 前端：`use-lock-guard.test.js` 增「探测 403 → 专门文案 + 重试禁用」用例。
- 后端：`MatchLockIntegrationTest` 增「撤销裁判授权后 `lock-status` 返回 403」用例（可复用现有 `grantReferee` 帮助方法）。

**代价**：后端 ~10 行；前端 request 4 处；guard ~10 行；2 个测试用例。

> 2026-10-25 已实施：四个锁接口权限失败改 403 + 中文文案，前端 403 专门文案并禁用重试；另补修：心跳 403 触发遮罩、acquire 403 不重试。

## B. 需要产品/协议决策（不擅自动）

### B1 退出时「冲刷事件」与「释放锁」的竞态

**位置（行号已核实，与上一版一致）**

- `frontend/src/pages/scoreboard/index.vue:771`（`onBackPress` 内的 `void eventPipeline.flushPendingEventsImmediately()`）↔ `:748`（`onUnload` 的 `releaseMatchLock`）。
- `frontend/src/pages/tournament/team-relay.vue:1091`（`goBack` 内冲刷）↔ `:1145`（`onUnload` 释锁）。

**机制核实**：事件上云走 `MatchServiceImpl.saveMatchEventsInternal`（第 309-311 行）→ 要求 `requireActiveMatchLock`（`MatchLockService.java:116-130`，不满足抛 `ForbiddenException` → 403「执裁会话已失效」）。冲刷失败后 `match-events.js` 的 `scheduleRetry` 计时器会被 `onUnload` 的 `eventPipeline.stop()`（`match-events.js:380-384`）清掉，所以只能等下次进入续传 → **数据不丢、但「退出时顺手传完」经常失败**，与上一版判断一致。

**上一版漏掉的一个更根本的事实**：羽毛球侧的冲刷**只写在 `onBackPress` 里**，页内 UI 导航（结算成功后 redirect、遮罩返回、`leaveDeniedEntry`）根本不会触发冲刷；接力赛只有 `goBack` 按钮触发。所以「退出即传完」在部分退出路径上不是「竞态失败」而是「压根没发起」。

**三个方向**：① 退出前 `await` 冲刷再导航（多一次网络往返，需 loading）；② 释锁延后（如 `setTimeout` 或页面 unload 后再发）；③ 维持现状（靠下次进入续传）。若选 ②，注意 `releaseMatchLock` 已是 `.catch(() => {})` 的 best-effort，不会阻塞 UI。

> 2026-10-25 已实施（②方向变体）：三页面 onUnload 统一改为「先冲刷未同步事件、冲刷完成（或失败）后再 best-effort 释锁」，onBackPress/goBack 显式冲刷已删，接力物理返回键与排球退出路径由此首次获得冲刷。

### B2 —— **撤销（上一版误报，已核实不成立）**

上一版称「羽毛球重试成功后不重排 10 秒自动结算定时器（`enterReadOnly` 清掉了，`onRetrySuccess` 没重排）」。**实际会重排**：

唯一不重排的路径是 `source === 'settled'`（`index.vue:633-638`）——那里直接跳战报页，本来就不需要定时器。上一版建议的那一行补丁是冗余（只会先 `clearTimeout` 再重设）。

### B3 `lock-status` 扩展 `sameToken`（后端比对请求头锁 token）

- `backend/src/main/java/com/scoring/backend/domain/vo/MatchLockStatusVO.java` 只有 `locked / sameAccount / lockExpireTime`，协议层确实分不出「同账号」与「同设备」。

> 2026-10-25 已实施：`lock-status` 返回 `sameToken`，前端探测带 `X-Match-Lock-Token` 头并以服务端判定取代 URL 约定，`skipReplaceConfirm` 废除；旧后端降级为同账号持锁一律弹确认。

而 `utils/back-navigation.js:147-150` 有 **600ms 转场节流**：窗口内调用**静默 return**，调用方拿到的仍是 undefined → 视为「已离页」→ 遮罩被清、页面仍冻结（`isReadOnly`）。排球记分页 `pages.json:83-87` 是 `navigationStyle: custom` 且页内无返回按钮（`grep 返回/退出` 只命中 state-page 的兜底按钮），iOS 上属于无出口冻结页。

**概率**：仅在「刚发生过一次导航（<600ms）就点遮罩返回」时触发（典型：进入被拒遮罩后立刻点返回）。**改法二选一**：① 三个页面把 `navigateBackOrHome` 的节流状态暴露出来（如 `back-navigation.js` 返回 boolean），`onBack` 直接透传；② 或让 guard 的 `back()` 在清遮罩后延迟一段时间检查页面是否还在栈内，不在则重新 `showDenied`。
