# 项目复盘与答辩准备 — 亮点 · 踩坑 · 设计决策

> **用途**: 求职/答辩/复盘时的「怎么讲这个项目」底稿。配合 [[TECH_STACK.md]]（技术点怎么落地）一起用。
> **原则**: 每条都来自真实代码与真实开发日志，不是通用话术。面试时优先讲「为什么这么设计」和「踩过的坑」，而不是罗列功能。

---

## 1. 一句话定位

一个**从创建赛事到赛后归档全闭环**的微信小程序（羽毛球 + 排球双运动，含苏迪曼杯式团体赛与接力追分赛），前端 uni-app（Vue 3）双端编译，后端 Spring Boot 3 + MyBatis-Plus + MySQL + Flyway。核心难点不在「记分」本身，而在**赛制流转的状态机**、**团体赛父子比赛模型**和**可配置的小组排名引擎**。

---

## 2. 项目亮点（按「含金量」排序）

### 2.1 可配置的小组排名引擎（最有含金量）

- 把排名规则从代码里抽出来：`RankingConfig`（判据优先级序列）+ `GroupStandingEngine`（通用排序引擎）。
- 4 类比赛（个人 / 苏杯五项 / 接力追分 / 排球）是**互相独立的排名域**，各有预设模板，不能跨类型复用判据——因为团体赛比个人赛多「场内大分/场内局」一层。
- 支持自定义判据序列，且**系统会自动补一个兜底判据**（`systemFallbackCriterion`）保证任何输入都能排出序、不会死循环或永远「未决」。
- 难点：多人并列的 H2H 循环比较、退赛策略（删除 vs 单场判负）、差值 vs 比率两种算法。

### 2.2 链表式淘汰树（含三四名败者链路）

- 淘汰赛不用邻接表，而是「指针式」：每场记录 `next_match_id + next_match_slot`（胜者去向），三四名赛再加 `loser_next_match_id + loser_next_match_slot`（败者去向）。
- 结算一场比赛只改自己和「下一场」的两个字段，**多场并行结算互不干扰**，不用重算整棵树。

### 2.3 团体赛父子比赛模型（苏迪曼杯 + 接力）

- 苏杯五项是一场父级团体赛 + 5 场按需创建的子比赛；接力追分是另一种「分段连续累计」模型。
- 难点：父比赛按子项胜负数自动结算、子比赛的场内局/局内小分要回滚到父比赛排名。

### 2.4 排球状态机的复杂度收敛

- 记分、发球权、轮转、自由人换人、队长切换、换边，全部收进 `useScoreboard.js`（2200+ 行）一个 composable，Phone/Pad 只做 UI。
- `match-state.js` 抽成**纯函数**（不依赖 Vue），缓存读写以 `matchId` 为 key，可独立测试。
- 事件同步用 **800ms 防抖 + 按 eventSeq 幂等 upsert**，扛住高频加分、断线重试。

### 2.5 工程化细节

- **Flyway 19 个版本**管 schema 演进；**雪花 ID 统一字符串传输**（防 JS 精度丢失）；**ThreadLocal 鉴权**分层；**悲观锁 `SELECT ... FOR UPDATE`** 防并发重复结算/生成。
- 双端适配：横屏记分板强制 `pageOrientation: landscape`，`isTablet` 分流，6 档尺寸 + `clamp` + CSS 变量。

## 3. 踩坑复盘（面试重点：讲「坑」比讲「功能」分高）

> 每条结构：**现象 → 根因 → 解法 → 通用教训**。

### 坑 1：撤销历史套娃，把本地存储打爆

- **现象**: 微信开发者工具报 `setStorageSync:fail exceed storage max size 10Mb`。
- **根因**: `pushHistory()` 存的是「完整比赛快照」，而快照里又带着 `historyStack` 自己 → 历史里嵌历史，体积指数膨胀。
- **解法**: 快照剥离 `historyStack`；写失败时退化为「清空撤销历史再落盘」。
- **教训**: 序列化/快照必须排除自引用结构；本地存储要设上限和降级路径。

### 坑 2：`<switch>` 组件兼容性导致整页逻辑静默失效

- **现象**: 新增按钮不显示、自动结算不生效。
- **根因**: Uni-app 旧版 Vue 3 下 `<switch>` 原生组件编译**静默失败**，整个文件新增逻辑未生效——不是报错，是「看起来没反应」。
- **解法**: `<switch>` → 按钮式 toggle 组；`reactive` → `ref`；箭头函数 → function 声明。
- **教训**: 小程序原生/自定义组件有静默失败的坑，新功能要逐点验证「真的渲染出来了」。

### 坑 3：`<button>` 硬编码样式，CSS 覆盖不动

- **现象**: 规则弹窗的步进器按钮突出界面。
- **根因**: 微信小程序 `<button>` 有硬编码的 `min-width`/`padding`，CSS `width` 覆盖不了。
- **解法**: 自定义控件里 `<button>` → `<view>`。
- **教训**: 小程序原生组件默认样式不可控，做自定义控件优先用 `view`。

### 坑 4：排球创建误走羽毛球校验链路

- **现象**: 排球加了队伍，创建比赛仍报「选手列表不能为空」。
- **根因**: 请求误走羽毛球旧校验，只死看 `sportType`。
- **解法**: 后端兼容——请求里**有 `teams` 且没有 `players`** 就按排球处理，不再只信前端传的类型字段。
- **教训**: 多运动类型入口要按「实际提交的数据形态」判断，不能只信一个类型字段。

### 坑 5：自由人轮转两层错位

- **现象**: 副攻失去发球权后自由人不是立刻换上，要拖几轮；甚至「自由人到前排不换回」「同一自由人同时出现在两个位置」。
- **根因**: 混着两层问题——内部 6 槽位轮转顺序 vs 页面展示顺序没对齐；自由人运行态把「绑定自由人」误认成「普通持有人」。
- **教训**: 排查这种 bug，先统一「场上 1-6 号位认知」再看状态机；位置认知一偏，后面判断全歪。

### 坑 6：换边后屏幕左右对应乱掉

- **现象**: 换边后屏幕左侧到底是原始 left 还是 right，逻辑和展示对不上。
- **根因**: `displaySideSwapped` 语义含糊。
- **解法**: `match-state.js` 显式新增 `screenLeftParticipantSide` 记录「屏幕左 ↔ 原始参赛方」的映射，并自动迁移旧缓存。
- **教训**: 「换边」这类状态必须显式建模映射关系，且要考虑旧缓存兼容迁移。

### 坑 7：废弃接口连坐测试套件

- **现象**: 全量 `mvn test` 长期红。
- **根因**: `theme-config` 接口整段注释了，但相关测试还在。
- **教训**: 废弃接口要连测试一起清，否则测试套件失去「红 = 真出问题」的信号价值。

### 坑 8：雪花 ID 的 JS 精度

- **根因**: 19 位雪花 ID 超过 JS `Number.MAX_SAFE_INTEGER`（2^53 - 1），JSON 当 number 传输会精度丢失。
- **解法**: 所有 ID 统一字符串传输，前端原样比较。
- **教训**: 前后端 ID 类型契约要早定，否则排查「同一个 ID 对不上」会非常痛苦。

## 4. 设计决策 Q&A（「为什么这么设计」答辩稿）

### Q1 淘汰赛为什么用「链表指针」而不是邻接表/树？

每场比赛只改自己和「下一场」的两个字段，结算 O(1)，多场并行互不干扰。邻接表/树在每次晋级后要重算整棵树的展示状态，而指针式天然贴合「按场推进」的增量结算模型。代价是多了几个字段，重置/退赛时要小心维护指针。

### Q2 鉴权为什么拆成「拦截器解析」和「Guard 强制」两层？

`AuthInterceptor` 只做「解析 token → `AuthContext` 存 ThreadLocal」，`AuthGuard.requireUserId()` 才「强制登录」。好处是公开接口（赛事列表/详情）也能拿到「可选的当前用户」用于 favorite 状态，受保护接口才强制。ThreadLocal 在 `afterCompletion` 里 `clear()`，防止线程池复用串号。

### Q3 为什么所有 ID 用雪花算法 + 字符串传输？

雪花算法无需中心化发号、天然有序，适合分布式；19 位超过 JS 安全整数，必须字符串传输防精度丢失。

### Q4 为什么不用 Pinia/Vuex，而用 `reactive()` 模块单例？

当前全局状态只有登录态（`store/auth.js`），规模不需要 Pinia。用 Vue 3 的 `reactive()` 导出模块级单例就够了，少一个依赖、少一层心智负担。等状态真的复杂了再迁，迁移成本也不高。

### Q5 为什么把排球核心逻辑收进一个 2200+ 行的 composable，而不是拆散？

刻意「集中复杂度」：所有排球状态流转（记分/轮转/自由人/队长/换边）共享同一份响应式状态，拆散反而要靠事件总线传状态、更难排查。Phone/Pad 只做 UI 差异。代价是文件大，靠 `match-state.js` 纯函数兜底可测性。

### Q6 为什么 `match-state.js` 必须是纯函数？

它不依赖 Vue，任何上下文（页面/composable/测试）都能调，缓存读写集中、可单测；「离开页面必须 clear」的约定也收在这里统一管。

### Q7 排名引擎为什么「按比赛类型隔离模板」，还加系统兜底判据？

个人赛三层分数、苏杯四项四层、接力只有胜负+小分、排球有积分制——一套规则解释不了所有。隔离模板避免「把个人赛的胜局/小分拿去解释团体赛」。系统兜底判据（`POINT_WIN_RATE` / `TEAM_CHILD_POINT_WIN_RATE`）保证任意判据序列最终都能排出序，不死循环、不永远「未决」。

### Q8 为什么引入 Engine 层，不让 Service 直接算？

`BracketEngine` / `RoundRobinEngine` / `GroupStandingEngine` 是纯算法、不依赖 Spring Bean/Mapper，可独立单测。Service 负责编排（查数据、加锁、落库），Engine 负责计算——职责清晰。

### Q9 结算/生成淘汰赛为什么用悲观锁？

`SELECT ... FOR UPDATE` 锁住 tournament / match 行，防止「双人同时点生成淘汰赛」或「同时结算」导致重复推进。并发量不大，悲观锁简单可靠。

### Q10 横屏记分板怎么做的双端适配？

`pageOrientation: landscape` 强制横屏；`isTablet` 判断分流 Phone/Pad 两个组件；6 档尺寸 + `clamp()` + CSS 变量统一缩放。逻辑完全共享，只是 UI 不同。

## 5. 可能的追问与扩展点（提前想好）

- **换一种运动（乒乓球/篮球）怎么加？** 在 Engine 层加算法、在 `RankingConfig` 加模板/判据、加 sportType 枚举和专属记分板，主体链路复用。
- **观众想实时围观比分怎么办？** 现在比分在本地；需要只读接口 + 轮询或 WebSocket 推送，加「比赛进行中可读」的鉴权放行。
- **数据量大以后？** 赛事列表加分页/索引、热门接口加短缓存（PreLaunchAudit 也提到无缓存问题）、冷数据归档。
- **安全？** JWT 过期/刷新、HTTPS、裁判密码哈希、越权校验（当前已按创建者/裁判双角色守卫）。
- **多端一致性？** 微信小程序 + H5 一套代码，靠 `#ifdef H5` 条件编译隔离差异。
