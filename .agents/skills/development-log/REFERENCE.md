# DevelopmentLog.md 写作要求

这份参考文件固化的是当前项目里已经确认下来的 `DevelopmentLog.md` 写法偏好。后续更新日志时，优先遵守这里的规则。

## 1. 目标

`DevelopmentLog.md` 不是正式文档，也不是对外汇报材料，而是“自己回看时能快速找回上下文”的开发日记。

它要回答的核心问题是：

- 这阶段到底做了什么
- 哪些关键决策是怎么定下来的
- 哪些地方是用户反复讨论后改过的
- 当前项目实际推进到了什么程度

## 2. 内容取舍

优先写：

- 方向性决策
- 结构性调整
- 用户纠正过的关键设计细节
- 已经落地的功能链路
- 联调中发现的真实问题与修复
- 当前阶段判断和后续原则

少写或不写：

- 纯命令执行过程
- 无价值的试错
- 重复描述
- 过长测试日志
- 过度正式的背景铺垫

## 3. 语气与密度

- 全文中文
- 偏口语、但要清楚
- 像自己写给自己看的项目日记
- 保留关键细节，但不追求面面俱到
- 不要一大坨，也不要一行一个碎句写得太散

推荐状态是：

- 有层次
- 比较紧凑
- 一眼能扫到重点

## 4. 当前认可的排版风格

当前用户已经明确认可的风格是：

- 文件顶部允许保留 `<!-- markdownlint-disable -->`
- 用 `# Development Log` 作为总标题
- 每次记录用 `## 日期 + 阶段标题`
- 先用 1 段总述交代本阶段方向
- 中间穿插少量说明性短段落
- 关键点用 `-` 条目列出
- 每个 `-` 条目前加一个硬 Tab 缩进
- 空行要有，但不要太多

简单示意：

```md
<!-- markdownlint-disable -->

# Development Log

## 2026-06-09 某阶段

这一阶段先把大方向定下来了……

	- 关键点一
	- 关键点二

这里补一小段解释……

	- 调整点一
	- 调整点二
```

## 5. 这一项目里特别要保留的内容

如果日志来自当前这类开发协作，优先保留：

- 共享大厅还是拆分大厅这类产品结构决策
- 创建流程是否复用旧模型
- 页面布局被纠正过的地方
- 交互流程为什么改
- 主链路已经搭到什么程度
- 某个真实 bug 是怎么暴露、怎么修掉的

一句话原则：重点写“改了什么、为什么改、现在到哪了”，不要写成机械流水账。
